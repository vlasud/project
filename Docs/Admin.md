# Админ-система

Код: `Src/Services/AdminService` (источник правды об уровнях/пароле),
`Src/Services/BanService` (источник правды о банах), `Src/Systems/AdminSystem`
(подписчик: команды, диалоги, персист), права команд —
`Src/Services/Core/PlayerCommandService` + резолвер в
`Src/Systems/Core/PlayerCommandSystem`. SQL: `Sql/admins.sql`, `Sql/bans.sql`.

Покрывает: уровни доступа, вход в админку `/alogin`, выдачу/снятие уровня
`/setadmin` (с диалоговой регистрацией пароля для новой цели), админ-чат `/a`,
кик `/kick`, **бан аккаунта `/ban`** (проверка активного бана — на логине),
справку `/ahelp` (диалог со списком доступных команд по эфф. уровню) и **пакет
команд воздействия на игрока** (`/sethp`, `/setarmour`, `/slap`, `/agun`,
`/askin`, `/devskin`) + личный карманный телепорт админа (`/savepos`, `/tppos`).

Входящий канал жалоб ОТ игрока — репорт из меню `/mn` («Связь с администрацией»):
текст уходит всем залогиненным админам онлайн строкой `[Репорт] {ник}[{id}]:
{текст}` (`ADMIN_COLOUR`, тег `[Репорт]` ≠ `[A]`) и в файл-лог. Ответ — обычным
`/an {id}`. Источник правды кулдауна и журнал — `Src/Services/Core/ReportService`,
рассылку делает `Src/Systems/Core/MenuSystem`; механика — `Docs/PlayerMenu.md`.

## Модель прав команд

Команда декларирует ГРУППУ и ПОРОГ через `PermissionSpec` (тегированный union),
не зная, КАК это проверяется. Резолвер (`PermissionResolver`, задаётся
владельцем `PlayerCommandService` — `PlayerCommandSystem`) транслирует спек в
серверные факты. Одна механика гейтит и админов (числовой уровень), и орг-команды
(членство/битовая маска фракции — это НЕ числовая лестница).

`PermissionSpec::Kind`:

| Kind | Поля | Резолвер |
|----|----|----|
| `None` | — | всегда `true` (команда открыта всем) |
| `AdminLevel` | `adminLevel` | `AdminService::getEffectiveLevel(id) >= adminLevel` |
| `FactionMember` | `factionId` | `FactionService::getMemberFaction(id) == factionId` |
| `FactionPermission` | `factionId`, `factionMask` | член фракции И (`mask==0 ? true : hasPermission(id, mask)`) |

Фабрики: `PermissionSpec::admin(level)`, `factionMember(id)`, `faction(id, mask)`.

`PlayerCommandService::add(name, params, handler, perm = {})` — хвостовой `perm`
по умолчанию `None` (существующие вызовы не меняются). Проверка — в `dispatch`
ПОСЛЕ антифлуда и ДО разбора аргументов. Отказ (либо резолвер вернул `false`,
либо резолвер не задан при `perm != None`) → `dispatch` возвращает `false`,
ничего не отправляя. Дальше `PlayerCommandSystem` показывает текст неизвестной
команды.

**Единый ответ** на отказ прав и реальную неизвестную команду:
`Неизвестная команда. Введите /help` (решение геймдизайнера). Тот, кому команда
недоступна, не отличит её отсутствие от отсутствия прав — существование команды
не палится (защита от прощупывания).

### Гейт dev/debug/editor-тулинга

Весь дев/дебаг/редакторский тулинг гейтится `admin(DEVELOPER_LEVEL)` (порог 6) —
доступен ТОЛЬКО разработчику (эффективный уровень >= 6, а 6 достижим лишь прямым
INSERT в БД). Любому другому игроку команда отвечает как «неизвестная» (см. выше),
поэтому само существование тулинга не палится.

Под гейтом (`PermissionSpec::admin(AdminService::DEVELOPER_LEVEL)`):

| Система | Команды |
|----|----|
| `EditorSystem` | `/editor` |
| `TextDrawEditorSystem` | `/td` |
| `GangZoneEditorSystem` | `/gzone`, `/gzhere` |
| `DebugCameraSystem` | `/camera`, `/cpoint`, `/cplay` |
| `VehicleDebugSystem` | `/veh`, `/vput`, `/vdel`, `/vrespawn`, `/vinfo`, `/vhp`, `/vrepair`, `/vengine`, `/vlock`, `/vmod`, `/vhack` |
| `LocationDebugSystem` | `/pos`, `/tp`, `/tpup`, `/vw`, `/int`, `/hackpos`, `/vel`, `/veldebug`, `/violations`, `/acclear` |
| `GridDebugSystem` | `/gridtest`, `/gridclear`, `/gridcell`, `/streamdebug`, `/near` |
| `SpectateSystem` | `/spec`, `/specoff` |
| `WeaponDebugSystem` | `/rof` |
| `ElectionSystem` | `/edev` (только дев-меню выборов; голосование через урны НЕ гейтится) |
| `FactionSystem` | `/fdev` (только дев-меню фракций; игровые `/faction`/`/invite`/… НЕ гейтятся) |

Гейт декларативный: только хвостовой `perm` в `add(...)`, тела обработчиков не
изменены. Раньше эти команды (спавн машин `/veh`, телепорт `/tp`, чит-имитации
`/vhp`/`/hackpos`/`/vhack`, все редакторы) были открыты любому игроку — теперь
закрыты под разработчика.

## Уровни доступа

Эффективный уровень = `loggedIn ? storedLevel : 0`. Гейтит команды ИМЕННО
эффективный уровень: до успешного `/alogin` в текущей сессии он 0, даже если в БД
записан уровень 5.

| Уровень | Имя (геймдизайнер) |
|----|----|
| 0 | не админ |
| 1 | Младший модератор |
| 2 | Модератор |
| 3 | Старший модератор |
| 4 | Администратор |
| 5 | Главный администратор |
| 6 | Разработчик |

Имена — в `LEVEL_NAMES` (анонимный namespace `AdminSystem.cpp`).

Константы уровней (`AdminService`):

| Константа | Значение | Смысл |
|----|----|----|
| `DEVELOPER_LEVEL` | `6` | «Разработчик» — авто-логин без пароля, только из БД |
| `MAX_LEVEL` | `6` | абсолютный максимум (загрузка из БД + диапазон имён `LEVEL_NAMES`) |
| `MAX_ASSIGNABLE_LEVEL` | `5` | максимум, который выдаёт `/setadmin` (и `setLevel`/`finalizeRegistration`) |

**Уровень 6 («Разработчик») — абсолютный максимум, выставляется ТОЛЬКО прямым
INSERT в БД.** Командного пути выдать или снять 6 нет: `/setadmin` ограничен
диапазоном 0..5 (`MAX_ASSIGNABLE_LEVEL`), а `setLevel`/`finalizeRegistration`
клампят к тому же значению. Разработчику **не нужен админ-пароль**: на старте
сессии `cacheLoaded` при `storedLevel >= DEVELOPER_LEVEL` сразу ставит
`loggedIn = true`, поэтому `getEffectiveLevel` отдаёт 6 без `/alogin`, и
разработчик попадает в рассылку `/a` (она по `isLoggedIn`). Авто-логин без
пароля даётся СТРОГО для уровня из БД (в `cacheLoaded`), а не из команды —
самоэскалации до 6 нет. `/alogin` для разработчика вернёт «Вы уже вошли в
админку» (он уже залогинен — отдельной ветки не нужно). Эффективный уровень 6
≥ 5 даёт разработчику доступ к `/setadmin` (для уровней 1..5) и иммунитет к
`/setadmin`/`/kick`/`/ban` от уровня 5 (иерархия по `storedLevel`: `6 >= 5`).

## Команды и пороги

| Команда | Порог | Действие |
|----|----|----|
| `/alogin <пароль>` | `None` (проверки внутри) | вход в админку |
| `/setadmin <id> <уровень>` | `admin(5)` | выдать/снять уровень (0..5; уровень 6 командой не выдаётся) |
| `/a <текст>` | `admin(1)` | админ-чат всем залогиненным админам |
| `/kick <id> <причина>` | `admin(1)` | кик игрока |
| `/goto <id>` / `/gethere <id>` | `admin(1)` | админ-телепорт к игроку / игрока к себе |
| `/savepos` / `/tppos` | `admin(1)` | личная закладка координат админа (на себя) |
| `/slap <id>` | `admin(2)` | подброс игрока вверх на фикс. высоту |
| `/ban <id> <дней> <причина>` | `admin(3)` | бан аккаунта на дни + кик |
| `/sethp <id> <hp>` | `admin(4)` | задать здоровье (0..100) |
| `/setarmour <id> <броня>` | `admin(4)` | задать броню (0..100) |
| `/askin <id> <скин>` | `admin(4)` | временный скин сессии (1..311, кроме 74) |
| `/agun <id> <оружие> <патроны>` | `admin(5)` | выдать оружие (0..46) с патронами (1..9999) |
| `/devskin <id> <скин>` | `admin(6)` | основной скин (память + БД) |
| `/ahelp` | `admin(1)` | диалог со списком доступных команд (по эфф. уровню) |

Цвет всех админ-сообщений — `ADMIN_COLOUR = Colour::FromRGBA(0xFFB400FF)`.

### /alogin

1. Не активная сессия — тихий выход.
2. Уже залогинен → «Вы уже вошли в админку» (сюда же попадает разработчик, уже
   авто-залогиненный в `cacheLoaded`).
3. В lockout → «Слишком много попыток входа. Подождите N сек.».
4. Не зарегистрирован ИЛИ `storedLevel == 0` → ЕДИНЫЙ отказ «Неверный пароль» +
   `registerFailedLogin` (не палим, что аккаунт не админ).
5. Иначе верификация пароля на ВОРКЕРЕ (`crypto_pwhash_str_verify`), в колбэке
   serial-guard. Успех → `setLoggedIn(true)`, `clearLoginFails`, «Вход в админку
   выполнен. Уровень: N — Имя». Провал → `registerFailedLogin` + «Неверный
   пароль».

### /setadmin

- цель невалидна/не в сессии → «Игрок не найден»; `id == self` → «Нельзя
  изменить собственный уровень»; уровень вне 0..5 (`MAX_ASSIGNABLE_LEVEL`) →
  «Уровень должен быть от 0 до 5» (уровень 6 командой недостижим);
  `target.storedLevel >= actor.storedLevel` → «Цель равна вам по уровню или
  выше» (иерархия по СОХРАНЁННОМУ уровню, не эффективному; разработчик с
  `storedLevel = 6` неприкосновенен для уровня 5);
- `level == 0` → снятие (`setLevel 0`, сброс логина), сообщения + лог;
- `level >= 1` и цель уже зарегистрирована → `setLevel`, сообщения + лог;
- `level >= 1` и цель НЕ зарегистрирована → запуск диалоговой регистрации на
  цели, pending level = level.

### Регистрация админа (диалоги пароля)

Пер-цель `PendingRegistration{active, level, firstPassword, serial}`. `serial` —
сессии ЦЕЛИ на момент старта (колбэки диалогов/финал сверяют его).

1. `DialogStyle_PASSWORD` «Регистрация админа — Пароль», тело «Придумайте
   админ-пароль. Минимум 8 символов». `< 8` символов → «Минимум 8 символов!» +
   повтор. Правая кнопка = отмена назначения.
2. Подтверждение «Регистрация админа — Подтверждение», тело «Повторите
   админ-пароль». Несовпадение → «Пароли не совпадают» + назад к шагу 1. Правая
   кнопка = назад.
3. Финал: IP цели берётся серверно
   (`getNetworkData().networkID.address` → `PeerAddress::ToString`),
   `AdminService::finalizeRegistration` хеширует пароль и пишет строку НА
   ВОРКЕРЕ; колбэк (serial-guard) сидирует кэш `cacheLoaded`, авто-логинит
   (`setLoggedIn(true)` — цель только что доказала пароль) и шлёт «Вы
   зарегистрированы как админ. Уровень: N — Имя».

### /a

Формат `[A] [<Имя уровня>] <Имя>[<id>]: <текст>`, цвет `ADMIN_COLOUR`. Текст —
жадный параметр; обрезка `MAX_ADMIN_CHAT_BYTES = 180` (utf-8, ~90 кириллических)
через `sanitizeUserText`. Рассылка всем онлайн с `isLoggedIn` — O(online).

### /kick

Цель невалидна → «Игрок не найден»; `target.storedLevel >= actor.storedLevel` →
«Нельзя применить к этому игроку». Иначе лог в `[A]`, сообщение кикнутому,
`target->kick()`. **Причина обязательна** (см. «Отступления»).

### /ban

Бан АККАУНТА на дни (порог `admin(3)`). Параметры: `id`, `дней`, `причина`
(жадный последний параметр, обязателен).

- цель невалидна ИЛИ нет активной сессии → «Игрок не найден» (бан пишется по
  `accountId` — источнику правды связки, поэтому сессия обязательна);
- `id == self` → «Нельзя применить к этому игроку»;
- `target.storedLevel >= actor.storedLevel` → «Нельзя применить к этому игроку»
  (иерархия по СОХРАНЁННОМУ уровню, как в `/kick`/`/setadmin`);
- `дней` вне `1..365` → «Срок бана должен быть от 1 до 365 дней» (валидация ДО
  записи);
- иначе: `accountId` цели и админа берутся из сессий, IP цели — серверно
  (`getNetworkData().networkID.address` → `PeerAddress::ToString`);
  `BanService::banAccount` пишет строку `ban` (`banned_until = NOW() + INTERVAL
  дней DAY`, причина обрезана `MAX_BAN_REASON_BYTES`, `banned_by`, `ip`); лог в
  `[A]` (`{админ}[{id админа}] забанил {имя}[{id}] на N дн. Причина: ...`), сообщение
  забаненному «Вы забанены на N дн. Причина: ...», `target->kick()`.

| Константа | Значение | Смысл |
|----|----|----|
| `MIN_BAN_DAYS` | `1` | минимум срока |
| `MAX_BAN_DAYS` | `365` | максимум срока (перм-бан — отдельная механика, не `/ban`) |
| `MAX_BAN_REASON_BYTES` | `120` | обрезка причины (utf-8 байт до записи; в БД хранится utf-8, < `VARCHAR(128)`) |

IP цели пишется **в запас** (под будущий IP-бан) и на проверку логина пока не
влияет — банится именно аккаунт.

### Команды воздействия на игрока и dev-телепорт

Пакет «рук» администратора: прямое изменение состояния игрока (здоровье, броня,
оружие, скин), физический толчок (`/slap`) и личная закладка координат
(`/savepos` + `/tppos`). Полная спецификация механики/баланса/иерархии и ВСЕХ
текстов — `Docs/GameDesign/UI_Texts.md`, подраздел «Команды воздействия на игрока
и dev-телепорт».

**Легитимность для анти-чита (ключевой инвариант).** Все изменения идут СТРОГО
через сервисы, которые ставят грейс-окно — иначе валидаторы зафиксировали бы
ложный чит:

| Команда | Сервис | Почему не сырой вызов |
|----|----|----|
| `/sethp`, `/setarmour` | `PlayerHealthService::setHealth/setArmour` | сырой `player.setHealth` → HealthHack (несанкционированный рост HP) |
| `/agun` | `PlayerWeaponService::giveWeapon` | регистрирует выдачу в серверный инвентарь + грейс → нет WeaponHack |
| `/askin` | `PlayerSkinService::setSkin` | временный скин сессии (переживает респаун, в БД НЕ пишется) |
| `/devskin` | `PlayerPersonalSkinService::setSkin` + `PlayerSkinService::setSkin` + БД | основной скин аккаунта (память + применить сразу + write-through) |
| `/slap`, `/savepos`, `/tppos` | `PlayerLocationService::getPosition/teleport` | `teleport` ставит грейс позиции → нет TeleportHack |

**Иерархия (по СОХРАНЁННОМУ уровню, как `/kick`).** ДА у `/sethp`, `/setarmour`,
`/slap`, `/agun` (необратимое/силовое вмешательство в чужую игру); НЕТ у `/askin`
(косметика, вреда состоянию нет), `/devskin` (только уровень 6 — вершина,
проверка не сработала бы), `/savepos`/`/tppos` (на себя, цели нет). У `/agun`
иерархия на чужого, но на СЕБЯ разрешена (вооружить себя мимо иерархии безвредно).

**Диапазоны (валидируются ДО применения — клиентскому числу не верим).** HP/броня
`0..100` (`MIN_VITAL`/`MAX_VITAL`) — верх запрещает невидимый god-режим через
«сверх-HP»; оружие `0..46` (`MIN_GUN_ID`/`MAX_GUN_ID`) И слот оружия валиден
(`WeaponSlotData(id).slot() != INVALID_WEAPON_SLOT` — отсекает дыры диапазона);
патроны `1..9999` (`MIN_AMMO`/`MAX_AMMO`); скин `1..311` кроме 74
(`PlayerSkinService::isValidSkin`). `/slap` — фикс. высота `SLAP_HEIGHT = 5.0`
(параметр не даём, иначе шлепок стал бы орудием убийства).

**Играбельное состояние цели** (`isPlayingState`) требуется там, где берём/ставим
позицию или HP: `/sethp`, `/setarmour`, `/slap` (цель), `/savepos` (сам админ).
Невалидное состояние → «Игрок не найден» (для `/savepos` — «Сейчас нельзя
сохранить координаты»). Иначе перенос/правка по мусорной позиции мёртвого.

**Цель не уведомляется** ни одной из этих команд (столп «кто админ — не палится»):
игрок и так видит обратную связь в игре (полоска HP, броня, оружие, скин,
физический подброс). Прозрачность — канал `[A]` + файл-лог (`logAdminAction`), кроме
`/savepos`/`/tppos` (личный телепорт — в `[A]` НЕ объявляется).

**`/devskin` и БД.** Активная сессия цели ОБЯЗАТЕЛЬНА (основной скин пишется по
`accountId` из сессии; нет сессии → «Игрок не найден»). Write-through —
`DatabaseManager::throwQuery` `UPDATE player SET skin=? WHERE id=<accountId>` (тот
же паттерн, что персист в `PlayerPersonalSkinSystem`). UPDATE без чтения обратно;
в колбэке к игроку не обращаемся (он мог выйти), поэтому serial-guard не нужен.
Замечание: если цель во фракции, применённый `m_skinService.setSkin` перетрёт
органный скин до следующей смены фракции — это поведение задано ГД дословно
(«применить сразу»), основной личный скин при этом корректно осел в память + БД.

**`/savepos`/`/tppos`.** Состояние — `PlayerSavedLocationService` (Core, только
память, без БД): пер-игрок `{position, interior, virtualWorld, valid}`, O(1)
доступ. `/savepos` пишет принятую сервером позицию/интерьер/мир; `/tppos` без
сохранённой точки → «Сначала сохраните координаты: /savepos». Сброс слота — на
конце сессии (`AdminSystem` subscribeEnd, рядом с `m_adminService.reset`), иначе
координаты одного админа утекли бы в переиспользованный слот.

### /ahelp

Диалог со списком админ-команд, доступных игроку **на его текущем эффективном
уровне** (порог самой `/ahelp` — `admin(1)`, поэтому не-админ её не видит — единый
ответ «неизвестная команда»). Разработчик (эфф. 6) видит и весь dev-тулинг.

Список **не дрейфует от набора зарегистрированных команд**: он строится из РЕАЛЬНО
зарегистрированных команд и фильтруется ТЕМ ЖЕ резолвером, что и `dispatch` —
`PlayerCommandService::collectAccessible(player)` проходит по `m_commands`, берёт
только `Kind::AdminLevel` команды, у которых `m_permissionResolver(player, perm)`
== `true`, и возвращает `{name (нижний регистр), adminLevel}`. Игровые/`None`/
фракционные команды в список не попадают. Резолвер не задан → ни одной команды (как
в `dispatch`). Путь редкий (по команде), `O(числа команд)` на сбор + `O(n log n)`
сортировка — не per-tick.

Обработчик (`AdminSystem::cmdAdminHelp`): берёт `collectAccessible`, сортирует по
уровню (возр.), затем по имени, и собирает `DialogStyle_TABLIST_HEADERS` (колонки
«Команда | Описание»). Каждая группа уровня отбивается строкой-разделителем
`--- <Имя уровня> (ур. N) ---`, так что уровень каждой команды виден явно. Заголовок
«Доступные админ-команды», кнопка «Закрыть»; список read-only — на любой ответ просто
закрывается (реакции на выбор нет). Кириллица — через `u()`.

Описания — в **каталоге** `COMMAND_DESCRIPTIONS` (анонимный namespace
`AdminSystem.cpp`): таблица `имя команды (нижний регистр) → краткое описание` для
всех админ- и dev-команд (см. их в `LocationDebugSystem`/`VehicleDebugSystem`/
редакторах и т.д.). Команды без записи в каталоге показываются **без описания**
(граничный случай, не падает). Каталог — лишь подписи; источник истины НАБОРА
команд — резолвер, поэтому добавление новой админ-команды сразу попадает в `/ahelp`
(описание добавляется в каталог отдельно).

### Проверка бана на логине

Проверка активности бана — в `PlayerAuthSystem` (логин-`selectQuery` по имени, тот
же, что грузит аккаунт): `LEFT JOIN ban b ON b.account_id = p.id AND b.banned_until
> NOW()`, остаток дней считает БД (`CEIL(TIMESTAMPDIFF(SECOND, NOW(),
b.banned_until) / 86400)`), бана нет → NULL → 0. Один SELECT на логин (без
отдельного запроса и гонки за активностью). Если остаток > 0 — доступ НЕ выдаётся,
сессия НЕ стартует: «Аккаунт заблокирован. Осталось: N дн.» + `kick()`. Проверка
серверная и ДО логина — пройти мимо неё клиент не может. Сохранён существующий
guard логина (версия подключения `PlayerConnectionVersionService`).

## Анти-брутфорс /alogin

Антифлуд команд ловит лишь идентичные строки, перебор идёт разными паролями —
поэтому свой счётчик в `AdminService`:

| Константа | Значение | Смысл |
|----|----|----|
| `MAX_ALOGIN_ATTEMPTS` | `5` | после стольких неудач — lockout |
| `ALOGIN_LOCKOUT` | `60` с | длительность блокировки `/alogin` |

`registerFailedLogin` инкрементит; при достижении порога ставит lockout и
сбрасывает счётчик. `clearLoginFails` — на успешном входе. Состояние пер-игрок,
чистится `reset` на конце сессии.

## Персист (admin_account)

Таблица `admin_account` (см. `Sql/admins.sql`): `account_id` (FK `player.id`),
`level` (0..6; через `/setadmin` пишется только 0..5, уровень 6 — ручным INSERT),
`password_hash` (libsodium, NULL — пароля нет; для уровня 6 необязателен),
`registration_ip`, `registered_at`.

- старт сессии (`AdminSystem::loadAdmin`): `selectQuery` `level, password_hash` по
  `account_id`; колбэк со serial-guard сидирует `cacheLoaded` (клампит уровень к
  `[0, MAX_LEVEL]` = 0..6 и при уровне >= 6 авто-логинит без пароля). Нет строки →
  не админ (слот нулевой);
- конец сессии: `AdminService::reset(id)` + сброс pending-регистрации;
- запись write-through: `setLevel` (UPSERT level, `throwQuery`),
  `finalizeRegistration` (хеш + UPSERT всех полей на воркере).

Лайфцикл и serial-guard — строго через `PlayerSessionService::subscribeStart/End`
(конвенция персиста аккаунта).

## Персист (ban)

Таблица `ban` (см. `Sql/bans.sql`): `account_id` (PK, FK `player.id`),
`banned_until` (`DATETIME`, бан активен пока `> NOW()`), `reason`
(`VARCHAR(128)`, NULL), `banned_by` (аккаунт админа, NULL), `ip`
(`VARCHAR(46)`, IP цели в запас), `created_at`.

- запись write-through одной строкой: `BanService::banAccount` — `throwQuery`
  UPSERT (`ON DUPLICATE KEY UPDATE` перетирает срок/причину/IP/время; повторный
  бан того же аккаунта обновляет существующую строку), параметры через `.bind`;
- RAM-кэша нет: забаненный по определению не онлайн, источник правды — БД;
- чтение — только на логине (`PlayerAuthSystem`), см. выше.

## Бутстрап первого админа

`/setadmin` гейтится `admin(5)` — назначить может только уже залогиненный уровень
5 (или выше). В игре назначить первого супер-доступа некому, поэтому он заводится
вручную в БД. Рекомендуемый бутстрап — **уровень 6 («Разработчик»), без пароля**:

```sql
INSERT INTO admin_account (account_id, level) VALUES (<account_id>, 6)
ON DUPLICATE KEY UPDATE level = 6;
```

Уровень 6 авто-логинится на старте сессии (`cacheLoaded` ставит `loggedIn = true`
при `storedLevel >= 6`), `password_hash` не нужен. Эффективный уровень 6 ≥ 5 даёт
доступ к `/setadmin`, которым разработчик заводит остальных админов уровней 1..5
(цель задаёт пароль в диалоге регистрации). Снять или выдать уровень 6 командой
нельзя (диапазон 0..5 + иерархия по `storedLevel`) — только прямым изменением в БД.

Альтернатива — супер-админ уровня 5 С ПАРОЛЕМ (заходит через `/alogin`):

```sql
INSERT INTO admin_account (account_id, level, password_hash, registered_at)
VALUES (<account_id>, 5, '<libsodium crypto_pwhash_str хеш>', NOW())
ON DUPLICATE KEY UPDATE level = 5, password_hash = VALUES(password_hash);
```

Для уровней 1..5 `password_hash` ОБЯЗАТЕЛЕН: строка с `level` 1..5, но
`password_hash = NULL` даёт `registered = false`, и `/alogin` для неё вернёт
«Неверный пароль» (входа нет — защита от «фейкового» админа без пароля). Хеш нужен
валидный `crypto_pwhash_str` (тот же, что у игроков). Уровень 6 — единственный, для
кого `password_hash` опционален, потому что он авторизуется без `/alogin`.

## Логирование

`AdminSystem::logAdminAction`: строка уходит в админ-чат всем залогиненным админам
(канал `[A]`) и в файл-лог `LogManager::log(Message, "[ADMIN] ...")`.

## Три правила

- **Читер-абуз:** уровень гейтится `getEffectiveLevel` (0 до `/alogin`);
  уровень/пароль — серверные факты; уровень 6 («Разработчик») НЕДОСТИЖИМ через
  команды — только прямым INSERT в БД (`/setadmin` ограничен 0..5,
  `setLevel`/`finalizeRegistration` клампят к `MAX_ASSIGNABLE_LEVEL`); авто-логин
  без пароля даётся СТРОГО для уровня >= 6 из `cacheLoaded` (из БД), а не из
  команды — самоэскалации до 6 нет; единый отказ скрывает существование команд и
  кто админ; иерархия по `storedLevel` (нельзя трогать равного/старшего, в т.ч.
  разработчика с `storedLevel = 6`);
  анти-брутфорс `/alogin`; serial-guard на всех async-цепочках (верификация
  пароля, загрузка сессии, регистрация) — колбэк после дисконнекта/реслота не
  трогает чужой слот; IP берётся серверно. `/ban`: порог `admin(3)` (эффективный
  уровень); иерархия по `storedLevel` (нельзя равного/старшего/себя); срок
  `1..365` валидируется ДО записи; `accountId`/IP — серверные; запрос
  параметризован (`.bind`); проверка бана на логине серверная и до выдачи доступа
  — клиент её не обойдёт; срок бана считает БД от своего `NOW()`, не клиент.
  **Команды воздействия:** все изменения СТРОГО через сервисы (Health/Weapon/
  Skin/Location) — анти-чит уважает грейс, ложного срабатывания нет; иерархия по
  `storedLevel` у силовых (`/sethp`/`/setarmour`/`/slap`/`/agun`); god-режим
  запрещён клампом `0..100`; ВСЕ клиентские числа (hp/броня/оружие/патроны/скин)
  валидируются против диапазонов ДО применения; гейт прав в `dispatch` стоит до
  антифлуда и тел обработчиков (для постороннего команды «не существуют»); позиция
  для `/slap`/`/savepos` — принятая сервером (`LocationService`), не сырой клиент;
  `/devskin` — accountId из сессии (серверный факт), UPDATE параметризован.
- **Краш:** `get(id)` проверяется на `nullptr`; все геттеры сервиса bounds-guard
  по id; цель ре-fetch + serial в диалогах и async; libsodium-верификация и
  Argon2id — на ВОРКЕРЕ; никаких исключений в ядро. `/ban`: цель ре-fetch перед
  использованием; проверка бана под существующим guard логина; запись на воркере,
  mysqlx-объекты границу потока не пересекают (контракт `DatabaseManager`).
  **Команды воздействия:** null-гард цели до разыменования; играбельное состояние
  там, где берём/ставим позицию или HP; `/devskin` — активная сессия (иначе нет
  accountId); UPDATE на воркере без чтения обратно, к игроку в колбэке не
  обращаемся (мог выйти), serial-guard не нужен; `PlayerSavedLocationService` —
  bounds-check `[0, MAX_PLAYERS)` во всех методах, reset на конце сессии (нет
  утечки координат в реслот).
- **Перф:** резолвер прав O(1) без аллокаций; команды событийные; тяжёлый Argon2id
  — на воркере; `/a` рассылка O(online). `/ban` — событийный, одна строка-запись;
  проверка бана — тем же логин-`selectQuery` (LEFT JOIN), а не per-tick.
  **Команды воздействия:** все — холодный путь (по команде), не per-tick;
  `PlayerSavedLocationService` — O(1) доступ к `std::array`, без аллокаций;
  `/devskin` — единственный UPDATE-запрос на воркере (не блокирует главный поток).
