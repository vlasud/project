# Редактор аттачей (дев-тулинг)

Дев-инструмент для подгонки прикреплённых к игроку объектов (аксессуары,
инструменты в руке и т.п.) с сохранением/загрузкой пресетов в файл. Код:
`Src/Systems/Core/AttachmentEditorSystem`. Опирается на `AttachmentService`
(`Src/Services/Core/AttachmentService`) — источник правды о выданных слотах
аттачей игрока; редактор сам ничего не хранит, кроме сессии диалога (модель,
кость, offset/rotation/scale последнего прикреплённого объекта).

Команда: **`/aedit`** — единственная точка входа, открывает LIST-меню. Доступна
только `AdminService::DEVELOPER_LEVEL` (уровень 6, «Разработчик»); обычный
игрок команду вызвать не может (гейт — `PermissionSpec::admin`, резолвит
`AdminSystem`). Редактор всегда работает над аттачем САМОГО игрока, вызвавшего
команду (dev не может подогнать аттач чужому персонажу).

## Поток: гизмо — основной способ подгонки

Владелец: «для редактора использовать надо клиентский редактор, с гизмо».
Поэтому клиентский нативный редактор объекта (мышь — двигать/крутить/
масштабировать, клик — сохранить, ESC — отмена) — ГЛАВНЫЙ путь правки, а не
один из равнозначных пунктов меню:

1. Дев выбирает **«Приатачить/заменить объект»** → INPUT: ID модели
   (`0..19999`, диапазон `AttachmentService::sanitize`) → LIST: кость
   (18 пунктов, см. таблицу ниже) → `attach()` со стартовыми
   `offset=(0,0,0)`, `rotation=(0,0,0)`, `scale=(1,1,1)`.
2. Сразу после успешной привязки (слот заведомо валиден — только что создан)
   редактор БЕЗ возврата в меню открывает клиентский гизмо
   (`AttachmentService::beginEdit()` через `beginGizmoEdit()`) — дев сразу
   двигает/крутит/масштабирует объект мышью.
3. Клик — подгонка сохранена, ESC — отменена; в обоих случаях колбэк
   `beginGizmoEdit` возвращает в `showMain`. При `saved=true` итоговые
   offset/rotation/scale читаются ОБРАТНО из сервиса через
   `AttachmentService::slotData()` (гизмо кладёт их прямо в приватные данные
   слота, минуя числовые поля редактора) и обновляют сессию — иначе
   последующее «Сохранить в файл» унесло бы старые числа.

Если `attach()` не удался (нет свободных слотов/невалидные данные) —
сообщение об ошибке и обычный возврат в меню, гизмо не открывается.

## Меню

Пункты показаны ВСЕГДА (конвенция UI — не прятать недоступное); гейт — на
клике, не на видимости:

1. **Приатачить/заменить объект** — доступен без текущего аттача (см. поток
   выше — после успешной привязки сразу открывается гизмо). Если у сессии уже
   был активный слот — он снимается ПЕРЕД новым attach (один активный слот на
   сессию редактора; иначе повторные клики исчерпали бы 10 слотов игрока).
2. **Редактировать мышью (гизмо)** — ОСНОВНОЙ пункт правки, стоит первым после
   привязки (выше числовых полей). Требует уже привязанного слота (гейт
   `needsSlot`). Идентичен автооткрытию из п.1 — используется для повторной
   подгонки уже приатаченного объекта без пересоздания слота.
3. **Offset / Rotation / Scale** — ВТОРИЧНЫЙ путь: точный числовой ввод, когда
   нужны конкретные значения, а не «на глаз» мышью. Каждый пункт открывает
   INPUT-диалог, принимающий три числа `X Y Z` (разделитель — пробел или
   запятая). Ввод разбирается робастно: меньше/больше трёх чисел, нечисловой
   мусор или лишний токен — сообщение об ошибке и повтор того же диалога (без
   падения на сервер). Валидный ввод переприменяется через `attachToSlot()` на
   ТОТ ЖЕ слот — `AttachmentService::sanitize` дополнительно клампит offset
   (`[-10, 10]`) и scale (`[0.01, 10]`).
4. **Сохранить в файл** — INPUT: имя пресета → JSON-файл
   `attachments/<имя>.json`, запись АСИНХРОННО через `ThreadPool` (главный
   поток не блокируется).
5. **Загрузить из файла** — доступен и БЕЗ текущего аттача. Асинхронный список
   `attachments/*.json` → LIST выбора → асинхронное чтение → парсинг JSON на
   главном потоке (`try/catch` + пополевая валидация) → `attach()` к
   деву и загрузка распознанных данных в сессию для дальнейшей правки. Битый
   файл не роняет сервер — просто сообщение об ошибке.
6. **Снять объект** — `detach()` текущего слота + сброс сессии редактора.

Карточка меню всегда показывает ТЕКУЩИЕ параметры (модель, кость,
offset/rotation/scale) прямо в тексте пунктов — как во всех остальных
дев-редакторах проекта (`GangZoneEditorSystem` и т.п.).

На каждом клике под-меню (гизмо, offset/rotation/scale, сохранение, снятие)
слот РЕ-ВАЛИДИРУЕТСЯ через `AttachmentService::isAttached()` — дев мог
переподключиться в тот же id игрока или слот мог быть снят извне, пока висел
диалог; в этом случае сессия сбрасывается и показывается сообщение. При
автооткрытии гизмо сразу после привязки повторная проверка не нужна: слот
только что создан тем же вызовом.

## Формат файла пресета

`attachments/<имя>.json`:

```json
{
  "model": 2228,
  "bone": 6,
  "offset": [0.1, 0.0, -0.05],
  "rotation": [0.0, 0.0, 90.0],
  "scale": [1.0, 1.0, 1.0]
}
```

Парсинг (`AttachmentEditorSystem::parsePreset`) валидирует каждое поле
отдельно: `model` — целое `0..19999`; `bone` — целое `1..18`;
`offset`/`rotation`/`scale` — массивы РОВНО из трёх числовых элементов.
Любое несоответствие (тип, диапазон, отсутствующее поле, битый JSON) — файл
отклоняется целиком, дев получает сообщение об ошибке. Даже после парсинга
`AttachmentService::attach()` повторно санитизирует offset/scale перед
применением — двойная защита от порченого вручную файла.

## Защита от path traversal

Имя пресета — из клиентского INPUT-диалога, поэтому санитизируется ДО
использования в пути: разрешён только алфавит `[A-Za-z0-9_-]`, имя не может
быть пустым. Белый список уже сам по себе исключает `/`, `\`, `..`, `:` —
такое имя не может вывести запись/чтение за пределы каталога `attachments/`.
Невалидное имя — сообщение об ошибке и повтор диалога ввода (сохранение не
запускается).

## Читер-абуз / краш-безопасность / перф

- Команда `/aedit` — только `AdminService::DEVELOPER_LEVEL`; обычный игрок
  вызвать не может. Аттач — всегда на своём игроке (id вызвавшего команду).
- Все числовые параметры (модель, кость, offset, rotation, scale) клампятся
  `AttachmentService::sanitize` перед применением к клиенту — гигантский
  масштаб/оффсет на полкарты не пройдёт, даже если пресет отредактирован
  вручную.
- Файловый I/O — строго асинхронный (`ThreadPool`); все колбэки проверяют
  `onlinePlayer()` — дев мог выйти, пока читался/писался диск.
- Слот ре-валидируется на каждом клике под-меню; `detach()`/`attachToSlot()`
  bounds-safe по `playerId`/`slot`. На дисконнекте сессия редактора сбрасывается
  (сам аттач снимает `AttachmentSystem::resetPlayer`).
- Редактор полностью событийный (команда/диалоги/gizmo) — per-tick работы нет.
