# Семьи

Player-created социальные группы поверх фракций (не Core). Код:
`Src/Services/FamilyService`, `Src/Systems/FamilySystem`. Схема БД:
`Sql/families.sql` (`family`, `family_member`).

Горизонтальный социальный контур: «свои люди» параллельно вертикали организаций.
Семьи не дают рангов/скинов/цвета/денег (это только у фракций) — только название,
состав и приватный чат. Семья не конкурирует с фракцией: лимит участников держит
её социальной группой, а не второй организацией.

## Устройство

- **Семья — данные игрока** (в отличие от фракций — части кода): создаётся любым
  игроком в рантайме. В БД лежит целиком (write-through), переживает рестарт.
- **Одна семья на игрока.** Вступление — ТОЛЬКО по приглашению владельца (диалог
  подтверждения у приглашённого). Создание бесплатное.
- **Создание свободное — гейта по дому НЕТ** (убран решением владельца: раньше
  требовался свой дом). Любой авторизованный игрок без семьи создаёт её
  бесплатно; зависимость `FamilySystem` от `HouseService` удалена.
- **Лидер (владелец)** — создатель семьи (`owner_account_id`). Только он
  приглашает, выгоняет и распускает (роспуск теперь идёт через «Покинуть семью» —
  см. ниже).
- **Название — одно слово ЛАТИНИЦЕЙ**, 3–24 буквы (`FamilyService::validateName`:
  только `A-Z`/`a-z` — без цифр, пробелов, символов и кириллицы). Инъекция
  цветокодов в тег `[{название}]` невозможна по построению (не-буквы не
  проходят); `sanitizeName` остаётся первым шагом (обрезает края-пробелы —
  дружелюбно к « Corleone »), всё прочее честно отбраковывает валидация с
  текстом-правилом.
  - **Уникальность — регистронезависимая**: «vlasud» занял имя — «Vlasud» и
    «vlaSuD» не пройдут (`equalsIgnoreCaseAscii` в памяти; БД-UNIQUE на `name` в
    коллации `utf8mb4_general_ci` — страховочная сетка сворачивает регистр так
    же). С чистой латиницей ASCII-свёртка покрывает ВСЕ допустимые имена —
    прежнее ограничение «Корлеоне/корлеоне — разные» исчезло вместе с
    кириллицей. Существующей БД нужен одноразовый
    `ALTER TABLE family MODIFY name VARCHAR(64) NOT NULL COLLATE utf8mb4_general_ci;`
    (см. `Sql/schema_all.sql`). Legacy-названия с не-латиницей продолжают жить —
    правило применяется на СОЗДАНИИ.
- **Лимит** — 20 участников (`MAX_MEMBERS`): большая RP-семья, но не вторая фракция.

### Уход владельца, роспуск, исключение

- **«Покинуть семью» для ЛИДЕРА** (`/family` → пункт 5) — это ПОЛНЫЙ РОСПУСК
  семьи, а не передача власти. UI-текст подтверждения прямо предупреждает:
  «Вы лидер — семья «{название}» будет РАСПУЩЕНА полностью». Действие вызывает
  тот же `disbandFamily`, что и прежний отдельный пункт «Распустить семью» (пункт
  теперь объединён с выходом — см. «Команды» ниже).
- **«Покинуть семью» для РЯДОВОГО члена** — простое исключение из состава
  (`leaveFamily`), семья продолжает жить.
- **НАСЛЕДОВАНИЕ ВЛАДЕНИЯ УБРАНО.** Раньше выход владельца передавал власть
  старейшему из оставшихся; эта ветка UI-недостижима (владелец либо распускает,
  либо остаётся). `FamilyService::leaveFamily` соответственно упрощён: он больше
  НЕ меняет `owner_account_id` — это только выход РЯДОВОГО члена (роспуск
  последнего члена внутри `leaveFamily` сохранён как страховка на случай прямого
  вызова, UI туда владельца не приводит).
- **Исключение** (подменю «Члены семьи» → игрок → «Исключить», только лидер) —
  `FamilyService::kickMember(ownerPlayerId, targetAccountId)` исключает
  произвольного члена (в т.ч. ОФФЛАЙН — он есть в списке членов).
  Отказы: `NotOwner` (не владелец), `NotFound` (у вызывающего нет своей семьи),
  `TargetNotFound` (аккаунт не среди членов), `CannotKickSelf` (targetAccountId —
  сам владелец: для этого случая есть «Покинуть семью»). При успехе — DELETE
  строки члена (write-through), немедленная чистка онлайн-слота цели (если она
  сейчас в сети — членство/чат `/f`/гейты семейных машин закрываются мгновенно, не
  дожидаясь следующего действия цели).

**Припаркованные машины при уходе/роспуске/исключении.** Вокруг
`leaveFamily`/`disbandFamily`/`kickMember` FamilySystem снимает ШЕРИНГ
(`ParkedVehicleService`, см. `Docs/ParkedVehicles.md`): роспуск/уход последнего
члена → `onFamilyDissolved(familyId)` (все машины семьи); выход рядового члена
или исключение → `onOwnerLeftFamily(accountId)` цели (только ЕЁ расшаренные — цель
могла быть владельцем машин, даже не будучи владельцем семьи). В обоих случаях
машины ОСТАЮТСЯ припаркованы ЛИЧНО у дома (`UPDATE family_id -> NO_FAMILY`,
экземпляры не уничтожаются). `familyId`/`accountId` захватываются ДО вызова
(после — слоты обнулены). ИНВАРИАНТ: `leave`/`disband`/`kickMember` зовутся только
из этих UI-путей — иные пути осиротят `parked_vehicle` семейной ссылкой.

## Команды

- **`/family`** — одна команда, открывает меню по состоянию игрока (диалог-список):
  - **не в семье**: единственный пункт «Создать семью» (ввод названия). Гейта по
    дому НЕТ — submit сразу идёт в `createFamily` (сессия/имя/уникальность
    валидируются сервисом). Успех — чат-сообщение с деталями (`Семья «{}» создана.
    Вы — лидер. Чат семьи — команда /f`) + праздничный ПОПАП `congratulations!`
    (`ScreenNoticeService`, зелёный `0x90EE90`, 5с; тексты попапов — английские,
    как `engine is broken`/`no fuel`);
  - **в семье** — 5 пунктов, ВСЕ видны ВСЕГДА любому члену (правило видимости —
    недоступность объясняет обработчик сообщением при клике, не скрытием пункта):
    1. **«Информация»** — TABLIST_HEADERS «Поле | Значение»: Название, Владелец
       (онлайн — «Имя[id]» актуальным ником, иначе снимок из состава), Членов
       («{n}/{MAX_MEMBERS}»), Создана (`d.m.Y` из `created_at`).
    2. **«Члены семьи»** — TABLIST_HEADERS «Игрок | Статус», ИНТЕРАКТИВНЫЙ: выбор
       строки открывает ПОДМЕНЮ члена. `listItem` резолвится по СНИМКУ порядка
       accountId, захваченному на показе (онлайн-сортировка могла перетасовать
       список под висящим диалогом — живой индекс указал бы не на того).
       Сортировка: сначала ОНЛАЙН, потом оффлайн (стабильный
       partition поверх состава, уже отсортированного по `joined_at` — внутри
       каждой группы стаж сохраняется). Онлайн — актуальный ник (`getName()`,
       игрок мог переименоваться) + зелёный `{90EE90}онлайн`; оффлайн — снимок
       `Mem::name` (оборонительно через `neutralizeColorCodes` — legacy-строкам БД
       инвариант латиницы не гарантирован) + красный `{FF5A5A}оффлайн`. Владелец
       помечен `(лидер)`, сам игрок — `(вы)`; лидер, смотрящий на себя, —
       одним суффиксом `(вы, лидер)`.
       **Подменю члена** (LIST, заголовок — имя): «Информация» / «Исключить»,
       оба видны всем (правило видимости). «Информация» — карточка «Поле |
       Значение»: Игрок, Статус (цветом), «В семье с {дата}» (`joined_at`);
       расширяемая. «Исключить» — гейты на клике (только лидер; не себя), дальше
       MSGBOX-флоу кика (`showKickConfirm`, снимок `targetAccount`) — это
       ЕДИНСТВЕННЫЙ путь исключения (корневого пункта нет). Членство цели
       ре-валидируется на каждом клике подменю («Этот игрок больше не в семье»).
    3. **«Транспорт семьи»** — TABLIST_HEADERS в ТОМ ЖЕ формате, что `/car` →
       «Мои машины» (общий builder `ParkedVehicleRow::build`, см.
       `Docs/CarMenu.md`/`Docs/ParkedVehicles.md`), READ-ONLY. Источник —
       `ParkedVehicleService::parkedOfFamily(familyId)`. Пустой список — сообщение
       в чат, в диалог не заходим. «Забрать» доступа семьи здесь БОЛЬШЕ НЕТ — это
       делает ТОЛЬКО владелец машины через `/car` → «Вернуть от семьи».
    4. **«Пригласить в семью»** (только лидер) — INPUT ПО ID (как передача дома в
       `/home`): тело подсказывает «посмотреть можно по TAB» и условия цели.
       Мусор/вне `[0, MAX_PLAYERS)` — «Введите корректный id игрока» (ошибка
       ВВОДА); слот пуст — «Такого игрока нет в сети». Найден — тот же флоу
       приглашения, что раньше (гейт лидера, лимит, цель не в семье,
       `showInviteConfirm` с serial-guard приглашающего).
    5. **«Покинуть семью»** — семантика ЗАВИСИТ от роли: рядовой — простой выход
       (как раньше); ЛИДЕР — ПОЛНЫЙ РОСПУСК (см. «Уход владельца, роспуск,
       исключение» выше). Отдельного пункта «Распустить семью» больше нет — он
       слился с этим для лидера.

  **Исключение члена** — ЕДИНСТВЕННЫЙ путь: «Члены семьи» → выбор игрока →
  подменю → «Исключить» (работает и для ОФФЛАЙН-члена — он есть в списке).
  Отдельного корневого пункта «Выгнать из семьи» (по нику) НЕТ — убран как
  избыточный дубль подменю. Гейты на клике: только лидер («Это может только
  лидер семьи»), не себя («Себя выгнать нельзя — используйте «Покинуть семью»»);
  отказ по гонке (цель уже вне семьи на момент действия) — «Этот игрок больше
  не в семье» (`Result::TargetNotFound`). Подтверждение MSGBOX со снимком
  `targetAccountId` (паттерн `/home` `expectedAccount`), действие —
  `FamilyService::kickMember`.

  Меню строится ДИНАМИЧЕСКИ (вектор действий), диспетчеризация по выбранному
  действию, не по магическим индексам. Каждый колбэк пересобирает доступные
  действия и сверяет выбор — состояние могло измениться, пока диалог открыт
  (например семью успели распустить, пока висел диалог другого пункта).
- **`/f [текст]`** — чат семьи: рассылка всем ОНЛАЙН-членам своей семьи. Формат
  строки: `[{название}] {ник}[{id}] : {текст}`. Цвет — обычный белый
  (`Colour::White()`), без спец-окраски; системные уведомления членам
  (вступил/вышел/роспуск) — стандартным `INFO_COLOUR`. Текст санитизируется (`cp1251→utf8`,
  `sanitizeUserText(180)`, затем `neutralizeColorCodes` — цветокоды `{` `}` `~`
  раскрашивает КЛИЕНТ при рендере, иначе игрок подделает цвет строки); пустой —
  молча игнор. В `PlayerChatService::tryChat` (общий мут/антиспам, ДО рассылки)
  уходит тот же санитизированный текст, что и в рассылку (как `ChatSystem`).

## Персист (write-through)

Все операции пишут в БД сразу, без снапшота на конце сессии (как членство
фракций — нечего откладывать):

- `createFamily` — INSERT в `family` + первая строка `family_member` (владелец),
  одной транзакцией.
- `joinFamily` — INSERT строки `family_member`.
- `leaveFamily` — DELETE строки уходящего РЯДОВОГО члена (наследование убрано —
  `owner_account_id` больше НЕ трогается этой операцией).
- `kickMember` — DELETE строки исключённого члена (тот же запрос, что
  `leaveFamily`, инициатор другой — владелец, не сам член).
- **Оба DELETE квалифицированы `account_id AND family_id`** (не только аккаунтом):
  async-запросы уходят в общий воркер-пул БЕЗ гарантии порядка, и «вышел/кикнут →
  тут же вступил в другую семью» с фильтром только по `account_id` мог бы стереть
  строку уже НОВОЙ семьи, если DELETE исполнится после INSERT.
- `disbandFamily` — DELETE всех `family_member` семьи + DELETE строки `family`,
  одной транзакцией.

Ошибки БД уходят в `errorCallback` (логируются, сервер не падает); транзакции
откатываются (`rollback`) при сбое посередине.

### Загрузка на старте

`FamilySystem::initialize` грузит ВСЕ семьи, затем всех членов (двумя
`selectQuery`, члены строго после семей). `finalizeLoad`: снимает семьи без
членов (битые строки), сортирует состав по `joined_at`, чинит владельца на
старейшего, если его строка членства пропала, выставляет `m_nextId = max(id)+1`,
строит индекс `account → family` и ТОЛЬКО в самом конце поднимает флаг
`m_loaded`. Загрузка асинхронна, поэтому колбэк дорезолвит членство уже
подключившимся игрокам.

`m_loaded` — гард от гонки/сбоя загрузки: пока он `false` (до `finalizeLoad` или
если любой из `selectQuery` ушёл в error-колбэк) `createFamily`/`joinFamily`
ОТКАЗЫВАЮТ с `Result::NotLoaded` («Семьи ещё загружаются, попробуйте через
момент»). До выставления `m_nextId` по `max(id)` из БД новый id конфликтовал бы с
ещё не загруженными строками (рассинхрон память↔БД); при сбое загрузки фича
просто неактивна до рестарта, без порчи данных. `errorCallback` обоих
`selectQuery` логирует и оставляет `m_loaded = false`. Фикс владельца битой строки
в `finalizeLoad` (`throwQuery`) тоже логирует через `errorCallback`.

`finalizeLoad` в самом конце оповещает **one-shot подписчиков** `subscribeLoaded`
(аналог `HouseService::subscribeOwnershipLoaded`; поздняя подписка после загрузки —
колбэк сразу). Через него `ParkedVehicleSystem` грузит `parked_vehicle` СТРОГО после
семей (они нужны для гейта РАСШАРЕННЫХ; обе загрузки async, порядком регистрации
гарантию не дать) — см. `Docs/ParkedVehicles.md`.

### Онлайн-членство

`onSessionStart(playerId, accountId)` ставит онлайн-слот игрока из индекса по
аккаунту; `onSessionEnd` чистит слот. Серверная правда о семье остаётся в
`m_families`/БД, когда члены оффлайн. id семьи генерирует сервер (единственный
писатель): без AUTO_INCREMENT, INSERT с явным id.

## Применение SQL

`Sql/families.sql` (`CREATE TABLE IF NOT EXISTS family`, `family_member`,
utf8mb4; столбец `family.name` — коллация `utf8mb4_bin` под in-memory проверку
уникальности) применяется ВРУЧНУЮ к схеме БД до запуска — механизма автомиграций
нет (как все `.sql`, см. `factions.sql`).

## Константы баланса

| Константа     | Значение | Смысл                                          |
|---------------|----------|------------------------------------------------|
| `MAX_MEMBERS` | 20       | лимит участников (соц-группа, не вторая фракция)|
| `NAME_MIN`    | 3        | мин. длина названия (символов utf-8)           |
| `NAME_MAX`    | 24       | макс. длина (тег в `/f` не раздувает строку)    |
| создание      | бесплатно| нет «налога на дружбу», нулевое давление на экономику |
| гейт создания | свой дом | основатель должен владеть домом (`ownsHouse`)   |

**Баланс гейта (временный RP-порог, на заметку при расстановке домов).** Гейт «нужен
дом» сейчас почти бесплатен и тривиально обходится: любой занимает первый зелёный
дом за секунды только ради разблокировки семьи. Это ослабляет дома как ценность —
на старте их разберут «под семью», а не под жильё. Приемлемо как временный порог,
но на будущее заложить либо ЦЕНУ занятия (когда появится сток денег), либо
ощутимый ПЕРЕВЕС числа домов над числом активных игроков — иначе «один дом на
игрока» + гейт создадут дефицит = «налог на новичка, пришедшего позже». Дома ставит
дев вручную (`/house`), чисел для оценки дефицита в коде нет — отметить при
расстановке.

## Три правила

- **Читер-абуз:** членство и владелец — серверная правда (`m_families`,
  `m_playerAccount`); пригласить может ТОЛЬКО владелец, согласие приглашённого
  перепроверяет состояние на момент клика (семья есть, не переполнена, цель не в
  семье, приглашавший — всё ещё владелец ЭТОЙ семьи и та же его сессия по
  `serial`); нельзя вступить будучи в семье / в переполненную / в несуществующую
  / пригласить себя; id игрока из ввода — bounds + онлайн + авторизация; и имя, и
  текст `/f` санитизированы от инъекции цветокодов (`{` `}` `~` обезвреживаются —
  их парсит клиент) и контролов; `/f` через `tryChat` (тем же санитизированным
  текстом). Создание — уникальность имени проверяется синхронно по всем семьям в
  памяти (ASCII-регистронезависимо; БД-UNIQUE в `utf8mb4_bin` совпадает).
  `create`/`join` отказывают (`Result::NotLoaded`), пока загрузка не завершена —
  id не выдаётся до синхронизации `m_nextId` с БД. **Гейта по дому нет** (создание
  свободное — см. «Устройство»). **Ники — клиентский ввод, не право:** и
  приглашение, и исключение резолвят НИК только В accountId/playerId (точное
  сравнение с `player.getName()`/`Mem::name`); дальше вся авторизация — по
  accountId/serial, нику не доверяется ничего сверх поиска цели. **Kick:**
  доступен ТОЛЬКО владельцу (`isOwner` по аккаунту слота, не по клиенту), MSGBOX
  захватывает `targetAccountId` (не ник — переименование/перелогин цели между
  показом и подтверждением не уводит исключение не туда), нельзя выгнать
  владельца (`CannotKickSelf`), онлайн-слот цели чистится СИНХРОННО внутри
  `kickMember` — чат `/f` и гейты семейных машин закрываются для неё немедленно,
  без окна гонки.
- **Краш/UB:** bounds-guard `playerId` во всех геттерах и слотах; null-гарды
  (`getFamily`, `getPlayers().get`); async-колбэки БД и диалогов заново берут
  живого игрока и сверяют сессию; ошибки БД — через `errorCallback`; `m_nextId`
  и мапы (`m_families`/`m_accountFamily`/`m_playerFamily`) держатся
  консистентными; роспуск снимает онлайн-слоты всех членов до удаления семьи;
  ре-валидация владения/членства на КАЖДОМ клике каждого пункта меню и подменю —
  диалог мог висеть, пока состояние менялось из другого окна (кик самого
  кликающего, роспуск, исключение цели третьим лицом).
- **Перф:** рассылка `/f` — один проход по онлайн-игрокам O(online), без
  per-tick работы; меню/создание/вступление/kick/роспуск — холодный путь
  (команда/диалог); резолв цели приглашения — O(1) по id; выбор члена — по снимку порядка списка
  или по составу семьи (kick, ≤`MAX_MEMBERS`=20) — оба холодные и малы; загрузка
  всех семей — только на старте.
