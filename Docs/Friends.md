# Друзья (`/friend`, `/friendaccept`, `/friendcancel`)

Бизнес-фича (НЕ Core). Код:
- `Src/Services/FriendService` — списки друзей игроков онлайн и заявки в друзья.
- `Src/Systems/FriendSystem` — привод: команды, диалоги, БД, оповещение о входе.

Схема БД: `player_friend` + колонка `player.last_seen` в `Sql/schema_all.sql`.

## Что даёт дружба

Сейчас — **видеть, когда друг заходит в игру**: на старте его сессии всем друзьям
онлайн уходит голубое сообщение

```
Ваш друг Lo_Vlasud[22] зашёл в игру
```

Дружба **взаимная**: односторонней «подписки» нет, и оповещение получают ровно те, кто у
вошедшего в списке.

## Меню `/friend`

```
/friend ──► Мои друзья / Добавить в друзья
```

### Мои друзья

```
Ivan_Petrov[7] онлайн
Anna_Smirnova оффлайн 31.07.2026 23:15
Old_Player оффлайн (ни разу не выходил)
```

Онлайн-друг показан с **id** — его можно сразу набрать в другой команде; у оффлайн-друга
id нет вовсе (он бессмысленен), вместо него — когда игрок последний раз был в сети.

Выбор друга открывает действия: сейчас там один пункт — **«Удалить из друзей»**.

Список читается **свежим запросом в БД на каждое открытие диалога**, а не из кэша.
Иначе `last_seen` у друга, вышедшего уже после нашего входа, застыл бы на снимке времени
нашей загрузки и показывал бы заведомо старую дату.

Удаление снимает **обе** строки одним `DELETE` и чинит кэш второй стороны, если она
онлайн, — иначе до её перезахода дружба считалась бы живой и она получала бы оповещения.
Удалённому НЕ сообщается, что его удалили.

### Добавить в друзья

Диалог просит **id игрока в сети** (числовой ввод — через `showNumberInput`, см.
`Docs/PlayerMenu.md`: мусор и overflow сервис отсекает сам). Адресату уходит

```
Lo_Vlasud[22] хочет добавить вас в друзья. Принять заявку? /friendaccept 22 /friendcancel 22
```

`/friendaccept` подсвечена зелёным, `/friendcancel` — оранжевым. **id отправителя
подставлен прямо в команды**: заявок может висеть несколько, и игроку остаётся повторить
готовую строку, а не искать, чей это был id. Цветокоды в строке **наши**, а ник
отправителя подставляется уже обезвреженным (`Encoding::neutralizeColorCodes`) —
подделать ими текст нельзя.

Отказы на отправке: себе, уже в друзьях, адресата нет в сети, у любой стороны упёрлись в
`MAX_FRIENDS`, своя заявка этому игроку уже висит, у адресата упёрлись в
`MAX_PENDING_REQUESTS`.

## Заявки

Заявки живут **только в памяти** (как звонок в телефоне) и хранятся **списком у
адресата**. Отвечают на них по **id отправителя**: `/friendaccept 22`, `/friendcancel 22`.

**Почему по id, а не «одна заявка на игрока».** Одиночный слот делал заявку дефицитом:
недоброжелателю хватало слать заявку раз в минуту, чтобы никто другой не смог добавить
человека в друзья. Список плюс адресация по id убирают и дефицит, и двусмысленность
«чью заявку я сейчас принял».

- **Повторная заявка от того же отправителя не ставится** — она и так висит.
- **`MAX_PENDING_REQUESTS` = 10** входящих на игрока. Список конечен, но одна заявка
  чужую больше не вытесняет. При добавлении новой протухшие подчищаются на месте, чтобы
  потолок не забивался мёртвыми записями раньше, чем до них дойдёт тик.
- **`REQUEST_TTL` = 60 с.** Протухшие снимает общий тик 1 Гц (`expireRequests`), обе
  стороны узнают об этом. Тик, как и у телефона, никогда не отменяется, в том числе из
  своего колбэка; список мутируется ДО уведомлений, а не во время обхода.
- **Приём сверяет серию сессии отправителя**: пока заявка висела, он мог выйти, а слот
  `playerId` — достаться другому игроку.
- Конец сессии снимает и входящие заявки игрока, и заявки, которые **он отправил** другим:
  иначе на его заявку ответил бы новый владелец слота, и адресат подружился бы с
  посторонним.
- Ответ на несуществующий id отвечает отказом и, если что-то ждёт ответа, подсказывает
  сколько именно заявок висит.

## «Последний раз в сети»

Колонка `player.last_seen` пишется в **save-канале** сессии
(`PlayerSessionService::subscribeSave`): он срабатывает и на конце сессии, и на
периодическом автосейве, поэтому после краша сервера отметка отстаёт максимум на интервал
автосейва, а не теряется целиком. Запись идёт через `throwQueryOrdered` с ключом
`player:<accountId>` — отметка не должна обгонять другие записи этой же строки.

Писателем колонки владеет фича друзей, потому что она единственный её потребитель. Если
last-seen понадобится ещё кому-то, писателя стоит вынести в общий аккаунт-персист.

## Балансовые константы

| Константа | Значение | Смысл |
|---|---|---|
| `FriendService::MAX_FRIENDS` | 50 | потолок списка: диалог остаётся читаемым, строки в БД не растут без предела |
| `FriendService::REQUEST_TTL` | 60 с | сколько живёт неотвеченная заявка |
| `FriendService::MAX_PENDING_REQUESTS` | 10 | потолок ВХОДЯЩИХ заявок на игрока |

Потолок соблюдается и **на загрузке** из БД: если константу когда-нибудь уменьшат, старые
списки просто подрежутся, а не сломают диалог.

## Миграция БД (выполняет ПОЛЬЗОВАТЕЛЬ)

```sql
ALTER TABLE `player` ADD COLUMN `last_seen` DATETIME NULL DEFAULT NULL;

CREATE TABLE IF NOT EXISTS `player_friend` (
    `account_id` BIGINT   NOT NULL,
    `friend_id`  BIGINT   NOT NULL,
    `since`      DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (`account_id`, `friend_id`),
    CONSTRAINT `fk_friend_account` FOREIGN KEY (`account_id`) REFERENCES `player` (`id`) ON DELETE CASCADE,
    CONSTRAINT `fk_friend_friend` FOREIGN KEY (`friend_id`) REFERENCES `player` (`id`) ON DELETE CASCADE
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4;
```

Дружба хранится **двумя строками** (`a->b` и `b->a`). Так список друзей аккаунта — обычный
`SELECT` по `account_id` без `OR`/`UNION`, а удаление снимает обе строки одним `DELETE`.
Внешние ключи с каскадом: удалённый аккаунт не оставляет висячих дружб.

## Три правила

- **Читер-абуз:** заявку можно отправить только игроку ОНЛАЙН, повторную тому же —
  нельзя, а список входящих ограничен `MAX_PENDING_REQUESTS`; заблокировать человека от
  чужих заявок, заняв единственный слот, невозможно — адресация идёт по id отправителя.
  Протухание чистит список через минуту. Приём сверяет серию
  сессии отправителя, конец сессии снимает и свои, и отправленные заявки — подружиться с
  посторонним через переиспользованный `playerId` нельзя. `MAX_FRIENDS` проверяется у
  ОБЕИХ сторон и на приёме, а не только на отправке. Индекс строки в списке приходит от
  клиента и сверяется с ЖИВЫМ списком. Ники игроков всюду проходят
  `neutralizeColorCodes` — цветовой инъекции в чужой чат нет. Дружба пишется двумя
  строками одним `INSERT IGNORE`, односторонней не остаётся.
- **Краш-безопасность:** все входы сервиса bounds-safe по `playerId`; `IPlayer*` в
  колбэках диалогов, таймера и async-запросов берётся заново из пула и проверяется;
  async-колбэки — под serial-guard; `expireRequests` снимает заявку ДО вызова наблюдателя;
  ввод id проходит через `showNumberInput` и проверяется по диапазону `0..MAX_PLAYERS` до
  сужения к `int`; ошибки БД идут в лог и не роняют вход.
- **Перф:** всё событийно — команда, диалог, старт/конец сессии. Тик заявок 1 Гц.
  Списки короткие (потолок 50), поиск по ним линейный на холодном пути. БД: один SELECT на
  вход, один на открытие списка, по одному короткому запросу на приём и удаление.
