# Дома

Player houses — зачаток петли собственности (бизнес-фича, не Core). Код:
`Src/Services/HouseService`, `Src/Systems/HouseSystem`.

**Два разных источника правды:**

- **ОПИСАНИЕ дома** (статический контент, ставит дев) — JSON-файл `houses.json`
  рядом с сервером (рабочая директория): id, интерьер, вход/выход, угол, vw.
- **ВЛАДЕНИЕ** (`house → аккаунт`) — динамические данные АККАУНТА: в БД (таблица
  `house_owner`, write-through как членство фракций `faction_member`). В
  `houses.json` НЕ хранится.
- **СТАВКИ на ничейный дом** — в БД (`auction_lot` / `auction_bid` /
  `auction_player`), общие для всех аукционов таблицы (см. `Docs/Auction.md`).
  Правило проекта: вся динамика — в БД, json правится только дев-командами.

Дом — это пикап ВХОДА в позиции создателя плюс интерьер из каталога готовых
интерьеров; внутри интерьера — пикап ВЫХОДА. Первый игроцкий шаг к собственности
— **покупка по госцене**: наступив на пикап ничейного (зелёного) дома, игрок видит
предложение купить его за `House.price` — сумму, которую задал дев при создании.
Согласился и хватило денег — дом сразу его: иконка краснеет (31→32), владение
пишется в БД (`house_owner`) и переживает рестарт. Контроль доступа (замки, чужой
дом не пускает) — будущее: сейчас любой занятый дом пускает внутрь молча.

**Бесплатного занятия нет, торгов за госимущество — тоже.** Дом продаёт
государство по фиксированной цене. Аукцион остаётся отдельной системой и в будущем
даст игрокам выставлять СВОЁ имущество на продажу; торговля госимуществом через
него прекращена (см. «Аукцион» ниже).

## Устройство

- **Дом = вход + интерьер + выход.** Создаётся дев-тулзой `/house` в текущей
  позиции игрока. Вход (пикап-домик) стоит на позиции создателя в основном мире
  (vw 0). Наступание на пикап входа НИЧЕЙНОГО дома открывает окно торгов;
  ЗАНЯТОГО — телепортирует в интерьер. Наступание на пикап выхода внутри — обратно
  на точку выхода.
- **Владелец — АККАУНТ.** `House.owner` хранит КЛЮЧ аккаунта
  (`std::to_string(accountId)`); `""` — ничейный (зелёный). Это лишь **in-memory
  зеркало БД** (`house_owner`), а НЕ значение из `houses.json`: наполняется из БД
  на старте (`loadOwnershipAsync` после разбора описаний — безусловно, на всех
  ветках) и на итоге аукциона. `setOwner`
  меняет только память — запись владения в БД делает `HouseSystem`. Ключ строится
  одинаково и в торгах (`AuctionSystem`), и в гейте семьи (`FamilySystem`) —
  `std::to_string(accountId)` из `PlayerSessionService`. `HouseService` остаётся на
  строках (не связан с типом `AccountId`).
- **id дома — порядковый номер создания.** Генерирует сервер (единственный
  писатель): `m_nextId = max(id)+1` на загрузке. В файле id — порядковый;
  дубликат при загрузке отбрасывается.
- **Лимит парковки `House.parkingCap`** — дев-контент дома (как интерьер): макс.
  число ПРИПАРКОВАННЫХ у дома машин владельца. Задаётся при создании (шаг ввода в
  `/house`), клампится в `[MIN_PARKING_CAP, MAX_PARKING_CAP]` = `[1, 10]`.
  `DEFAULT_PARKING_CAP` (1) — для старых `houses.json` без поля и как фолбэк парса.
  Считаются ВСЕ припаркованные записи владельца (личные + расшаренные им семье —
  все у его дома по модели «один дом, радиус 30 м»). Enforce — в `CarMenuSystem::parkHere`
  (см. `Docs/CarMenu.md`, `Docs/ParkedVehicles.md`). Кап живёт ТОЛЬКО в `houses.json`
  (не в БД, миграций нет).
- **Точка выхода — за спиной создателя.** Считается от позиции входа на
  `EXIT_DISTANCE` (1.10 м) В СТОРОНУ СПИНЫ по углу поворота создателя в момент
  создания (`HouseService::backOf`, SA-MP конвенция «вперёд» = `(-sin a, cos a)`,
  значит «назад» = `(sin a, -cos a)`, угол из `getRotation().ToEuler().z`).
  **Направление выхода пользователь проверяет в игре** — сообщение «выход — за
  спиной» при создании подсказывает, куда смотреть.
- **Каталог интерьеров** (`HouseService::catalog()`, фиксированная таблица) —
  имя в дев-меню + SA `interior id` + фикс. точка спавна внутри и угол. Координаты
  входа — канонические SA-MP. 6 пунктов:

  | Индекс | Название           | interior id | Назначение                       |
  |--------|--------------------|-------------|----------------------------------|
  | 0      | Мотель (комната)   | 10          | мелкая комната, временное жильё  |
  | 1      | Малая квартира     | 1           | дешёвая однушка, старт игрока     |
  | 2      | Средний дом        | 5           | средний жилой, семейное жильё     |
  | 3      | Особняк            | 5           | крупный богатый, статусное жильё  |
  | 4      | Склад              | 1           | индустриальное, криминал/бизнес   |
  | 5      | Офис               | 3           | деловой, штаб фракции, кабинет    |

  Несколько пунктов делят один SA `interior id` (5 — особняк/средний дом, 1 —
  квартира/склад): это один игровой интерьер с РАЗНЫМИ точками спавна — допустимо.
  **Достижимость пикапа выхода** (точка спавна + `EXIT_PICKUP_OFFSET` по X) для
  каждого интерьера каталога пользователь проверяет в игре: смещение по X может
  упереть пикап в стену/мебель в тесном интерьере — тогда подобрать выход нельзя.
- **vw на дом уникальный** — `VW_BASE + id` (`VW_BASE = 2000000`), чтобы интерьеры
  разных домов не пересекались. Снаружи (вход/выход/иконка) — основной мир (vw 0).
  Диапазон `[VW_BASE .. VW_BASE + MAX_HOUSE_ID]` (т.е. `[2000000 .. 3000000]`)
  зарезервирован под дома; при будущей игровой покупке стоит заложить осознанный
  потолок id/vw, чтобы он не пересёкся с vw других будущих систем (интерьеры
  бизнесов, инстансы).
- **Лимит домов `MAX_HOUSE_ID` (1000000).** Потолок id дома: `VW_BASE + MAX_HOUSE_ID`
  заведомо < `INT_MAX`, vw не переполняет int. `createHouse` отказывает на потолке
  (сообщение «достигнут лимит домов»); `finalizeLoad` зажимает `m_nextId` ≤
  `MAX_HOUSE_ID+1`; при загрузке `parse` пропускает записи с `id` вне `(0, MAX_HOUSE_ID]`.
  Поле `virtualWorld` из файла НЕ доверяется — vw ВСЕГДА пересчитывается
  (`VW_BASE + id`), даже если в файле есть значение (оно лишь для читаемости).
- **Удаление дома с игроками внутри.** При удалении (`/house` → удалить) перед
  снятием пикапа выхода все онлайн-игроки с `vw == house.virtualWorld`
  телепортируются на точку выхода (vw 0) через `PlayerLocationService` — иначе они
  остались бы заперты в интерьере без пикапа выхода.
- **3D-текст у входа** — игроцкий ориентир дома (первый постоянный игроцкий
  маркер дома помимо радар-иконки), виден всем у двери. Создаётся в `spawnHouse`
  через `TextLabelService::add` на позиции входа (vw 0), снимается в `despawnHouse`.
  Хэндл лейбла трекается в `Runtime::label` наравне с пикапами/иконкой
  (пересоздаётся на загрузке/создании, снимается при удалении — нет утечки/двойного
  remove). Лейбл — данные сервер→клиент (сервис санитизирует текст), клиентского
  ввода нет.

## Иконка на карте

Глобальная (стримится по близости, радиус **150 м** — иконка видна только вблизи
дома, не засоряет радар издалека), одна на дом у точки входа (vw 0), стиль
`MapIconStyle_Global` (стрим-радиус передаётся в `addGlobal`). Тип иконки кодирует состояние: ничейный — **31** (зелёный
домик), занятый — **32** (красный домик). Это именные домовые спрайты SA с
фиксированным цветом — переданный `Colour` они игнорируют, цвет задаёт сам тип
иконки.

**Перекраска** (`refreshHouseIcon`). У глобальных иконок НЕТ update — только
`removeGlobal`+`addGlobal`. При смене владельца (и при применении владения из БД на старте)
старая иконка снимается, заводится новая по актуальному `owner` (31→32), хэндл в
`Runtime::mapIcon` обновляется (нет утечки/двойного remove). На старте все дома
спавнятся ничейными (`spawnHouse` по `owner.empty()` — иконки зелёные), а
`loadOwnershipAsync` ПОСЛЕ спавна применяет владение из БД и перекрашивает занятые
в красные. То есть владение из БД догоняет уже заспавненные дома. Загрузка владения
вызывается БЕЗУСЛОВНО на всех ветках разбора описаний (пусто / битый файл / успех),
а не только на успешном — иначе на пустом/битом `houses.json` владение не подтянулось
бы вовсе и флаг загрузки не встал бы.

## Покупка ничейного дома (игроцкое взаимодействие)

Единственное игроцкое взаимодействие с домом помимо входа/выхода. Наступив на
пикап ВХОДА ничейного дома, игрок получает предложение купить его по госцене.

| Что | Значение |
|---|---|
| Цена | `House.price`, задаёт дев; `0` — дом НЕ продаётся |
| Что видит игрок | «Дом #4», тип интерьера, лимит парковки, цена |
| Кому можно продать | у кого ещё нет дома (`ownsHouse`) |
| Когда покупка доступна | владение легло в память (`isOwnershipLoaded`) |
| Что происходит | списание денег → `setOwner` → `house_owner` + перекраска иконки |

Порядок в `buyHouse` важен и весь авторитетный — диалог мог провисеть сколько
угодно: аккаунт → **гейт `isOwnershipLoaded`** → дом существует → всё ещё ничей →
цена не 0 → у покупателя нет дома → **списать деньги** → `setOwner`. Если `setOwner`
не прошёл (дом исчез между проверкой и выдачей), деньги возвращаются немедленно.

**Гейт `isOwnershipLoaded` — не формальность.** Пока зеркало `house_owner` не
пришло из БД, `ownsHouse` отвечает «дома нет» ВСЕМ, и правило «один дом в одни
руки» проверять нечем. Хуже: персист владения делает `DELETE … WHERE house_id=… OR
account_id=…`, поэтому покупка вторым домом стёрла бы строку НАСТОЯЩЕГО дома
покупателя. Раньше этот путь гейтился через `ready()` аукциона; у прямой покупки
гейт свой.

### Аукцион

Категория `house` в `AuctionService` остаётся **зарегистрированной, но лотов не
даёт**: `describeLot` всегда возвращает `false`. Две причины:

1. лоты, уцелевшие с прежней схемы (в БД лежат уже списанные у игроков деньги), на
   своём сроке увидят «лота нет» и **вернут ВСЕ ставки** вместо того, чтобы выдать
   дом мимо новой модели. Если бы категорию сняли совсем, `resolveDue` пропускал бы
   её и деньги остались бы заперты навсегда;
2. будущая продажа имущества между игроками переиспользует этот же ключ категории.

Покупка дома дополнительно зовёт `closeLot` — если по этому дому оставались старые
ставки, они возвращаются сразу, а не ждут срока. На чистой базе это no-op.

Владение выставляет `setOwner` (оптимистичная память), а персист в `house_owner` и
перекраску иконки (зелёная→красная) доводит ЕДИНАЯ точка
`HouseSystem::onOwnerChanged` (подписка на `HouseService::subscribeOwnerChanged`,
общая для аукциона/передачи/выселения — см. «Передача и выселение» ниже): `DELETE
WHERE house_id=… OR account_id=…` + `INSERT` в ОДНОЙ ТРАНЗАКЦИИ внутри
`throwQuery` (`startTransaction` → execute → `commit`, при исключении —
`rollback` + проброс) — либо вся пара применилась, либо ничего. При сбое записи
`errorCallback` (главный поток) **откатывает оптимистичную память** через
`setOwnerSilent` (БЕЗ повторной нотификации — не зациклить откаты при затяжном
сбое БД) + повторная перекраска иконки (красная→зелёная). `houses.json` при смене
владельца НЕ переписывается (список домов не меняется). Вход в УЖЕ занятый дом —
молчаливый телепорт без сообщения (строка на каждый вход = спам).

**Удаление дома девом закрывает торги и возвращает все ставки** — иначе списанные
деньги сгорели бы вместе с домом.

### Государственная цена

`House.price` — дев-контент дома, как интерьер и лимит парковки. Задаётся шагом
ввода при создании (`интерьер → лимит парковки → гос. цена`) и правится потом в
подменю дома `/house` (`Гос. цена: $N (изменить)`). Отсутствует в файле или мусор
→ 0.

**`0` означает «дом не продаётся»**, а не «бесплатно»: на пикапе игрок получит
«госцена не назначена». Так дом, которому дев ещё не проставил цену (в том числе
любой дом из старого `houses.json`), не раздаётся даром. Чтобы выставить его на
продажу, достаточно задать цену в подменю — пересоздавать дом не нужно.

## Точка выхода наружу

Дом создаётся в точке дева: там встаёт пикап ВХОДА. Точка, где игрок появляется,
выходя из дома, считается один раз при создании и лежит в `House.exit`:

```
exit = Geometry::backOf(entrance, exitAngle, EXIT_DISTANCE)   // EXIT_DISTANCE = 2.0
```

То есть **два метра за спиной создателя** по его же углу. `Geometry::backOf`
держит конвенцию SA-MP (`вперёд = (-sin, cos)`, значит `назад = (+sin, -cos)`) —
локальных копий тригонометрии в вызывателях нет.

### Углы округляются до четверти оборота

`Geometry::snapToQuarterTurn` приводит любой угол к **0 / 90 / 180 / 270** (360 —
это 0, отрицательные нормализуются в `[0, 360)`, NaN/inf → 0). Применяется ко ВСЕМ
углам: поворот создателя при создании, `exitAngle` на загрузке, `insideAngle`
каталога при телепорте внутрь.

Зачем: угол приходит из клиентского поворота игрока сырым (`187.34`, `359.71`). По
такому углу точка «за спиной» уезжает с оси мира — визуально объект оказывается
смещён и повёрнут «под небольшим углом». Округление даёт ровные оси и
повторяемость: два дома, поставленные примерно одинаково, встанут одинаково.

**Пересчёт на загрузке.** `HouseService::loadHouse` заново считает `exitAngle` и
`exit` из `entrance` + округлённого угла, а не берёт `exit` из файла. Иначе дома,
созданные до этой правки, навсегда остались бы со старым углом и старой дистанцией,
а поле `exit` в `houses.json` тихо разъезжалось бы с формулой. Источник правды —
вход и угол; `exit` в файле остаётся только для читаемости.

### Разворот игрока

Точки прибытия имеют осмысленное «лицом куда», и он выставляется через
`PlayerLocationService::teleport(..., facingAngle)` — не сырым `setRotation` у
вызывателя (перемещения игрока идут одной точкой, см. контракт сервиса):

| Куда | Угол |
|---|---|
| Внутрь дома | `CatalogEntry::insideAngle` — замер интерьера |
| Наружу | `House::exitAngle + 180` — **спиной к входу** |

Про `+180`: точка выхода лежит ЗА спиной создателя, значит вход остаётся позади
вышедшего и смотреть он должен ОТ входа. Взяли бы сам `exitAngle` — игрок появлялся
бы лицом к двери, из которой только что вышел. `snapToQuarterTurn` заодно
нормализует `270 + 180 = 450` обратно в `90`.

**Камера.** После КАЖДОГО разворота зовётся `CameraService::setBehind`:
`setRotation` крутит модель, но камера остаётся смотреть прежним курсом, и игрок
оказывается вывернут относительно вида — визуально «появился боком». Камера ставится
и на входе, и на выходе.

Раньше угол не применялся вообще: игрок сохранял то направление, в котором шёл
снаружи, а поля `insideAngle`/`exitAngle` лежали мёртвыми.

**Риск ре-триггера.** Точка выхода недалеко от пикапа входа, и если она окажется
внутри радиуса срабатывания, вышедший игрок сработает вход снова. У домов это
гасит грейс `EXIT_GRACE` (1.5 c, `inEntranceGrace`) — но только один раз: стоящего
на месте игрока пикап после грейса втянет обратно. Два метра выбраны владельцем
как запас над радиусом; лечится дальнейшим увеличением `EXIT_DISTANCE`.

## 3D-текст у входа

Трёхстрочный лейбл у пикапа входа (vw 0), `TextLabelService` (стримится per-player
по близости). Тип интерьера первой строкой, номер дома второй — слово `Дом`
обязательно (голое `#7` у пикапа двусмысленно), **статус третьей**:

```
{интерьер}\nДом #{id}\n{статус}
```

| Состояние дома | Третья строка |
|---|---|
| Занят, ник владельца известен | `Владелец: Ivan_Petrov` |
| Занят, ник неизвестен | `Частная собственность` |
| Ничей, госцена > 0 | `Продаётся` |
| Ничей, госцена = 0 | `Не продаётся` |

Например: `Особняк` / `Дом #7` / `Продаётся`.

`Не продаётся` вместо `Продаётся` при нулевой цене — чтобы лейбл не звал игрока к
пикапу, который откажет («госцена не назначена»).

**Ник владельца берётся из `player.name`, отдельной колонки под него нет** — иначе
копия разъезжалась бы со сменой ника. Источники:

- на старте — `LEFT JOIN player` в запросе владения (`loadOwnershipAsync`). Именно
  LEFT: при INNER строка владения без записи в `player` (аккаунт удалили вручную)
  выпала бы из выборки, дом в памяти стал бы ничейным и его продали бы второй раз;
- в игре — из живой сессии владельца (`onlineNameOf`). И покупка, и передача дома
  возможны только ОНЛАЙН-игроку, так что на этих путях ник известен всегда.

`Частная собственность` — фолбэк, когда ник неизвестен: владелец офлайн и запись не
пришла из загрузки (например откат памяти после сбоя записи в БД). Дом при этом
верно числится занятым.

Ник — клиентский текст, а лейбл рендерит клиент, поэтому он проходит через
`Encoding::neutralizeColorCodes`: `{RRGGBB}` и `~` в нике иначе перекрасили бы
вывеску (то же правило, что для чата).

**Обновление — `TextLabelService::setText`**, живьём у всех, кто рядом: снимать и
заводить лейбл заново, как глобальную иконку (у неё нет `update`), не требуется.
Перерисовка вызывается на смене владельца (покупка/передача/выселение), на откате
памяти после сбоя БД, на приходе владения из БД и при правке госцены девом.

- **Цвет** — `Colour{90, 238, 144}` (рация-зелёный `90EE90`) в пару к зелёной
  иконке («свободно»). Не белый (выгорает на песке) и не `00FF00` (кислотный).
- **drawDistance** — `10.0f` (сервис 1..200, дефолт 30): текст виден только у самой
  двери, не засоряет горизонт при плотной застройке.
- **testLOS** — `true`: лейбл НЕ проступает сквозь стены/объекты (виден только при
  прямой видимости двери).

У входа постоянная подпись (номер дома + тип интерьера) — основной игроцкий
ориентир дома помимо радар-иконки.

## Ре-триггер входа/выхода

Появившись внутри интерьера, игрок не должен мгновенно сработать пикап выхода и
вылететь обратно; и наоборот — выйдя, не должен тут же снова втянуться входом
(точка выхода в `EXIT_DISTANCE` от пикапа входа). Страховка:

1. **Смещение пикапа выхода** на `EXIT_PICKUP_OFFSET` (2 м по X) от точки спавна
   внутри — игрок появляется не на пикапе.
2. **Грейс выхода** `EXIT_GRACE` (1.5 с): после входа `m_exitGraceFrom[id]`
   фиксирует момент; пока грейс активен, `onExitPickup` молча игнорирует подбор.
3. **Грейс входа** (симметричный, та же длительность `EXIT_GRACE`): после выхода
   `m_entranceGraceFrom[id]` фиксирует момент; пока грейс активен, `onEntrancePickup`
   молча игнорирует подбор — точка выхода стоит рядом со входным пикапом.

Оба грейса per-player (не глобальные): на лаге позиции одного игрока не затрагивают
других. Грейсы время-основанные — стейл-значение из переиспользованного слота
далеко в прошлом, ложного срабатывания не даёт (сброс на дисконнекте не нужен).
Оба массива value-init (`{}`) — без неинициализированного чтения на первом подборе.

Пикапы входа/выхода — edge-триггер `PickupService`: обработчик срабатывает РАЗОВО
при входе игрока на пикап (не повторяется, пока он стоит; повтор только после
схода и возврата). Грейсы остаются нужны для ДРУГОГО кейса — телепорт в интерьер
ставит игрока на пикап выхода (и наоборот), и это уже свежий вход на соседний
пикап; грейс гасит именно эту кросс-сработку.

## Команда `/house` (дев-тулза)

Одна команда (`DEVELOPER_LEVEL`, `HelpCategory::Hidden`), открывает диалог-меню:

- **`Дома — дев-меню`** (LIST): `Создать дом` / `Список домов` / `Выбрать дом по id`.
- **`Создать дом — интерьер`** (LIST): строки = каталог; `Создать` ведёт к вводу
  лимита парковки (не создаёт дом сразу).
- **`Лимит парковки`** (INPUT): тело `Сколько машин можно парковать у этого дома?
  Учитываются и личные машины владельца, и расшаренные им семье.\nДопустимо от 1
  до 10.`, кнопки `Создать` / `Назад` (обратно к выбору интерьера). Ввод — числовой
  (`showNumberInput`, сервис сам парсит целое; мусор/overflow → повтор показа).
  Диапазон `[MIN_PARKING_CAP, MAX_PARKING_CAP]` проверяется в колбэке: вне диапазона
  → `Лимит должен быть от 1 до 10. Попробуйте снова` + ре-показ этого же ввода (дом
  не создаётся). Валидное значение → дом создаётся в текущей серверной позиции
  игрока (entrance = `getPosition`, angle = `getRotation().z`, exit за спиной,
  уникальный vw), заводится пикап входа + иконка + пикап выхода + 3D-текст,
  сохраняется JSON, сообщается id и кап. `interiorIndex` захватывается в колбэк
  ввода; при ре-показе сохраняется.
- **`Список домов`** (LIST): строка `#{id} - {интерьер}` (порядок по id); пусто →
  сообщение `Домов пока нет`. Выбор → подменю.
- **`Выбрать дом по id`** (INPUT): тело `Введите id дома.`, кнопки `Открыть` /
  `Назад` (в главное меню). Ввод — числовой (`showNumberInput`, сервис сам парсит
  целое; мусор/overflow → повтор показа). id проверяется через `getHouse`:
  существует → то же подменю `Дом #{id} — {интерьер}`, что и из списка; иначе —
  сообщение `Дом #{id} не найден` + возврат в главное меню (диалог не зацикливаем).
- **`Дом #{id} — {интерьер}`** (LIST): первой строкой информационный `Лимит
  парковки: {cap}` (без действия — дев видит кап без чтения файла), затем
  `Телепорт ко входу` (дев прыгает КО ВХОДУ, не внутрь — чтобы сам прошёл через
  пикап и проверил вход) / `Удалить дом`.
- **`Удаление дома`** (MSGBOX): `Удалить дом #{id} ({интерьер})?\nЭто действие
  нельзя отменить.`; `Удалить` / `Назад`.

Сообщения дев-зелёным `{170,255,170}` (как прочая дев-тулза), все через `u()`:
`Дом #{id} создан (...). Лимит парковки — {cap}. Вход — на вашей позиции, выход —
за спиной`; `Дом #{id} удалён`; `Телепорт ко входу дома #{id}`; `Домов пока нет`;
`Дом #{id} не найден`; `Неверный интерьер`; `Достигнут лимит домов`;
`Лимит должен быть от 1 до 10. Попробуйте снова`.

## Передача и выселение (`/home`)

Второе и третье игроцкое взаимодействие с владением (после аукциона) — оба живут в
`HomeMenuSystem` (`/home`, полная структура меню — `Docs/HomeMenu.md`), НЕ в
`HouseSystem`. Оба идут через общий гейт занятости (ни одна из припаркованных
машин владельца не занята водителем — `ParkedVehicleService::byVehicleId` +
`VehicleService::getDriver`) и общее действие «все припаркованные машины
владельца — на парковку» (`ParkedVehicleService::unpark` по каждой записи:
уничтожает экземпляр + `DELETE parked_vehicle`, шеринг семье уходит вместе со
строкой; подробности — `Docs/ParkedVehicles.md`).

**Единая точка персиста владения (`HouseService::subscribeOwnerChanged`).**
Раньше запись `house_owner`/иконку менял только обработчик занятия дома
напрямую. Теперь `HouseService::setOwner` на КАЖДОМ успешном вызове (итог торгов,
передача, выселение) нотифицирует подписчиков `(houseId, oldKey, newKey)` —
`HouseSystem::onOwnerChanged` остаётся ЕДИНСТВЕННЫМ персистером house_owner и
единственным местом, где перекрашивается иконка:

- `newKey` непустой (итог торгов/передача) — `DELETE WHERE house_id=… OR
  account_id=…` + `INSERT` в ОДНОЙ ТРАНЗАКЦИИ (та же атомарность, что раньше
  была только у занятия дома);
- `newKey` пустой (выселение) — `DELETE WHERE house_id=…`;
- иконка перекрашивается ОПТИМИСТИЧНО сразу (до ответа БД, как было раньше);
  при сбое записи откат памяти идёт через `HouseService::setOwnerSilent`
  (БЕЗ повторной нотификации — иначе рекурсия запускала бы новую БД-попытку и
  при затяжном сбое БД зациклила бы откаты) + повторная перекраска иконки.

`HomeMenuSystem` (и любой будущий писатель владения) НЕ обращается к БД
напрямую — только `HouseService::setOwner(houseId, ownerKey)`; персист и иконку
доводит подписчик. Это не даёт логике БД расползтись по нескольким системам.

**Передача** (`HomeMenuSystem::executeTransfer`, MSGBOX-подтверждение
`Передать дом {ник}[{id}]? Все припаркованные машины отправятся на парковку.
Это действие нельзя отменить.`): ре-валидация на согласии — свой дом ещё есть,
получатель НЕ сам игрок, получатель онлайн с активной сессией, получатель ещё
НЕ владеет домом (`ownsHouse`, модель «один дом на игрока» не нарушается) →
гейт занятости → `unpark` всех припаркованных → `setOwner(houseId,
recipientKey)`. Уведомления: отправителю `Дом передан {ник}[{id}]`, получателю
`{ник}[{id}] передал вам дом — теперь это ваш дом`. Получатель идентифицируется
ТОЛЬКО серверным id/сессией — ник НЕ вводится (id набирается в INPUT, дальше всё
резолвится по `PlayerSessionService`).

**Выселение** (`HomeMenuSystem::executeEvict`, MSGBOX `Выселиться из дома? Дом
станет ничейным, припаркованные машины отправятся на парковку.`): гейт занятости
→ `unpark` всех припаркованных → `setOwner(houseId, "")` (снятие владельца, дом
снова свободен — доступен занятию любым игроком существующим путём). Сообщение
`Вы выселились. Дом снова свободен`.

Спавн-выбор «Дом» (`Docs/SetSpawn.md`) у ОБОИХ участников перерезолвится сам на
следующем спавне — `SpawnChoiceSystem` резолвит `houseOf` заново каждый раз, без
форса.

## Персист

Два независимых хранилища: ОПИСАНИЕ домов — `houses.json`, ВЛАДЕНИЕ — БД
(`house_owner`).

### Описание домов (JSON-файл)

`houses.json` в рабочей директории сервера. Хранит ТОЛЬКО статический контент
(id, интерьер, вход/выход, угол, vw) — БЕЗ владельца. После каждого создания/
удаления — запись всего набора асинхронно (`ThreadPool`, диск на воркере).
Загрузка — один раз на старте (`HouseSystem::initialize` → `loadFromFileAsync`);
файла нет — пусто (норма для первого запуска). Сериализация/разбор — через
`nlohmann/json` (не свой парсер). Рантайм-хэндлы (пикапы/иконка) в JSON НЕ
хранятся — пересоздаются из полей на загрузке (`HouseSystem::Runtime`). Дом из
файла всегда грузится ничейным; legacy-поле `owner` в старом `houses.json`
игнорируется при разборе.

#### Формат

Массив объектов домов (`HouseService::serialize()`, `dump(2)`):

```json
[
  {
    "id": 1,
    "interiorIndex": 2,
    "entrance": [2495.0, -1688.0, 13.5],
    "exit": [2496.0, -1690.0, 13.5],
    "exitAngle": 90.0,
    "virtualWorld": 2000001,
    "parkingCap": 1
  }
]
```

Поля координат — массивы из трёх чисел `[x,y,z]`. Поля `owner` в файле НЕТ —
владение живёт в БД (`house_owner`). `parkingCap` — необязательное: старый
`houses.json` без поля грузится с `DEFAULT_PARKING_CAP` (1), и на следующем
`saveToFileAsync` (любой create/delete) весь набор перезапишется уже С полем.

### Владение (БД)

Таблица `house_owner` (`Sql/house_owner.sql`, **применяется вручную** — как
`Sql/factions.sql`/`Sql/families.sql`):

| Колонка      | Тип      | Смысл                                                  |
|--------------|----------|--------------------------------------------------------|
| `house_id`   | INT (PK) | дом из `houses.json` — один владелец на дом            |
| `account_id` | BIGINT   | аккаунт владельца, `UNIQUE` — один дом на аккаунт      |
| `claimed_at` | BIGINT   | unix-время занятия (диагностика)                       |

Write-through, как членство фракций (`faction_member`), через ЕДИНУЮ точку
`HouseSystem::onOwnerChanged` (подписка на `HouseService::subscribeOwnerChanged`
— зовётся после КАЖДОГО успешного `setOwner`, будь то итог торгов, передача
(`Docs/HomeMenu.md`) или выселение):

- **`newKey` непустой (итог торгов/передача)** — `DELETE WHERE house_id=… OR
  account_id=…` + `INSERT` в ОДНОЙ ТРАНЗАКЦИИ внутри `throwQuery`
  (`startTransaction`/`commit`, при исключении — `rollback` + проброс): либо вся
  пара применилась, либо ничего. Память владения выставляется оптимистично ДО
  запроса; при сбое записи `errorCallback` откатывает её на `oldKey` через
  `setOwnerSilent` (БЕЗ повторной нотификации — иначе рекурсия запускала бы новую
  БД-попытку и при затяжном сбое БД зациклила бы откаты) + перекраска иконки.
- **`newKey` пустой (выселение)** — `DELETE WHERE house_id=…`.
- **Удаление дома** (`/house`, отдельный путь — НЕ идёт через `setOwner`) —
  `DELETE WHERE house_id=…` (нет осиротевшего владения; иначе строка ссылалась бы
  на несуществующий дом и блокировала бы аккаунт по `UNIQUE`).
- **Загрузка на старте** — один `selectQuery` всех строк `house_owner`, чейнится
  ПОСЛЕ разбора описаний (`loadOwnershipAsync`) **безусловно на всех ветках**
  (пусто / битый файл / успех), а не только на успешной. Воркер вычитывает строки
  под per-row `try/catch`: порченое поле (NULL/тип/конвертация) пропускает ТОЛЬКО
  эту строку (`continue`), а не валит всю выборку — одна битая запись `house_owner`
  не теряет всё владение. Колбэк на главном потоке: для каждой живой записи
  (`account_id != 0`, дом ещё существует) — `setOwnerSilent` в памяти (БЕЗ
  нотификации `subscribeOwnerChanged` и БЕЗ записи в БД — иначе загрузка
  зеркала спровоцировала бы избыточный write-through каждой строки обратно в ту
  же БД, откуда она только что прочитана) + `refreshHouseIcon` (зелёная →
  красная). `getHouse`-гард отсекает
  осиротевшее владение (дом удалён из `houses.json`). По завершении (успех ИЛИ
  ошибка БД) `HouseSystem` зовёт `HouseService::markOwnershipLoaded()` — встаёт флаг
  `isOwnershipLoaded` (гейт занятия, см. ниже) И one-shot оповещаются подписчики
  (`subscribeOwnershipLoaded`; `SpawnChoiceSystem` перерезолвит спавн «Дом»). Если
  загрузка из БД упала, флаг всё равно встаёт: фичу не блокируем навсегда, работаем
  с пустым in-memory владением, а БД-бэкстопы держат консистентность.

**Гейт занятия (`HouseService::isOwnershipLoaded`).** Пока владение из БД не легло
в память, `ownsHouse` ещё не видит чужие дома — игрок мог бы занять второй дом до
прихода зеркала (старт-гонка «один дом на игрока»). Поэтому подведение итогов до
выставления флага отвечает `Дома ещё загружаются, попробуйте через момент` и
ничего не пишет. Флаг — одноразовый старт-гейт (узкое окно первых секунд после
запуска). Источник правды флага — `HouseService` (а не `HouseSystem`): по
завершении `loadOwnershipAsync` (на ВСЕХ ветках — успех/ошибка БД) `HouseSystem`
зовёт `HouseService::markOwnershipLoaded()` — флаг встаёт И one-shot оповещаются
подписчики.

**Оповещение о завершении загрузки (`subscribeOwnershipLoaded`).** Владение
грузится async ПОСЛЕ старта сессий — игрок с выбором спавна «Дом» успевает
залогиниться и применить спавн (`SpawnChoiceSystem`) ДО прихода `house_owner`,
поэтому `houseOf` сначала не находит дом и спавн уходит на порт (дефолт).
Чтобы это
исправить, `HouseService` даёт one-shot наблюдатель завершения загрузки владения
(`subscribeOwnershipLoaded`): `markOwnershipLoaded` оповещает подписчиков ровно
один раз и очищает список (поздняя подписка после загрузки вызывает колбэк сразу
— one-shot не теряется). `SpawnChoiceSystem` подписывается и по событию
перерезолвит спавн каждому ОНЛАЙН-игроку с выбором «Дом» (зеркало
`FamilySystem::loadAll`, где членство дорезолвится уже-онлайн игрокам). Загрузка
владения одноразовая на старте — новые логины после неё уже видят владение,
повторно дёргать не нужно. Spawn-authority не нарушается: перерезолв идёт через
`applySpawn` (выбор главнее, см. `Docs/SetSpawn.md`).

`UNIQUE account_id` — БД-бэкстоп к in-memory проверке `ownsHouse` (один дом на
аккаунт): если память и БД разойдутся, `DELETE … OR account_id=…` перед `INSERT`
держит таблицу консистентной.

### Битый файл

`HouseSystem::parse` крах-безопасен (вызывается из колбэка на ГЛАВНОМ потоке;
на воркере — только чтение файла в строку): `nlohmann::json::parse` в `try/catch`,
на ЛЮБОМ исключении (битый/обрезанный/мусорный файл) — `ok=false`; колбэк логирует
предупреждение, переименовывает файл в `houses.json.bak` и продолжает с ПУСТЫМ
списком (не падает, без UB). Если JSON распознан как массив, но отдельные элементы
битые — они МОЛЧА пропускаются (валидация каждого поля): `id` целое в `(0, MAX_HOUSE_ID]`
(вне диапазона — пропуск, защита от переполнения vw); `interiorIndex` целое в
каталоге; `entrance`/`exit` — массивы из трёх КОНЕЧНЫХ чисел В ГРАНИЦАХ МИРА
(`|x|,|y| ≤ 20000`, `z ∈ [-1000, 5000]` — как `inWorldBounds` в `PlayerLocationService`);
`exitAngle` — с дефолтом при пропуске/неверном типе; `parkingCap` — необязательный
целый, отсутствие/не-int (float/строка) → `DEFAULT_PARKING_CAP`, всегда кламп в
`[MIN_PARKING_CAP, MAX_PARKING_CAP]` = `[1, 10]` (кап=0 из правленого файла
невозможен, владелец всегда паркует хотя бы 1). Поля `virtualWorld` и `owner`
из файла ИГНОРИРУЮТСЯ: vw всегда пересчитывается (`VW_BASE + id`), а владение
берётся из БД (`house_owner`), не из файла.

## Константы баланса

| Константа              | Значение  | Смысл                                           |
|------------------------|-----------|-------------------------------------------------|
| `VW_BASE`              | 2000000   | база уникального vw дома (`VW_BASE + id`)        |
| `MAX_HOUSE_ID`         | 1000000   | потолок id дома (`VW_BASE + id` < `INT_MAX`)      |

## Три правила

- **Читер-абуз:** дев-тулза `/house` целиком за `DEVELOPER_LEVEL` (создание/
  удаление/телепорт — только дев). Все перемещения — ТОЛЬКО через
  `PlayerLocationService::teleport` (сырой `setPosition` анти-чит откатил бы).
  Позиция/угол входа — серверные (`getPosition`/`getRotation`), не
  клиент-доверенные. vw-изоляция интерьеров (`VW_BASE + id`). Содержимому файла не
  доверяем: каждое поле валидируется (id > 0, interiorIndex в каталог, координаты
  finite), битые записи пропускаются. Содержимое файла — только КОНТЕНТ (без
  владения), игроки его не пишут. **Занятие — серверное:** владелец = серверный
  `accountId` из `PlayerSessionService` (НЕ клиентский ник/ввод), в БД пишется
  ЧИСЛО; согласие перепроверяет, что дом жив и ещё ничейный, а игрок ещё не владеет
  домом (in-memory `ownsHouse`, наполняется из БД на старте); занять чужой/занятый
  дом нельзя. **Лимит парковки — серверный:** `House.parkingCap` из `houses.json`
  (дев-контент, вводится только девом в `/house`, валидируется в `[1, 10]`), счёт —
  из `ParkedVehicleService` (серверная память припаркованных). Клиент не влияет ни
  на кап, ни на счёт; обойти капом ЧУЖОГО дома нельзя — `parkHere` резолвит дом
  через `houseOf` по СВОЕМУ `accountId`, не по позиции. **Один дом на игрока** держится трижды: гейт `HouseService::isOwnershipLoaded`
  (до прихода зеркала из БД итоги торгов отложены — иначе `ownsHouse` не видит чужие
  дома и можно занять второй; закрывает старт-гонку), in-memory `ownsHouse` + БД
  `UNIQUE account_id` (бэкстоп; `DELETE … OR account_id=…` перед `INSERT` не даёт
  упереться в UNIQUE и держит таблицу консистентной). Обычный игрок взаимодействует
  ТОЛЬКО наступанием на пикап — дистанцию/мир/антиспам проверяет `PickupService`,
  это безопасно. 3D-текст у входа — данные сервер→клиент (`TextLabelService`
  санитизирует текст), клиентского ввода нет. `Выбрать дом по id`: ввод числовой
  (`showNumberInput` отсекает мусор/overflow повторным показом), id прогоняется через
  диапазон `(0, MAX_HOUSE_ID]` + `getHouse` (несуществующий → отказ).
  **Передача/выселение** (`/home`, детали абьюз-векторов — `Docs/HomeMenu.md`):
  ре-валидация `houseOf` на КАЖДОМ клике и заново на согласии MSGBOX (диалог мог
  висеть, пока дом уходил из-под ног другим окном); получатель — ТОЛЬКО серверный
  id + активная сессия (ник не вводится); гейт занятости не даёт `destroy` машину
  под сидящим водителем; персист — та же единая точка, что итог торгов (выше).
- **Краш/UB:** JSON-парсер не падает на мусоре (лог + пусто + `.bak`); bounds на
  `interiorIndex` (в каталог) и `id`; null-гарды (`getHouse`, `getPlayers().get`,
  `PlayerSessionService::get`); рантайм-хэндлы пикапов/иконки/3D-текста трекаются в
  `m_runtime` и снимаются при удалении (нет утечки/двойного remove — `despawnHouse`
  до `removeHouse`, `spawnHouse` не дублирует существующий id; лейбл снимается
  только при despawn по `runtime.label >= 0`); **перекраска иконки** через
  `refreshHouseIcon` снимает старый хэндл и пишет новый в `Runtime::mapIcon` (нет
  утечки/двойного remove); диалог занятия заново берёт живого игрока и сессию
  (после согласия игрок мог выйти / сессия смениться); async file `errorCallback`
  (ошибки диска не валят сервер); **БД-запросы** (`throwQuery`/`selectQuery`) с
  `errorCallback` — ошибки БД логируются, не валят сервер; **загрузка владения**
  чейнится ПОСЛЕ разбора описаний (безусловно, на всех ветках), воркер-вычитка
  под per-row `try/catch` (битая строка `house_owner` пропускается, не валит
  выборку), колбэк на ГЛАВНОМ потоке, `getHouse`-гард перед
  `setOwner`/`refreshHouseIcon` (осиротевшее владение пропускается, рантайм-иконка
  гарантированно есть); **откат памяти при сбое записи занятия** в `errorCallback`
  (главный поток) заново берёт живого игрока и дом (`getPlayers().get`/`getHouse` +
  null-гарды — могли стать невалидны за время запроса), сверяет владельца перед
  откатом; колбэки пикапов/диалогов заново берут живого игрока; ввод
  id через `showNumberInput` (парс на сервисе) + диапазон/`getHouse`-гард (мусор →
  повтор, несуществующий → сообщение); **ввод лимита парковки** через `showNumberInput`
  (парс на сервисе) + диапазон-гард в колбэке (вне `[1, 10]` → ре-показ, дом не
  создаётся), колбэк заново берёт живого игрока (`getPlayers().get` + null — дев мог
  выйти на вводе), `createHouse` клампит кап повторно (двойная страховка); ре-триггер
  выхода исключён грейсом + смещением.
- **Перф:** пикапы/иконки/3D-текст событийные (создаются со спавном дома, нет
  per-tick); запись файла async вне главного потока; **владение из БД** — один
  `selectQuery` на старте; запись владения (`throwQuery`) — на ХОЛОДНОМ пути
  (создание/удаление, редко); на дом — O(1) операции (мапа по id). Торги — холодный
  путь (пикап-событие → диалог); `ownsHouse` и гейт семьи — по ПАМЯТИ, без БД-
  обращений per-check; per-tick БД нет. Список домов и выбор по id в дев-меню —
  холодный путь (по диалогу), сортировка id только в списке. Ввод лимита парковки —
  холодный дев-путь (по диалогу); enforce капа при парковке (`countParkedByAccount`)
  — O(записей владельца, ≤ кап, мало), холодный путь (по клику в `/car`).
