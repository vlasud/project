# Вещи и аптечки (Inventory)

Код: `Src/Services/InventoryService` (контейнер состояния + реестр типов),
`Src/Systems/InventorySystem` (персист по сессии + дев-выдача `/idev`),
`Src/Systems/MedkitSystem` (аптечка как первый предмет + `/healme`).
Общий потолок HP (используется в `/healme`): `Src/Services/Core/PlayerHealthService`.
Схема БД: `Sql/items.sql` (`player_items`).
Тексты/цвета: `Docs/GameDesign/UI_Texts.md`, раздел «Вещи и аптечки /healme».

## Что это

Фундаментальная система предметов игрока. Предмет — целочисленный тип
(`item_type > 0`) с количеством. У каждого типа — максимальный размер стека
(`maxStack >= 1`). Сами типы — часть кода (новый предмет = новая система-владелец),
поэтому **регистрируются кодом** через `InventoryService::registerItem` из
конструкторов систем (как фракции саморегистрируются `registerFaction`). В БД —
только данные: количество по типу на аккаунт.

Выдача сейчас — через **дев/админ-команду** `/idev` (покупка/лут/магазины —
будущее). Эффекты предметов — в системах конкретных предметов, не в базе.

## InventoryService (источник правды о вещах онлайн)

Чистый контейнер состояния + реестр типов (как `FactionService`): без
бизнес-эффектов и без обращений к БД внутри. Конструируется без зависимостей.

| Метод | Семантика |
|----|----|
| `registerItem(type, name, maxStack)` | реестр типов; `type > 0` уникален, `maxStack >= 1`; нарушение/дубликат — игнор с журналом (баг регистрации) |
| `add(playerId, type, n)` | добавить, НЕ выше `maxStack`; возвращает реально добавленное (0..n); `n<=0`/незарегистрированный тип → 0 |
| `remove(playerId, type, n)` | снять `n` **атомарно**: `count>=n` → снимает и `true`, иначе НИЧЕГО не снимает и `false`; `n<=0` → `false` |
| `count(playerId, type)` | текущее количество; невалидный/незарегистрированный → 0 |
| `maxStack(type)` | потолок стека типа; не зарегистрирован → 0 |
| `registeredItems()` | список `ItemDef{type,name,maxStack}` для дев-диалога |
| `loadItems(playerId, [(type,qty)])` | применить с **клампом** к `maxStack`; незарегистрированные/мусор (`qty<=0`) отбросить |
| `snapshot(playerId)` | ненулевые `(type,qty)` для сохранения |
| `reset(playerId)` | чистка слота (коннект/дисконнект) |

Состояние на игрока — маленький вектор стеков (предметов мало). `bounds-check`
`playerId` во всех методах. Горячего пути нет — всё событийно.

## Персист (загрузка на старте / сохранение на конце сессии)

Эталон — `WeaponProficiencySystem`. Персист по сессии (как личный скин и
проф-оружия), НЕ write-through:

- **Коннект/дисконнект** — `reset` слота, чтобы вещи одного аккаунта не утекли
  следующему игроку в том же `playerId`-слоте.
- **Старт сессии** (`subscribeStart`) — async `selectQuery` строк `player_items`
  по `account_id`; на главном потоке **serial-guard** (сессия не сменилась) +
  проверка, что игрок ещё онлайн, затем `loadItems`. Флаг `m_loaded[playerId]`
  ставится только после успешного колбэка.
- **Персист** (`subscribeSave`) — `REPLACE` снимка в `player_items` одним
  `throwQuery`: удаляем все строки аккаунта и вставляем текущие ненулевые
  (пропавшие предметы исчезают, нули не хранятся). **Не персистим**, если
  `m_loaded == false` (сбой загрузки/дисконнект до её колбэка) — иначе пустой слот
  затёр бы реальные вещи в БД. Идемпотентен, поэтому в save-канал: зовётся на конце
  сессии (внутри `end`, до teardown) **И** периодически автосейвом онлайн-игроков
  (см. `Docs/Autosave.md`).

### Потеря при краше и будущая покупка

Изменения в течение сессии живут **в памяти**, в БД уходят на конце сессии.
Краш/перезапуск сервера → изменения текущей сессии теряются (как личный скин и
проф-оружие). Для дев-выдачи это допустимо.

**Будущая ПОКУПКА** (трата денег за предмет) обязана быть устойчивой к крашу:
форсить сохранение сразу после операции **или** перейти на write-through для
покупаемых предметов. Сейчас write-through намеренно НЕ вводим (не усложняем).

### Известные ограничения персиста (по итогам QA-аудита)

- **`persistItems` атомарен (транзакция).** DELETE всех строк аккаунта + INSERT
  ненулевых выполняются в одной транзакции (`startTransaction`/`commit`, `rollback`
  при сбое). Это убрало частичную запись (падение воркера между удалением и частью
  вставок) и видимое «ноль строк» между DELETE и INSERT (параллельная загрузка
  больше не прочтёт пустой инвентарь).
- **Остаточная узкая гонка порядка персист↔загрузка при быстром релоге.** Сохранение
  старой сессии (`subscribeEnd`) и загрузка новой (`subscribeStart`) уходят на разные
  воркеры пула без гарантии порядка. Транзакция гарантирует, что загрузка прочитает
  ЛИБО полностью старое, ЛИБО полностью новое состояние (не частичное/пустое), но не
  гарантирует, что персист выполнится РАНЬШЕ загрузки: при очень быстром реконнекте
  загрузка может прочитать ещё не закоммиченное старое состояние (узкое окно, нужен
  лаг БД/спам реконнектов). Функционально почти безвредно СЕЙЧАС (оффлайн инвентарь
  не меняется → старое == новому). Станет важно при write-through/покупке — тогда
  сериализовать запись и чтение одного `account_id` (барьер «не стартовать загрузку,
  пока не завершён персист предыдущей сессии аккаунта»; требует доработки
  `DatabaseManager` под per-account очередь).
- **Штатная остановка сервера: потеря СМЯГЧЕНА автосейвом.** open.mp на выходе
  (`~Core → players.free()`) НЕ диспатчит `onPlayerDisconnect`, поэтому
  `PlayerSessionService::end()` и через него session-end-персист (наш `persistItems`)
  для остававшихся онлайн игроков не срабатывают. Чтобы изменения не терялись
  целиком, `persistItems` переведён в save-канал (`subscribeSave`) и гоняется
  **периодическим автосейвом** онлайн-игроков (`Src/Systems/AutosaveSystem`,
  интервал 2 мин — см. `Docs/Autosave.md`). Потеря ограничена интервалом автосейва
  (а не всей сессией) и покрывает также краш. Это **общее решение для всех систем
  на session-персисте** (инвентарь, прокачка оружия, личный скин). **Zero-loss на
  штатном стопе по-прежнему НЕ гарантируется**: гарантированная нулевая потеря
  требует хрупкого shutdown-flush (в `GameMode::free()` до `ThreadPool::shutdown`
  форсить персист онлайн-игроков и синхронно дренировать очереди `DatabaseManager`)
  — отложено намеренно.

## Дев-выдача `/idev`

Конвенция «дев-тулинг = ОДНА команда → диалог-меню» (как `/edev`/`/fdev`). Команда
`/idev`, право `AdminService::DEVELOPER_LEVEL` (admin level 6), скрыта из `/help`
(`HelpCategory::Hidden`).

- Меню выбора предмета — `DialogStyle_LIST`, заголовок «Вещи — дев-меню», один
  предмет на строку body (в порядке регистрации; `listItem` = индекс в
  `registeredItems`), кнопки «Выбрать»/«Закрыть». Новые предметы — новыми строками
  автоматически.
- Шаг количества — `DialogStyle_INPUT`, заголовок «Выдача: {item}», тело «Введите
  количество», кнопки «Выдать»/«Назад» («Назад» — возврат в меню выбора, не
  закрытие). Ввод — клиентский: `showNumberInput` отсекает мусор/overflow повторным
  показом; диапазон `1..MAX_DEV_GRANT` (10000) проверяем сами. `add` всё равно
  клампит к `maxStack`.
- Успех — `ADMIN_COLOUR` (`0xFFB400FF`): «Выдано: {n} × {item}. Всего: {total}»
  (`{n}` — реально добавлено, `{total}` — итог по типу). Выдача — **СЕБЕ**
  (вызвавшему); на цель можно расширить позже.

## Аптечка (первый предмет)

`Src/Systems/MedkitSystem`. В конструкторе регистрирует тип в `InventoryService` и
добавляет команду `/healme` (категория «Прочее», видима в `/help`).

### `/healme` — порядок проверок (важен для UX)

1. **Штраф после смерти** (`PlayerHealthService::hasMaxHealth(playerId)` —
   общий кэп HP активен) → отказ **первым**, цвет `ERROR_COLOUR`: «Вы ещё не
   оправились после смерти — лечиться нельзя». **Не тратим, не лечим.** Ключевое
   требование: под штрафом аптечка не работает, иначе обходит `DeathPenalty`
   (HP зажат на 10, поднять нельзя 5 минут — см. `Docs/DeathPenalty.md`).
2. **Полное здоровье** (`getHealth >= MAX_HEALTH - FULL_HEALTH_EPS`) → отказ, `ERROR_COLOUR`:
   «У вас полное здоровье — аптечка не нужна». До проверки наличия — не отнимаем
   предмет впустую.
3. **Нет аптечек** (`count == 0`) → отказ, `ERROR_COLOUR`: «У вас нет аптечек».
   Последним: осмыслен, только когда лечение разрешено и нужно.
4. Иначе: `hpBefore = getHealth`; `heal(MEDKIT_HEAL)` (серверно-авторитетно, зажим
   по 100); `restored = getHealth - hpBefore`. Если `restored <= 0` — лечение не
   применилось, аптечку **НЕ тратим** и выходим. Иначе `remove(ITEM_MEDKIT, 1)`
   (ровно одна, ПОСЛЕ лечения) и сообщение `INFO_COLOUR` (голубой): «Вы
   использовали аптечку: +{hp} HP. Осталось аптечек: {left}», где `{hp}` —
   **фактически восстановленное** HP (с 60 до 100 → +40, не +50), `{left}` —
   оставшееся количество.

Гард `restored <= 0` страхует редкое окно серверной смерти: пока сервер свёл HP в 0
и ждёт подтверждения от клиента (`alive && dying`), `heal` — no-op (обхода смерти
нет), поэтому аптечка в этот момент не списывается впустую.

## Баланс-константы

|----|----|----|
| `ITEM_MEDKIT` | 1 | код типа «Аптечка» в реестре вещей |
| `MEDKIT_HEAL` | 50.0 | сколько HP восстанавливает одна аптечка (зажим по 100/кэпу) |
| `MEDKIT_MAX` | 3 | максимум аптечек в стеке |

`Src/Systems/InventorySystem/InventorySystem.cpp`:

| Константа | Значение | Смысл |
|----|----|----|
| `MAX_DEV_GRANT` | 10000 | разумный предел разового ввода количества в `/idev` (до клампа `add` по `maxStack`) |

## Анти-чит / краш-безопасность / перф

- **Переполнение/дюп.** `add` зажимает к `maxStack` (нельзя > 3 аптечек). `remove`
  атомарен (проверка `count>=n` и снятие — одна операция, в минус не уводит).
  `/healme` снимает ровно одну аптечку и только после успешного лечения — дюпа нет.
- **Обход кэпа смерти.** `/healme` под активным кэпом HP полностью отказывает (не
  тратит, не лечит). Лечение идёт через серверно-авторитетный `heal` (зажим по
  100/кэпу), напрямую `setHealth` мимо сервиса не зовём.
- **Загрузка из БД** валидируется реестром (неизвестный тип отбрасывается) и
  клампится к `maxStack` (устаревший избыток не осядет). `item_type`/`quantity`
  читаются как `int64` и сужаются — битый ряд не роняет загрузку.
- **Async-колбэк БД** под serial-guard + проверкой онлайна: чужая сессия не получит
  чужие вещи, мёртвый игрок не разыменовывается.
- **Дев-команда** — `DEVELOPER_LEVEL`; ввод количества санитизируется
  (`1..MAX_DEV_GRANT`, мусор/overflow отсечён `showNumberInput`).
- **Перф.** Всё событийно (команда/диалог/старт-конец сессии), не per-tick.
  Контейнеры маленькие; в `loadItems`/`snapshot` — линейный обход короткого вектора.
