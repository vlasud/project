# Заработок по работам (`/jobwallet`)

Бизнес-фича (НЕ Core). Код:
- `Src/Services/JobWalletService` — сколько заработанного лежит у игрока по каждой
  работе и где это забирают.
- `Src/Systems/JobWalletSystem` — привод: команда `/jobwallet`, диалог со списком,
  напоминание в чат после логина.

## Зачем

Заработок каждой работы копится в её СОБСТВЕННОМ персистентном кошельке
(`BusWalletService` / `PortWalletService` / `HaulerWalletService`, у каждого своя
таблица), и забрать его можно было только у пикапа этой работы. Игрок, вышедший с
деньгами в кошельке, в следующий заход про них не вспоминает: на пикап он приходит,
только когда снова собрался работать.

Теперь есть единая СПРАВКА и напоминание на входе — но **только если забрать
действительно есть что**.

**Деньги отсюда не выдаются.** Забирают их по-прежнему на месте, у пикапа работы:
доехать до работы за своим заработком — это правило игры, а не техническое
ограничение. Поэтому окно только показывает, сколько и где лежит, а в регистрации
кошелька нет и не должно быть обработчика выдачи.

## Напоминание на входе

```
логин ──► работы асинхронно грузят свои кошельки из БД
          └─ каждая по готовности зовёт JobWalletService::notifyLoaded(playerId)
             └─ сумма по всем кошелькам > 0 и ещё не напоминали?
                └─ в чат: «Вы можете забрать заработанные деньги. Подробнее /jobwallet»
```

Спрашивать сумму прямо на старте сессии бесполезно: кошельки грузятся из БД
**асинхронно** и по одному, в этот момент там ещё нули. Поэтому сигналом служит сама
загрузка: работа зовёт `notifyLoaded`, когда её баланс лёг в память.

- **Одна строка на сессию.** Загрузок несколько (по числу работ), напоминание уходит
  на той, что первой дала ненулевую сумму. Флаг сбрасывается на старте сессии —
  переиспользованный слот `playerId` чужого напоминания не наследует.
- **Нулевая сумма — не повод замолчать навсегда:** остальные кошельки ещё грузятся, и
  напоминание уйдёт позже. Если денег нет нигде, игрок ничего и не увидит — как и
  задумано.

## Диалог `/jobwallet`

`DialogStyle_TABLIST_HEADERS`, заголовок с общей суммой, строка на каждую работу,
единственная кнопка «Закрыть»:

```
Заработок по работам — всего $4200
Работа                 В кошельке   Где забрать
водитель автобуса      $0           пикап работы в депо автобусов
грузчик порта          $1700        пикап работы в порту
портовый развозчик     $2500        пикап работы в депо развозчиков
```

Окно **справочное**: строки ничего не делают, забрать деньги отсюда нельзя. Колонка
«где забрать» поэтому обязательна — без неё список бесполезен: игрок узнал бы сумму,
но не узнал, куда ехать.

Показываются **все** зарегистрированные работы, включая нулевые: недоступность не
прячет строку (правило проекта), заодно видно, где заработок вообще бывает.

Единственная точка выдачи — пункт «Забрать деньги» на пикапе работы, как и раньше
(ре-валидация сессии по серверному `accountId`, обнуление кэша СРАЗУ против дюпа
двойным кликом, write-through в БД, выдача наличных через `PlayerMoneyService`).

## Саморегистрация работ

Как в `JobDismissService`: работа регистрирует свой кошелёк в конструкторе системы.

```cpp
serviceRegister.getService<JobWalletService>().registerWallet(
    "грузчик порта", "пикап работы в порту",
    [this](int playerId) { return m_portWalletService.balanceOf(playerId); });
```

Плюс одна строка в колбэке загрузки кошелька:

```cpp
m_portWalletService.load(playerId, balance);
m_jobWalletService.notifyLoaded(playerId);
```

**Новая работа подключается этими двумя строками** — ни сервис, ни `/jobwallet` не
правятся.

### Зарегистрированы сейчас

| Работа | Кошелёк | Где забирают | Таблица |
|---|---|---|---|
| `BusJobSystem` | водитель автобуса | пикап работы в депо автобусов | `bus_wallet` |
| `PortJobSystem` | грузчик порта | пикап работы в порту | `port_wallet` |
| `HaulerJobSystem` | портовый развозчик | пикап работы в депо развозчиков | `hauler_wallet` |

## Три правила

- **Читер-абуз:** окно ничего не меняет — оно только читает балансы, поэтому денежного
  вектора у него нет вовсе (нет ни выдачи, ни выбора строки, ни индекса от клиента).
  Выдача осталась там же, где была: пикап работы, `accountId` из СЕРВЕРНОЙ сессии,
  обнуление кэша до записи в БД (двойной клик выдаёт один раз), относительное списание
  в БД. Игрок видит только свой слот (`playerId` вызывающего). Антифлуд команды —
  корневой, в `PlayerCommandService` (см. `Docs/CommandFlood.md`).
- **Краш-безопасность:** колбэк диалога пустой — состояние он не трогает;
  `notifyLoaded` приходит из
  async-колбэка, где сама работа уже сделала serial-guard сессии, а система дополнительно
  проверяет `validPlayerId` и наличие игрока в пуле; регистрация без колбэков
  отбрасывается с записью в лог — пустой `std::function` не вызывается; ссылка на
  список стабильна (наполняется только на старте).
- **Перф:** событийно — команда игрока и три загрузки кошелька за логин. `totalBalance`
  и построение тела диалога — проход по числу работ (сейчас 3) с чтением кэша из
  памяти, без обращений к БД. Per-tick работы нет.
