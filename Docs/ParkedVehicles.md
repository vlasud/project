# Припаркованные у дома машины

Припаркованные у дома машины — бизнес-фича (НЕ Core). Код:
`Src/Services/ParkedVehicleService`, `Src/Systems/ParkedVehicleSystem`.

**Парковка у дома — БАЗОВОЕ состояние размещения** личной машины: постоянная точка
≤30 м от СВОЕГО дома, персист в БД, спавн/респавн там, переживает выход/рестарт.
**Шеринг семье — РЕЖИМ ДОСТУПА поверх** той же припаркованной машины (не отдельная
сущность): та же машина у дома, но водить могут все члены семьи владельца.
Собственность ВСЕГДА остаётся у аккаунта владельца (строка `personal_vehicle` НЕ
трогается).

**У места парковки машина НИКОГО НЕ ЖДЁТ — она приезжает по ВЫЗОВУ.** Живой экземпляр
существует только пока машина вызвана И вызвавший в игре: `/car` → «Вызвать машину» у
владельца, `/family` → «Транспорт семьи» у члена семьи (расшаренная — тоже только по
вызову). На выходе вызвавшего машина уходит из мира, после рестарта сервера у точки не
стоит ничего. Вызывать можно с ЛЮБОГО расстояния — машина появляется на СВОЕЙ точке
парковки (её ставит сам владелец, припарковав машину у дома), а не рядом с игроком.
**Слот вызова один:** новый вызов снимает прошлую вызванную ЭТИМ ЖЕ игроком машину —
безусловно, даже если в ней кто-то сидит. Запись `parked_vehicle`
(точка/владение/топливо) персистит ВСЕГДА — исчезновение экземпляра НЕ удаляет запись
(см. «Жизненный цикл экземпляра» ниже).

## Три состояния размещения машины

`PersonalVehicleService::OwnedVehicle{model, vehicleId, dbId}` имеет три
**взаимоисключающих** состояния (источник правды о размещении у дома —
`ParkedVehicleService`):

1. **В ОБЩЕМ ГАРАЖЕ** (по умолчанию): спавн через центральную парковку
   (`ParkingSystem`, 5 точек), СЕССИОННО. Нет строки `parked_vehicle`.
2. **ПРИПАРКОВАНА У ДОМА (лично)**: `parked_vehicle` с `family_id = NO_FAMILY`. В мире
   машины нет, пока её не ВЫЗВАЛИ (статус `в гараже`); по вызову экземпляр
   `Owner::Parked` появляется на своей точке у дома. Вызывать и водить может ТОЛЬКО
   ВЛАДЕЛЕЦ (замок).
3. **ПРИПАРКОВАНА + РАСШАРЕНА СЕМЬЕ**: та же строка `parked_vehicle`, но `family_id`
   = id семьи. Тот же экземпляр `Owner::Parked`, тоже ТОЛЬКО по вызову; вызывать и
   водить могут ВСЕ ЧЛЕНЫ семьи (их вход в вызов — `/family` → «Транспорт семьи»).

Переход гараж↔у-дома — **ре-тег НА МЕСТЕ** (тот же `vehicleId`, БЕЗ destroy/create):
меняются серверный тег (`VehicleService::setOwner`) и spawn-точка
(`setSpawnPosition`) на ЖИВОМ экземпляре, `park`/`unparkKeepInstance` правят лишь
запись+БД. Игрок остаётся в машине, она стоит где стояла (не пересоздаётся, не
респавнится, не исчезает). Переход лично↔в-семье — только `UPDATE family_id`, машина
НЕ пересоздаётся (замок применяется на следующей посадке за руль).

## Жизненный цикл экземпляра (вызов машины)

**ИНВАРИАНТ:** живой экземпляр припаркованной машины существует в мире ТОГДА И ТОЛЬКО
ТОГДА, когда запись ВЫЗВАНА (`Parked::calledBy != NO_ACCOUNT`) и вызвавший аккаунт
сейчас ОНЛАЙН. Ни владение, ни шеринг семье сами по себе экземпляр НЕ держат — у точки
парковки никто не ждёт. Запись `parked_vehicle` (точка/владение/топливо) персистит
ВСЕГДА, пока машина припаркована — исчезновение экземпляра НЕ удаляет запись.

**`calledBy` — РАНТАЙМНОЕ состояние, в БД не уходит:** после рестарта сервера все
записи загружаются невызванными, и в мире у точек не стоит ничего, пока игроки не
вызовут машины заново. Это и есть смысл фичи: пул не держат машины, которых никто не
ждёт.

Держат инвариант три точки:

- **вызов** (`ParkedVehicleService::call(dbId, caller)`) — ставит `calledBy = caller` и
  нотифицирует `subscribeReconcile` → система заводит экземпляр на точке. Гейт — тот
  же, что у руля (`hasAccess`): личную вызывает только владелец, расшаренную — любой
  член семьи-получателя. Расстояние НЕ проверяется (машина появляется на своей точке).
  **Слот вызова один:** `releaseOtherCalls(caller, keepDbId)` снимает прошлые вызовы
  этого аккаунта (`clearCall` → reconcile → деспавн), даже если в машине кто-то сидит;
- **парковка** (`park(..., liveVehicleId)`) — машину игрок ПРИГНАЛ сам, экземпляр уже
  стоит у точки, поэтому запись сразу помечается вызванной владельцем (и занимает его
  слот вызова). Иначе `calledBy == NO_ACCOUNT` при живом `vehicleId` разошёлся бы с
  миром: reconcile такой экземпляр не держит, а снять его на выходе владельца было бы
  некому (`onCallerOffline` идёт ПО ВЫЗОВАМ) — машина осталась бы ждать у точки;
- **выход вызвавшего** (`PlayerSessionService::subscribeEnd` → `onCallerOffline`) —
  снимает ВСЕ вызовы аккаунта (`calledByAccount` → `clearCall`), экземпляры уходят из
  мира. Запись и строка БД целы.

Три хелпера системы (по `dbId`, через публичный API сервиса `byDbId`/`setVehicleId`):

- **`spawnInstance(dbId)`** — завести экземпляр, если ещё нет (`vehicleId != -1` →
  no-op). `create(model, spot, angle, -1, -1, Owner::Parked, -1)` + `setVehicleId` +
  восстановление персистентного остатка бака поверх дефолтного полного (`setFuel`).
  Идемпотентно; пул-переполнение (`create == nullptr`) логируется, `vehicleId`
  остаётся `-1` (повтор на следующем вызове);
- **`despawnInstance(dbId)`** — уничтожить экземпляр, СОХРАНИВ запись+БД (это НЕ
  `unpark`). Снимает остаток бака в запись + write-through `UPDATE` ДО `destroy`
  (иначе следующий вызов дал бы бесплатный полный бак). **Порядок: `setVehicleId(dbId,
  -1)` ДО `destroy`** — тогда синхронный `onVehicleDestroyed` записи по `vehicleId` уже
  не найдёт (`m_byVehicleId` снят) → no-op, без ре-энтрантной порчи индексов (тот же
  паттерн, что `unpark`/`reset`). Идемпотентно (`vehicleId == -1` → no-op);
- **`reconcile(dbId)`** — единая точка: `desired = accountOnline(rec->calledBy)`; спавн
  при `desired && vehicleId==-1`, деспавн при `!desired && vehicleId!=-1`.

**Онлайн-трекинг** — `accountOnline(accountId)` резолвит через
`PlayerSessionService::playerByAccount` (единственный источник правды об онлайне; свой
`set<AccountId>` НЕ ведём — риск рассинхрона на двойном входе/перелогине, которые
сессия уже разруливает). `NO_ACCOUNT` → не онлайн. O(1).

**КРИТИЧНО по таймингу end-обработчика:** `PlayerSessionService::end` делает
`m_online.erase(accountId)` ПОСЛЕ прогона end-обсерверов. Значит внутри `subscribeEnd`
аккаунт ещё числится онлайн (`accountOnline` вернул бы `true`), и сам `reconcile`
экземпляр НЕ убрал бы. Поэтому `onCallerOffline` снимает вызовы ЯВНО (`clearCall`) — а
деспавн уже делает reconcile, которому `clearCall` и нотифицирует. На старте сервера
(`loadParked`) reconcile НЕ зовётся вовсе: вызванных записей после рестарта нет.

**Переходы режима доступа** (`shareToFamily`/`unshareFromFamily`,
`onFamilyDissolved`/`onOwnerLeftFamily` — ТРАНЗИТИВНО через `unshareFromFamily`) тоже
нотифицируют `subscribeReconcile`, но экземпляр от смены `family_id` НЕ появляется и НЕ
исчезает: желаемое состояние считается ТОЛЬКО по `calledBy`. Смена `family_id` меняет
лишь КОМУ можно вызывать и садиться за руль (замок применяется на следующей посадке).

**Непересечение с `PersonalVehicleService::reset`:** припаркованная прошла `detach`
(`vehicleId` владения → -1), поэтому `reset` (уничтожает владение с `vehicleId != -1`)
её НЕ трогает. Наборы `reset` (сессионные Personal) и `onCallerOffline` (Parked) —
непересекающиеся `vehicleId`; порядок между `PersonalVehicleSystem` и
`ParkedVehicleSystem` на конце сессии некритичен, двойного `destroy` одного id нет.

**Ре-энтрантность/двойной спавн:** `spawnInstance`/`despawnInstance` идемпотентны (гейт
по `vehicleId`); `setVehicleId` синхронно за `create` (окна между create и регистрацией
нет); `clearCall` идемпотентен (`calledBy == NO_ACCOUNT` → выход без нотификации);
`releaseOtherCalls` перебирает КОПИЮ `calledByAccount` (`clearCall` правит записи, но в
`m_byDbId` не вставляет и не удаляет); повторные start/end (перелогин без дисконнекта —
`start` сам зовёт `end`) безопасны. Спавн/деспавн — по числу вызванных записей (ноль
или одна на игрока), O(1) на запись.

## Источник правды

`ParkedVehicleService` — источник правды о ПАРКОВКАХ. Машины-сущности — у
`VehicleService` (Core, тег `Owner::Parked`); владение личными машинами — у
`PersonalVehicleService`; семьи/дома — `FamilyService`/`HouseService`.

Одна парковка — `struct Parked`:

- `personalVehicleId` — `dbId` (ссылка на `personal_vehicle.id`), PK парковки;
- `ownerAccountId` — аккаунт владельца (личный замок + возврат при выходе из семьи);
- `model` — модель машины;
- `spot` (`Vector3`), `angle` (`float`) — АБСОЛЮТНАЯ точка спавна у дома;
- `familyId` — `NO_FAMILY` (личная owner-only) ИЛИ id семьи (расшарена);
- `vehicleId` — id живого экземпляра (`Owner::Parked`) или `-1`;
- `fuel` — ПЕРСИСТЕНТНЫЙ остаток бака (`0..VehicleService::FUEL_CAPACITY`): источник
  правды, пока `vehicleId == -1`; пока заспавнена — источник правды
  `VehicleService::getFuel(vehicleId)`, поле лишь снимок на момент последнего
  сохранения (см. «Персист топлива» ниже);
- `calledBy` — аккаунт, ВЫЗВАВШИЙ машину к её точке, или `NO_ACCOUNT` (не вызвана — и
  тогда живого экземпляра в мире НЕТ). РАНТАЙМНОЕ поле, в БД не уходит (см. «Жизненный
  цикл экземпляра»). Запросы: `calledBy(dbId)`, `calledByAccount(accountId)` (линейный
  проход по записям — машин у игрока единицы, отдельный индекс держать дороже, чем
  синхронить), `canCall(dbId, accountId)`.

Индексы (все O(1)/холодные): `m_byDbId` (владеющий), `m_byVehicleId`
(гейт доступа/снятие), `m_byAccount` (`parkedByAccount`/`countParkedByAccount`/крайние
случаи), `m_byFamily` (`parkedOfFamily`/крайние случаи). **`NO_FAMILY` в `m_byFamily` НЕ
индексируется** — иначе `parkedOfFamily(NO_FAMILY)` вернул бы все личные машины сервера.

**`countParkedByAccount(accountId)`** — число ПРИПАРКОВАННЫХ машин аккаунта
(`m_byAccount.count`, без аллокации вектора). Считает ВСЕ записи владельца — личные
(`NO_FAMILY`) И расшаренные им семье (шеринг НЕ трогает `m_byAccount`, запись
остаётся у владельца). Все они стоят у ЕГО дома (модель «один дом, радиус 30 м»),
поэтому это и есть счёт для капа парковки у дома (см. `Docs/Houses.md`,
`Docs/CarMenu.md`). O(записей владельца, ≤ кап, мало).

**Зависимости** — `VehicleService`, `FamilyService` через `bind(...)` (зовёт
`ParkedVehicleSystem` в конструкторе). `HouseService` в сервис НЕ передаётся —
дом-гейт живёт в системе (где есть игрок/позиция).

## Owner::Parked (единый тег)

`VehicleService::Owner::Family` обобщён в `Owner::Parked` — ЕДИНЫЙ тег для всех
припаркованных машин (и личных, и семейных). Тег лишь маркирует, что машину при
СМЕРТИ (died-наблюдатели видят только серверно-санкционированную — контракт смерти в
`Docs/Vehicles.md`) НЕ удаляет `PersonalVehicleSystem` (`onVehicleDied` трогает только
`Owner::Player`, ранний return для прочих) — машина вернётся на
`spawnData.position = spot` респавном.
**`ownerId` тега служебный/неиспользуемый** (`create(..., Owner::Parked, -1)`):
`accountId` владельца (int64) не влезает в `int ownerId`, а для личной машины нет
`familyId`. Всё право доступа — в записи `Parked`, а не в теге.

## `dbId` в личных машинах

`PersonalVehicleService::OwnedVehicle` содержит `long long dbId` (id строки
`personal_vehicle`, `AUTO_INCREMENT`) — стабильный ключ, по которому парковка ссылается
на КОНКРЕТНУЮ машину. Не меняется этой фичей (заведён предыдущей). Окно `dbId == -1`
(между покупкой и приходом `LAST_INSERT_ID`) — машину нельзя парковать/шарить.

## `/car` — меню личного транспорта

`/car` теперь двухуровневое (корень: `Текущая машина` / `Мои машины` — полная
структура и все тексты в `Docs/CarMenu.md`). Раздел «Мои машины» — прежний список
владения; под-диалог машины (`CarMenuSystem`) видим ВСЕГДА (правило видимости — не
прячем по членству/роли/состоянию; недоступность объясняет обработчик сообщением).
Порядок: **Вызвать машину (или «Вызвать заново», если уже вызвана вами) / Респавн /
Показать на карте / Припарковать эту машину здесь / Убрать с парковки / Передать семье
(или «Вернуть от семьи», если уже расшарена)**. Гейт — в обработчике, не в
`buildActions`.

### «Вызвать машину» / «Вызвать заново»

Подаёт припаркованную машину на ЕЁ точку парковки. Расстояние не проверяется —
владелец вызывает машину откуда угодно, она появляется у дома (а не рядом с ним).
Лейбл динамический: «Вызвать заново», если машина уже вызвана ЭТИМ игроком — и тогда
пункт действительно ПОДАЁТ её на место заново: `call` видит живой экземпляр своего
вызывающего и делегирует в `respawnHome` (тот же путь, что «Респавн», без пересоздания
машины и с анти-абьюзом топлива). Под сидящим водителем — отказ `Occupied` (машину из
-под водителя не выдёргиваем).

`ParkedVehicleService::call(dbId, accountId)` (accountId СЕРВЕРНЫЙ, из сессии):

| Result | Сообщение |
|--------|-----------|
| `Ok` | `Машина вызвана и ждёт на своём месте парковки` |
| `Occupied` (повторный вызов, за рулём водитель) | `Вы сами за рулём — выйдите из машины, чтобы подать её на место` / `Пока в машине водитель, подать её на место нельзя` |
| `NotParked` | `Эта машина не в гараже — её сначала нужно припарковать у дома` |
| `NoAccess` | `Вызывать эту машину может только владелец или семья, которой она расшарена` |
| прочее | `Сейчас машину вызвать нельзя` |

Тексты — общие с `/family` → «Транспорт семьи» (header-only
`ParkedVehicleService/ParkedVehicleCallNotice.h`, аналог `ParkedVehicleRow`): входов в
вызов два, объяснение одного кода должно быть одно.

**Слот вызова один:** прошлая вызванная этим игроком машина уходит из мира сразу,
БЕЗУСЛОВНО — в том числе если в ней кто-то сидит (решение вызвавшего; пассажиры
оказываются на её месте). Второй вызванной машины у игрока быть не может.

### «Респавн» (новый пункт)

Убирает/возвращает машину по ТЕКУЩЕМУ размещению:

- **«вызвана»** (сессионная в мире, не припаркована) — не занята водителем ->
  `VehicleService::destroy` (уходит «на парковку», владение НЕ удаляется — заново
  вызывается на центральной парковке); занята водителем -> отказ.
- **припаркована («у дома» / «у дома семьи» / «брошена»)** (живой экземпляр есть) — не занята
  водителем -> `ParkedVehicleService::respawnHome(dbId)` -> `VehicleService::
  respawn(vehicle)`, машина телепортируется на её `spawnData.position` (уже =
  точка парковки, см. `setSpawnPosition` в `parkHere`); занята водителем -> отказ
  (анти-гриф — не выдёргивать машину из-под владельца/члена семьи за рулём).
- **«на парковке»** (не припаркована, нет живого экземпляра) — отказ «Машина уже на
  парковке»; **«в гараже»** (припаркована, но НЕ вызвана — `vehicleId == -1` у
  `Parked`, штатное состояние) — отказ `Эта машина в гараже — вызовите её, и она
  приедет на своё место` (возвращать на точку нечего: подача машины на место и есть
  вызов).

**АНТИ-АБЬЮЗ (топливо):** `VehicleService::respawn` — обёртка `vehicle.respawn()`
ядра, которое САМО даёт ПОЛНЫЙ БАК (`onVehicleRespawn`, как при любом респавне).
`ParkedVehicleService::respawnHome` снимает ТЕКУЩИЙ остаток `getFuel(vehicleId)` В
САМУ ЗАПИСЬ (`Parked::fuel`, то же поле, что источник правды деспавненной машины)
СРАЗУ ПЕРЕД вызовом `respawn` — а `ParkedVehicleSystem::onVehicleRespawned`
(подписан на `VehicleService::subscribeRespawned` уже ради восстановления после
несанкционированной смерти) восстанавливает его поверх дефолта БЕЗ ДУБЛИРОВАНИЯ
кода: единый метод теперь смотрит СНАЧАЛА на `m_pendingFuelRestore` (снимок
несанкционированной смерти — `onUnsanctionedDeath` кладёт его туда ДО ЛЮБОГО
возврата, в т.ч. повторной смерти на ядровом death-таймере, так что эта ветка
покрывает ВСЕ несанкционированные смерти), а если снимка нет — на саму запись
`Parked::fuel` (единственный путь без снимка в мапе — наш явный «Респавн» из
`/car`, `respawnHome` кладёт снимок ПРЯМО В ЗАПИСЬ). Подробности персиста топлива —
«Персист топлива» ниже (там же обновлён список источников снимка/восстановления).

### Припарковать эту машину здесь (гараж → лично у дома)

Предусловия (все СЕРВЕРНЫЕ, ре-валидация в обработчике, порядок от ранней причины):

1. авторизован — есть сессия (`accountId`);
2. своя машина — `owned[carIndex]` по `playerId`, `dbId != -1`;
3. ещё не припаркована — `!isParked(dbId)`;
4. сидит **ЗА РУЛЁМ этой машины** — `getVehicle(playerId)` == её живой экземпляр И
   `getSeat(playerId) == 0` (гарантирует, что машина в мире и её позиция известна);
5. свой дом — `HouseService::houseOf(to_string(accountId))` != nullptr;
6. ≤ `PARK_HOUSE_RADIUS = 30 м` — `glm::distance(carPos, house.entrance)`;
7. лимит парковки не достигнут — `countParkedByAccount(accountId) < house.parkingCap`
   (кап — дев-контент дома из `houses.json`; счёт учитывает личные + расшаренные;
   текущую машину ещё НЕ парковали — `isParked` дал false выше, в счёте её нет).

Действие (**ре-тег НА МЕСТЕ**, тот же `liveVehicleId`, БЕЗ destroy/create):
`spot = veh->getPosition()`, `angle = veh->getZAngle()`; a) `setOwner(*veh,
Owner::Parked, -1)` — серверный тег Player→Parked (под сидящим водителем не высаживает,
driver-gate только на входе); b) `setSpawnPosition(*veh, spot, angle)` — death-респавн
ядра вернёт машину сюда; c) `park(dbId, accountId, model, spot, angle, fuel,
liveVehicleId)` (память + INSERT, `family_id = NO_FAMILY`) — внутри связывает запись с
ТЕМ ЖЕ живым экземпляром (машину не создаём) и помечает её ВЫЗВАННОЙ владельцем, заняв
его слот вызова (см. «Жизненный цикл экземпляра»: пригнанная машина стоит здесь, пока
владелец в игре, и уходит из мира на его выходе); d) `PersonalVehicleService::detach(dbId)` — отвязать от сессионного трекинга
(`vehicleId` владения → -1). **Детач обязателен:** иначе `reset` на дисконнекте владельца
уничтожил бы припаркованную машину (см. «Ловушка reset» ниже). Игрок остаётся за рулём,
HP/позиция/состояние сохраняются.

### Убрать с парковки (лично/в-семье → гараж)

Только владелец МАШИНЫ (владение по `playerId`); `dbId` ре-валид; предусловие
`isParked(dbId)`. Живой экземпляр берём из parked-записи (`byDbId(dbId)->vehicleId` —
во владении `vehicleId` уже -1 после detach). Действие (**ре-тег НА МЕСТЕ**, тот же
`carId`, БЕЗ destroy): a) `setOwner(*veh, Owner::Player, playerId)` — тег Parked→Player
(снова личная владельца); b) `PersonalVehicleService::attach(dbId, carId)` — вернуть
машину в сессионный трекинг (обычный жизненный цикл: уничтожается на дисконнекте/смерти);
c) `unparkKeepInstance(dbId)` — снять запись + DELETE строки, живой экземпляр НЕ трогая.
Машина ОСТАЁТСЯ стоять на месте (не исчезает, не телепортируется), становится обычной
личной сессионной. Если машины в мире НЕТ (`veh == nullptr` — штатное «в гараже», пока
её не вызвали, и редкое окно внешнего destroy) — переносим
последний известный снимок `parked->fuel` записи в владение
(`PersonalVehicleService::setFuel`) ДО снятия записи (иначе следующий спавн через
центральную парковку взял бы устаревший `entry.fuel`, каким он был ДО парковки у дома),
затем снимаем только запись (`unparkKeepInstance`) — ре-тегать на месте нечего, машина
становится обычной личной и берётся на центральной парковке. Если была расшарена —
доступ семьи уходит вместе со снятием записи.

### Расшарить семье (лично у дома → семейный доступ)

Предусловия (порядок как раньше): нет семьи → не лидер семьи (`isOwner`) →
`dbId != -1` → **машина припаркована ЛИЧНО** (`parkedMode(dbId) == NO_FAMILY`;
`NOT_PARKED` «сначала припаркуйте у дома», иначе «уже расшарена»). Действие: `shareToFamily(dbId,
familyId)` = **только UPDATE `family_id`** + правка `m_byFamily`. Тот же экземпляр
`Owner::Parked`; driver-gate начинает пускать членов на СЛЕДУЮЩЕЙ посадке. Уведомление
онлайн-членам семьи. **НЕ трогает `VehicleService`** (машину не пересоздаём).

## `/family` → «Транспорт семьи» (вызов) и `/car` → «Вернуть от семьи» (снять шеринг)

`/family` → «Транспорт семьи» — TABLIST список расшаренных семье машин
(`parkedOfFamily(familyId)`), виден любому члену семьи (общий builder строки —
`ParkedVehicleRow::build`, единый с `/car` «Мои машины», см. `Docs/CarMenu.md`).
**Выбор строки = ВЫЗОВ машины** к её месту парковки (кнопка «Вызвать»): расшаренная
машина в мире тоже не ждёт, и это ЕДИНСТВЕННЫЙ вход в вызов для члена семьи — в `/car`
показывается только СВОЁ владение. Тексты ответа — общие с `/car` (`ParkedVehicleCall`,
см. «Вызвать машину» выше); после вызова список переоткрывается с новым статусом
машины. Гейт — серверный: `call` → `hasAccess` по `accountId` из сессии (член ТОЙ
семьи, которой машина расшарена). Снимок `dbId` строк уходит в обработчик КОПИЕЙ —
порядок `parkedOfFamily` (обход multimap) между показом и кликом не гарантирован, а
индекс из диалога должен указывать на ту машину, которую игрок видел в строке.

Снять доступ отсюда НЕЛЬЗЯ — пункта «Забрать» в `/family` нет.

**Снять шеринг может ТОЛЬКО владелец машины** — `/car` → «Мои машины» → машина →
«Вернуть от семьи» (динамический лейбл 5-го пункта вместо «Передать семье», когда
машина уже расшарена; см. `Docs/CarMenu.md`). Гейт — владелец МАШИНЫ (НЕ владелец
семьи — машина всегда личная, шарится только своя припаркованная), действие —
`unshareFromFamily(dbId)`: серверная ре-проверка владельца + `parkedMode(dbId) ==
familyId`; уведомление онлайн-членам семьи.

`unshareFromFamily` — ТОЛЬКО `UPDATE family_id -> NO_FAMILY`: машина не уничтожается
и не отправляется на парковку, ОСТАЁТСЯ припаркованной ЛИЧНО у дома владельца (тот
же экземпляр, лишь замок сужается до владельца).

## Массовый unpark при передаче/выселении дома (`/home`)

`HomeMenuSystem` (передача владения и выселение — полностью в `Docs/HomeMenu.md`)
убирает ВСЕ припаркованные записи прежнего владельца одним проходом
`parkedByAccount(accountId)` → `unpark(dbId)` для каждой. `unpark` (НЕ
`unparkKeepInstance`) — экземпляр УНИЧТОЖАЕТСЯ, строка `parked_vehicle` целиком
УДАЛЯЕТСЯ (см. «Персист» выше). Это осознанный выбор для передачи/выселения:

- **Судьба шеринга.** Расшаренная семье запись при `unpark` удаляется целиком —
  доступ семьи пропадает вместе с парковкой (машина не «наследуется» новым
  владельцем дома и не остаётся ничьей полу-семейной сущностью). Владелец машины
  (аккаунт в `personal_vehicle`) не меняется — после unpark машина просто
  перестаёт существовать как экземпляр; строка `personal_vehicle` НЕ трогается
  (собственность самой машины — отдельный вопрос от парковки).
- **Судьба топлива.** Строка `parked_vehicle` (где жил персистентный `fuel`)
  действительно удаляется целиком, но сама машина (`personal_vehicle`) НЕ
  уничтожается как владение — она остаётся в собственности того же аккаунта
  (парковка ≠ владение) и будет заново заспавнена через центральную парковку
  ПОЗЖЕ, взяв `fuel` из записи `personal_vehicle`. Если этот `fuel` не обновить
  перед `unpark`, он остаётся замороженным на значении ДО последней парковки у
  дома — ровно та же дыра, против которой штатный `CarMenuSystem::unpark`
  переносит `parked->fuel`/`getFuel` в `PersonalVehicleService::setFuel` перед
  снятием с парковки. `HomeMenuSystem::unparkAllOf` делает ТО ЖЕ САМОЕ перед
  КАЖДЫМ `unpark(dbId)`: если экземпляр ещё жив — `VehicleService::getFuel`,
  иначе последний снимок `parked->fuel` — и пишет его в `PersonalVehicleService`
  владельца (`setFuel` по найденному `ownedIndex`). Без этого шага возможен и
  дюп (заездил бак почти в ноль, передал дом — получил обратно полный бак при
  следующем вызове машины с парковки), и обратная потеря (бак был почти полон
  на момент парковки у дома, но заморожен низким).
- **Гейт занятости — предусловие ДО unpark-all.** `HomeMenuSystem` вызывает
  массовый `unpark` только после проверки, что НИ ОДНА из припаркованных машин
  владельца не занята водителем (`byVehicleId(vehicleId)->vehicleId` +
  `VehicleService::getDriver(vehicleId) != -1`) — иначе `unpark` уничтожил бы
  машину под сидящим игроком. При отказе передача/выселение не выполняются
  целиком (частичного unpark-a нет — либо все машины свободны и убираются, либо
  ни одна).

## Центральная парковка (`ParkingSystem`)

Припаркованную у дома машину (личную ИЛИ расшаренную) центральная парковка НЕ спавнит
(`isParked(dbId)` → отказ «Эта машина припаркована у дома — вызвать её или найти можно
через /car»): у неё своё место у дома, куда её подаёт ВЫЗОВ. Спавн отсюда либо вернул
бы дубль (машина уже вызвана), либо увёл бы её с точки.

Статус в списках `/car` и парковки — единый словарь по `parkedMode(dbId)`:

| `parkedMode` | статус | смысл |
|--------------|--------|-------|
| припаркована (любая), `vehicleId==-1` | `в гараже` | припаркована, но НЕ вызвана — в мире машины нет (вызвать: `/car`, у члена семьи — `/family`) |
| `NO_FAMILY`, у точки | `у дома`  | припаркована лично, вызвана, стоит у своей точки (≤ `HOME_SPOT_RADIUS = 30 м` по XY) |
| `familyId`, у точки | `у дома семьи` | припаркована и расшарена, вызвана, стоит у точки (дом лидера семьи — шарит только лидер свою припаркованную) |
| припаркована (любая), вдали | `брошена` | пустой экземпляр дальше радиуса — уехали и вышли («Респавн» в `/car` вернёт на точку) |
| `NOT_PARKED`, `vehicleId==-1` | `на парковке` | не припаркована, не в мире (взять на центральной парковке) |
| `NOT_PARKED`, `vehicleId!=-1` | `вызвана`  | не припаркована, в мире (центральная парковка) |

Факт «стоит ли у точки» — `ParkedVehicleService::isAwayFromSpot(dbId)`: живой
экземпляр записи дальше `HOME_SPOT_RADIUS` от `spot` по XY (Z игнорируется —
рельеф; квадрат дистанции, без sqrt). Позиция машины клиент-авторитетна — факт
влияет ТОЛЬКО на отображаемое слово, прав не даёт. Дистанционная логика ЕДИНА
для личной и расшаренной (решение владельца: как у личного транспорта) — пустая
расшаренная вне точки тоже «брошена»; КТО в занятой — показывает оверлей водителя.

В `/car` → «Мои машины» поверх словаря действует **оверлей водителя**: если за
рулём живого экземпляра кто-то сидит — колонка показывает `{ник}[{playerId}]`
вместо статуса (см. `Docs/CarMenu.md`). Список центральной парковки оверлей не
показывает.

**Сентинел `ParkedVehicleService::NOT_PARKED = -2`, НЕ `-1`:**
`FamilyService::NO_FAMILY` тоже равен `-1`, и пока `parkedMode` возвращал `-1` для
«не припаркована», это значение совпадало с «припаркована лично» — все
непри­паркованные машины показывались «у дома», а гейт «Передать семье» отказывал
уже припаркованной («сначала припаркуйте»). Сравнивать режим размещения с голым
`-1` НЕЛЬЗЯ — только с именованными константами `NOT_PARKED` / `NO_FAMILY`.

## Доступ за руль (серверный гейт)

`VehicleService::subscribeDriverGate` — общая инфраструктура ВЕТО на посадку за руль
(Core даёт крючок, политику решает бизнес). Зовётся из `bindOccupant`, когда игрок стал
водителем (`seat == 0`); наблюдатель возвращает `false` → сервис высаживает игрока
`removeFromVehicle(true)`. Пассажиров НЕ гейтит.

`ParkedVehicleSystem::onDriverGate` → `ParkedVehicleService::canDrive(vehicleId,
accountId)` (по ЗАПИСИ `Parked`, НЕ по тегу):

- не-`Parked` машина → `true` (гейт не наш);
- **личная** (`familyId == NO_FAMILY`) → только владелец: `accountId != NO_ACCOUNT &&
  accountId == ownerAccountId`;
- **расшаренная** → член семьи: `familyByAccount(accountId) == familyId` (работает и
  оффлайн-владельца).

`accountId` — СЕРВЕРНЫЙ (из сессии), не от клиента. Текст отказа различает личную
(`Машина заперта владельцем`) и семейную (`За руль этой машины пускают только членов
семьи`). O(1).

## Респавн на своей точке при уничтожении

По ВЫЗОВУ экземпляр создаётся `spawnInstance` →
`create(..., spot, angle, ..., Owner::Parked, -1)` (**spawn-позиция = spot**; ни старт
сервера, ни вход владельца сами машину не заводят); при парковке НА МЕСТЕ
`setSpawnPosition(*veh, spot, angle)`
задаёт ту же spawn-точку СУЩЕСТВУЮЩЕЙ машине (через `get/setSpawnData` — прочие поля
spawnData сохранены, машина не пересоздаётся). При смерти машина НЕ уничтожается:
`PersonalVehicleSystem::onVehicleDied` трогает ТОЛЬКО `Owner::Player` (и вообще видит
лишь серверно-САНКЦИОНИРОВАННЫЕ смерти). Значит `vehicleId` живого экземпляра
сохраняется, и машина вернётся ТЕМ ЖЕ pool-id на `spawnData.position = spot`:
несанкционированную смерть (грифер) `VehicleService` сам гасит отложенным респавном
(~100 мс, контракт смерти — `Docs/Vehicles.md`), санкционированную переспавнит ядро
через `game.vehicle_respawn_time` (≈ 10 с). На death-респавне `subscribeDestroyed` НЕ
дёргается — `vehicleId` в `Parked` НЕ обнуляется (отличаем «died→respawn» от
«destroy»). Штатный destroy живого экземпляра — ТОЛЬКО через `unpark` (пул-очистка,
чистит и БД); ре-тег парковки/снятия (`park`/`unparkKeepInstance`) экземпляр НЕ
трогает.

### Уведомление владельцу о несанкционированной смерти

`ParkedVehicleSystem::onUnsanctionedDeath` подписан на
`VehicleService::subscribeUnsanctionedDeath` (контракт крючка и антиспам-гейт —
`Docs/Vehicles.md`, «Уведомление владельца»). Владелец резолвится по ЗАПИСИ
`Parked` (`byVehicleId(vehicleId) -> ownerAccountId`), НЕ по тегу
`VehicleService` (`ownerId` тега `Owner::Parked` служебный/`-1`) —
`PlayerSessionService::playerByAccount(ownerAccountId)` (тот же резолв, что
`accountOnline`), offline → `-1` → уведомление молча пропускаем. **Уведомляем
ТОЛЬКО владельца машины, не членов семьи** — расшаренная стоит на своей обычной
точке у дома, для остальных членов ничего не изменилось.

Текст (`INFO_COLOUR`, `{имя}` — `VehicleModelNames::displayName`):

| `returnsInPlace` | Текст |
|----|----|
| `true` (первая смерть волны, вернулась НА МЕСТЕ) | `Вашу машину {имя} пытались уничтожить, но она цела` |
| `false` (повторная смерть окна, вернёт ядровой таймер к дому) | `Вашу машину {имя} пытались уничтожить. Она эвакуирована к вашему дому` |

## Ловушка reset (почему detach на парковке обязателен)

`PersonalVehicleService::reset` (конец сессии владельца) уничтожает ВСЕ машины владения
с `vehicleId != -1`. Парковка НА МЕСТЕ не зовёт `destroy` → `onWorldVehicleDestroyed`
припаркованной НЕ приходит → её `vehicleId` во владении сам НЕ обнуляется. Без явного
`detach(dbId)` (обнуляет `vehicleId` владения без destroy) припаркованная машина имела
бы во владении `vehicleId == carId`, и `reset` на дисконнекте владельца её `destroy` —
машина исчезла бы раньше, чем деспавн вызова успел снять её бак в запись (потеря
персистентного топлива), а порядок двух систем на конце сессии стал бы значимым.
Поэтому `parkHere` делает `detach` ЯВНО; после него живой экземпляр держит
только `ParkedVehicleService`, а `reset` его не трогает (во владении `vehicleId == -1`).
При снятии `attach(dbId, carId)` возвращает машину под сессионный трекинг — снятая с
парковки уничтожается на следующем дисконнекте как обычная личная (это норм).

## Крайние случаи

- **(a) Роспуск семьи** (`/family` Disband / последний член ушёл):
  `onFamilyDissolved(familyId)` — по `parkedOfFamily` СНЯТЬ ШЕРИНГ (`UPDATE family_id ->
  NO_FAMILY`) у каждой машины. Машины ОСТАЮТСЯ припаркованы ЛИЧНО (экземпляры не
  уничтожаются). **Выход владельца** (`leaveFamily`, семья жива):
  `onOwnerLeftFamily(accountId)` — снять шеринг только у РАСШАРЕННЫХ машин этого аккаунта
  (`familyId != NO_FAMILY`), личные не трогать. `FamilySystem` дёргает это вокруг
  `disbandFamily`/`leaveFamily` (захват `familyId`/`accountId` ДО вызова). Оба пути
  идут через `unshareFromFamily`, который нотифицирует `subscribeReconcile`, но
  экземпляр от смены `family_id` НЕ появляется и НЕ исчезает (желаемое считается по
  `calledBy`): машина, вызванная членом семьи, остаётся в мире до выхода ТОГО, кто её
  вызвал, а вызвать её дальше сможет только владелец.
- **(b) Потеря дома после парковки** — существующая парковка НЕ ломается (`spot`
  абсолютный, в БД); только НОВАЯ парковка/шеринг требуют дом.
- **(c) Битая расшаренность на старте** (нет семьи): в `loadParked` — **деградация в
  личную** (`familyId = NO_FAMILY`), машина НЕ теряется (лог Warning). Осиротевший
  `parked_vehicle` без `personal_vehicle` возможен, но машина самодостаточна
  (`model`/`spot` в строке) — оставляем.
- **(d) Загрузка `parked_vehicle` после семей** — `FamilyService::subscribeLoaded`
  (one-shot).

**ИНВАРИАНТ:** сейчас `leave`/`disband` зовутся только из двух диалогов `FamilySystem`
— оба покрыты снятием шеринга. Если появятся ИНЫЕ пути роспуска (авто-роспуск,
админ-команда), они осиротят `parked_vehicle` семейной ссылкой — тогда вынести
членство-наблюдатель в `FamilyService` (как `subscribeOwnershipLoaded` в
`HouseService`).

## Порядок загрузки (async после семей)

`parked_vehicle` грузится СТРОГО после семей (они нужны для гейта РАСШАРЕННЫХ; личные
семей не требуют). Обе загрузки async — `FamilyService::subscribeLoaded` (one-shot),
`ParkedVehicleSystem` в `initialize` подписывается, в колбэке грузит `parked_vehicle`
(`SELECT personal_vehicle_id, owner_account_id, model, x, y, z, angle, family_id`): для
каждой строки — нормализовать `family_id` (несуществующая семья → `NO_FAMILY`),
`loadParked` (регистрация записи в памяти) — и **НИКАКИХ спавнов: `reconcile` на старте
не зовётся вовсе**. `calledBy` в БД не хранится, после рестарта не вызвана ни одна
запись, у точек парковки не стоит ничего — машины появляются только по вызову (см.
«Жизненный цикл экземпляра»). Запись жива у обоих типов.

## Персист (`parked_vehicle`, write-through)

Схема — сводный `Sql/schema_all.sql` (применяется ВРУЧНУЮ, заменяет
`family_vehicle.sql` — тот НЕ применять). `personal_vehicle_id` — PK (одна парковка
на машину); `owner_account_id`; `model`; `x/y/z/angle` (`DOUBLE`); `family_id`
(`INT NOT NULL DEFAULT -1`: `-1 == NO_FAMILY` — ближе к in-memory модели, без
nullable-биндинга); `fuel` (`DOUBLE NOT NULL DEFAULT 100` — персистентный остаток
бака, см. «Персист топлива» ниже). Индексы по `owner_account_id` и `family_id`.

- **park** — INSERT (`throwQuery`, `family_id = -1`, `fuel` = РЕАЛЬНЫЙ снимок на
  момент парковки, не дефолт схемы); экземпляр НЕ создаётся (ре-тег живого через
  `setOwner`/`setSpawnPosition` делает `CarMenuSystem`), а запись связывается с ним
  (`setVehicleId`) и метится вызванной владельцем — `calledBy` в БД не пишется;
- **unparkKeepInstance** — DELETE по `personal_vehicle_id`, живой экземпляр НЕ трогает
  (снятие НА МЕСТЕ, fuel остаётся в живом экземпляре — источник правды переходит
  обратно к `PersonalVehicleService` через `attach`); **unpark** — то же + `destroy`
  экземпляра (пул-очистка, не вызывается нигде в коде сейчас — задел);
- **shareToFamily / unshareFromFamily / крайние случаи** — UPDATE `family_id`; в конце
  каждого пути смены `family_id` сервис зовёт `notifyReconcile(dbId)` →
  `subscribeReconcile` (система приводит экземпляр к желаемому — спавн/деспавн, с
  восстановлением персистентного `fuel` в `spawnInstance`);
- **UPDATE fuel** (`ParkedVehicleSystem::persistFuel`) — write-through по
  `personal_vehicle_id`, вызывается из `despawnInstance` (перед деспавном) и
  `onVehicleRespawned` (после восстановления снимка несанкционированной смерти).

### Персист топлива — закрывает «бесплатный эвакуатор с заправкой»

Задача (`Docs/GameDesign/Economy.md`, «Задел на будущий сток: топливо и заправки»):
без персиста цикл «докатал бак → владелец вышел (машина деспавнится) → вернулся
(машина спавнится с полным баком)» или «докатал бак → детонация → машина возвращается
целой respawn'ом с полным баком» давал бы бесплатный полный бак — самый удобный обход
будущего стока топлива (припаркованная машина уже стоит у дома, эвакуатор не нужен).

**Снимается** (в память `ParkedVehicleService::setFuel` + БД `persistFuel`):

- **`despawnInstance`** (выход владельца оффлайн — личная запись деспавнится) —
  `getFuel` живого экземпляра ДО `destroy`, иначе после уничтожения `getFuel` вернул
  бы `0` для несуществующей машины;
- **`onUnsanctionedDeath`** (контракт смерти — `Docs/Vehicles.md`) — снимок в
  `m_pendingFuelRestore[vehicleId]` НЕЗАВИСИМО от того, онлайн ли владелец (топливо
  не должно теряться из-за того, что уведомлять некого); машина ещё валидна
  (died-lock диспатча смерти), физический возврат случится позже;
- **`ParkedVehicleService::respawnHome(dbId)`** (`/car` → «Мои машины» → «Респавн» —
  см. `Docs/CarMenu.md`) — снимает `getFuel(vehicleId)` ПРЯМО В ЗАПИСЬ
  (`it->second.fuel = ...`, БЕЗ отдельной map — запись и так держит персистентный
  снимок) СРАЗУ ПЕРЕД `VehicleService::respawn(*vehicle)`.

**Восстанавливается** (`VehicleService::setFuel` поверх дефолтного полного бака от
`create`/`onVehicleRespawn`):

- **`spawnInstance`** (вход владельца/старт сервера для расшаренных) — `rec->fuel`
  применяется СРАЗУ после `create`;
- **`onVehicleRespawned`** (подписка `VehicleService::subscribeRespawned`, зовётся
  ПОСЛЕ того, как `onVehicleRespawn` уже поставил полный бак) — ранний выход, если
  запись `Parked` для `vehicleId` не найдена (не-Parked машина — не наш путь).
  Иначе ОДИН путь на ДВА источника снимка, приоритет по свежести:
  1. если для `vehicleId` есть снимок в `m_pendingFuelRestore` — берёт его.
     `onUnsanctionedDeath` кладёт снимок туда ДО ЛЮБОГО возврата, ПОКРЫВАЯ ВСЕ
     несанкционированные смерти (и «на месте», и повторную на ядровом
     death-таймере) — эта ветка отрабатывает для них ВСЕГДА;
  2. иначе берёт `parked->fuel` САМОЙ записи — единственный путь БЕЗ снимка в мапе:
     явный «Респавн» из `/car` (`respawnHome` кладёт снимок ПРЯМО В ЗАПИСЬ ДО
     вызова `respawn`, в `m_pendingFuelRestore` он не попадает).
  Затем — в память записи (`ParkedVehicleService::setFuel`), И в живой экземпляр
  (`VehicleService::setFuel`), И персистит (`persistFuel`).

Снимок `m_pendingFuelRestore` чистится И на успешном восстановлении, И в
`subscribeDestroyed` (машина исчезла НЕ через респавн) — `vehicleId` пула
переиспользуем, без очистки следующая СОВСЕМ ДРУГАЯ машина на этом id ложно
унаследовала бы чужой fuel на своём первом респавне.

Мусор из БД (`fuel` NaN/отрицательный/сверх `FUEL_CAPACITY`) клампится при загрузке
(`clampParkedFuel` в сервисе): не-конечное → `FUEL_CAPACITY` (полный бак безопаснее
пустого — не подозрительная выгода, а страховка от битых данных), отрицательное →
`0`, избыток → `FUEL_CAPACITY`.

**SQL-миграция** — одна колонка `fuel` в существующую таблицу (см. текст миграции в
отчёте задачи); жизненный цикл экземпляра по-прежнему целиком в памяти, менять
пришлось только схему хранения топлива.

## Константы баланса

| Константа           | Значение | Смысл                                            |
|---------------------|----------|--------------------------------------------------|
| `PARK_HOUSE_RADIUS` | 30 м    | радиус у своего дома, в котором можно припарковать (двор дома; в текст игроку не выводится) |
| `HOME_SPOT_RADIUS`  | 30 м    | радиус «стоит у дома» от точки `spot` (статус `у дома` vs `брошена`, `isAwayFromSpot`). НЕЗАВИСИМ от `PARK_HOUSE_RADIUS` — значения совпадают случайно, тюнятся врозь (где разрешено ПАРКОВАТЬ ≠ насколько далеко «уехал») |
| `House.parkingCap`  | `[1, 10]`, дефолт 1 | кап ПРИПАРКОВАННЫХ у дома машин владельца (дев-контент дома, `houses.json`); enforce в `parkHere` через `countParkedByAccount` |
| лимит владения      | число личных машин (`MAX_PERSONAL_VEHICLES = 2`) | парковка/шеринг не создают машину — переносят/открывают существующую |
| death-респавн       | `game.vehicle_respawn_time` (≈ 10 с) | возврат машины на точку у дома после САНКЦИОНИРОВАННОЙ смерти делает ЯДРО (не форсим); несанкционированную возвращает `VehicleService` (~100 мс) |

Парковка и шеринг **бесплатны и обратимы**, машину не создают — инфляции парка нет.
**Вызов и пул:** припаркованная машина занимает pool-слот ТОЛЬКО пока вызвана (и
вызвавший в игре) — не постоянно, как раньше. Сток пула теперь ограничен числом
игроков ОНЛАЙН (у каждого не больше одной вызванной машины на слот вызова), а не числом
домовладельцев в базе; после рестарта сервера слоты чисты.

## Три правила

- **Читер-абуз:** парковать/убирать — ТОЛЬКО владелец МАШИНЫ (`owned` по `playerId` +
  `dbId`), парковать — ТОЛЬКО за рулём этой машины (`getVehicle == экземпляр &&
  getSeat == 0`), ТОЛЬКО ≤30 м от СВОЕГО дома (`houseOf` по серверному `accountId`).
  Расшарить — ТОЛЬКО владелец СЕМЬИ (`isOwner`), над УЖЕ припаркованной лично
  машиной; забрать (`unshareFromFamily`, из `/family` ИЛИ `/car` → «Вернуть от
  семьи») — ТОЛЬКО владелец МАШИНЫ (не обязан быть владельцем семьи — своя машина).
  `dbId` ре-валидируется; нельзя парковать чужую/уже-припаркованную,
  расшарить не-припаркованную/уже-расшаренную. **`respawnHome`** — ТОЛЬКО по `dbId`
  из ре-валидированного `owned(playerId)` игрока (владелец); отказывает, если за
  рулём есть водитель (`getDriver != -1`, читает СЕРВЕРНЫЙ факт, не клиент) — машину
  нельзя выдернуть из-под сидящего (владельца или члена семьи). Не-владелец/не-член
  НЕ водит — серверный
  `canDrive` по записи `Parked` (`accountId` из сессии, `familyByAccount` из
  `FamilyService`, не по клиенту). `listItem` диалогов идентифицирует ДЕЙСТВИЕ, машину —
  захваченный `carIndex`/`dbId` с ре-валидацией. `family_id`/`accountId` серверные.
  **Лимит парковки у дома — серверный:** кап (`House.parkingCap`, дев-контент
  `houses.json`, валидируется в `[1, 10]`) и счёт (`countParkedByAccount` по серверной
  памяти) — клиент не влияет; обойти капом ЧУЖОГО дома нельзя (`houseOf` по СВОЕМУ
  `accountId`, не по позиции). **Вызов** — ТОЛЬКО по `dbId` из ре-валидированного списка
  (`owned(playerId)` в `/car`, снимок `parkedOfFamily` в `/family`) и ТОЛЬКО с серверным
  `accountId` из сессии: `hasAccess` (то же правило, что `canDrive`) не пускает ни
  чужого, ни члена ДРУГОЙ семьи; расстояние не гейт — машина появляется на СВОЕЙ точке,
  игрока к ней не телепортирует, так что «вызвать машину себе под нос» невозможно by
  design. Слот вызова один — спамом вызовов пул не набить (новый вызов снимает
  прошлый); `calledBy` не приходит от клиента и в БД не хранится.
  **Жизненный цикл экземпляра — целиком СЕРВЕРНЫЙ:** спавн/деспавн решает запись
  (`calledBy`) + факт онлайна вызвавшего (`playerByAccount` из сессии), клиент на него
  НЕ влияет. Деспавн НЕ трогает запись/БД (не открывает окна дюпа/потери владения).
- **Краш/UB:** bounds `playerId`/`vehicleId`/`dbId` везде; null-гард
  `IPlayer`/`IVehicle`/`House*`/`Family*`; ре-валидация предусловий в колбэках (игрок
  мог выйти/пересесть/уехать/сменить семью); битые ссылки `parked_vehicle` на старте —
  деградация в личную (не пропуск); гейт — событийный (`bindOccupant`), не per-tick;
  `unpark`: `eraseFromMemory` ДО `destroyInstance` (destroyed-наблюдатель no-op);
  крайние случаи берут снимок `parkedOfFamily`/`parkedByAccount` ДО `unshareFromFamily`
  (он правит `m_byFamily`). **Жизненный цикл экземпляра:** `spawnInstance`/
  `despawnInstance` идемпотентны (гейт по `vehicleId`), нет двойного спавна/утечки;
  `despawnInstance` — `setVehicleId(-1)` ДО `destroy` (ре-энтрантный `onVehicleDestroyed`
  → no-op); `onCallerOffline`/`releaseOtherCalls` перебирают КОПИЮ `calledByAccount`
  (`clearCall` правит записи, но в `m_byDbId` не вставляет и не удаляет — перебор не
  инвалидируется); `clearCall` идемпотентен; `accountOnline` отсекает `NO_ACCOUNT` до
  резолва; event-driven (вызов/сессия/переход), НЕ per-tick. **Ре-тег парковки/снятия:** тег/spawn меняем на ЖИВОМ
  валидном `veh` (перепроверен `get(carId)` в снятии — экземпляр мог пропасть внешним
  destroy → ветка `unparkKeepInstance` без разыменования); ре-тег синхронен в одном
  тике диалог-колбэка (внешний дисконнект между шагами невозможен, main однопоточный),
  `destroy` не зовётся → нет ре-энтрантного `onVehicleDestroyed`, правящего индексы под
  нами; `setSpawnPosition` режет NaN/Inf (не осядет в spawnData); `detach`/`attach`
  bounds-safe по `dbId`. `onUnsanctionedDeath` НЕ трогает пул машин (контракт
  подписки `subscribeUnsanctionedDeath` — только чтение записи `Parked` +
  сообщение); `playerByAccount` возвращает `-1` для оффлайна ДО обращения к
  `m_core.getPlayers()`, второй null-гард на случай гонки дисконнекта в тот же
  тик. **`respawnHome`:** null-гард `m_vehicleService`; `get(vehicleId)` перепроверен
  (экземпляр мог пропасть между показом меню и кликом → `NoInstance` без
  разыменования); `getDriver` — серверный факт занятости, не клиентский ввод;
  снимок `fuel` пишется В ЗАПИСЬ ДО `respawn()` (эффект синхронный, гонки нет —
  `respawn()` вызывает `onVehicleRespawn`/`subscribeRespawned` СИНХРОННО в этом же
  вызове, main однопоточный). **Персист fuel:** `setFuel`/`clampParkedFuel` режут NaN/Inf/отрицательное/сверх
  `CAP`; `m_pendingFuelRestore` чистится И на успешном восстановлении
  (`onVehicleRespawned`), И на `subscribeDestroyed` — иначе `vehicleId`
  (переиспользуемый pool-слот) ложно передал бы чужой fuel следующей, СОВСЕМ ДРУГОЙ
  машине на этом id; `onVehicleRespawned` перепроверяет существование записи `Parked`
  для `vehicleId` (могла исчезнуть между смертью и возвратом) прежде чем писать.
- **Перф:** спавн — по клику «Вызвать» (одна машина), деспавн — на выходе вызвавшего
  (ноль или одна запись); `calledByAccount` — линейный проход по записям парковок, на
  холодном пути (вызов/выход), не в тике; гейт доступа — O(1)
  (`m_byVehicleId` hash + `familyByAccount` hash); запросы `/car`/парковки/`/family`,
  переходы, крайние случаи (N UPDATE) — холодные (по команде/диалогу);
  `countParkedByAccount` (enforce капа) — `multimap.count`, O(записей владельца ≤ кап),
  на холодном пути парковки (клик в `/car`), без аллокации. `onUnsanctionedDeath` —
  РЕДКОЕ событие (антиспам на стороне `VehicleService`), `byVehicleId`/
  `playerByAccount` O(1) + один `sendClientMessage`. `persistFuel`/восстановление
  fuel — те же редкие события (деспавн/респавн), O(1) + один `UPDATE`. PER-TICK НЕТ.
