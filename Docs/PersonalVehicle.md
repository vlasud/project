# Личный транспорт

Личные машины игрока — бизнес-фича (НЕ Core). Код:
`Src/Services/PersonalVehicleService`, `Src/Systems/PersonalVehicleSystem`.

Разделение **«владею vs вызываю»** (как дом: владение аккаунтом vs физический
вход): покупка регистрирует ВЛАДЕНИЕ (модель машины), машину НЕ спавнит. Спавн —
отдельный шаг через **парковку** (см. `Docs/Parking.md`): на пикапе парковки игрок
выбирает свою машину, и она появляется на свободной точке.

**Право владения ПЕРСИСТИТСЯ** в БД (`personal_vehicle`, по `account_id`,
write-through — как членство фракций `faction_member`): какими моделями владеет
аккаунт, переживает перезаход. Грузится на старте сессии (`load`). А вот
машина-**СУЩНОСТЬ** в мире — **СЕССИОННАЯ**: спавнится/уничтожается через парковку,
её позиция/состояние НЕ сохраняются (`vehicleId` обнуляется на `reset` в конце
сессии). Покупка пока — ДЕБАГ-команда `/pvbuy <id модели>`; реальная покупка-UI
(салон/диалог) — будущее.

## Источник правды

`PersonalVehicleService` — источник правды о ВЛАДЕНИИ личными машинами игрока
ОНЛАЙН (какие МОДЕЛИ принадлежат аккаунту). Машины ядра — у `VehicleService` (Core,
источник правды о машинах); этот сервис ведёт, какими моделями владеет игрок и
какой экземпляр (id) сейчас заспавнен.

- **Запись владения** — `struct OwnedVehicle { int model; int vehicleId = -1; }`:
  модель машины + id её текущего заспавненного экземпляра в `VehicleService`
  (`-1` — не заспавнена сейчас; владение всё равно живёт).
- **Владение per-player** — `std::array<std::vector<OwnedVehicle>, MAX_PLAYERS>
  m_owned`. `vector` ради будущего расширения лимита; при
  `MAX_PERSONAL_VEHICLES == 1` держит 0..1 элемент.
- **Гейт загрузки** — `std::array<bool, MAX_PLAYERS> m_loaded`: пока зеркало
  владения из БД не легло в `m_owned`, `buy` отдаёт `NotLoaded`. Иначе «купил до
  загрузки» обошёл бы лимит (купленная модель + загруженная позже). Ставится
  `load`, снимается `reset` (как `m_ownershipLoaded` в `HouseSystem`).
- **Зависимость — `VehicleService`.** Реестр сервисов создаёт всё дефолтным
  конструктором, поэтому зависимость проставляется методом `bind(VehicleService&)`
  (как `VehicleService::bind`), который зовёт `PersonalVehicleSystem` в своём
  конструкторе. Машины создаются/уничтожаются ТОЛЬКО через `VehicleService::create`
  / `destroy` — сырой SDK сервис не трогает.

## Покупка (`buy`) — только ВЛАДЕНИЕ, write-through

`BuyResult buy(playerId, accountId, model)` — регистрирует владение (память +
запись в БД), машину НЕ создаёт:

1. bounds `playerId`, наличие связанного `VehicleService`, `accountId != NO_ACCOUNT`
   (иначе `Unavailable`). `accountId` — СЕРВЕРНЫЙ (из сессии), не от клиента;
2. **гейт загрузки** — `!m_loaded[playerId]` → `NotLoaded` (зеркало владения из БД
   ещё не пришло; покупка отложена, чтобы не обойти лимит гонкой);
3. **лимит** — `owned.size() >= MAX_PERSONAL_VEHICLES` → `LimitReached`
   (форсится ЗДЕСЬ, серверная политика, не на клиенте);
4. **модель** — вне диапазона машин SA `[400, 611]`, а также train carriage
   `569`/`570` → `InvalidModel` (валидируется ДО SDK). Train carriage ядро
   ОТКАЗЫВАЕТСЯ уничтожать (`release()` для `isTrainCarriage` делает early-return),
   поэтому такая машина не исчезла бы на `reset` — это утечка машин; её покупка
   запрещена;
5. иначе в `m_owned[playerId]` добавляется `OwnedVehicle{model, -1}` (память
   оптимистична), и **write-through INSERT** `personal_vehicle(account_id, model)`
   через `DatabaseManager::throwQuery` (ошибка БД лишь логируется в `errorCallback`,
   как `FactionService::setMember`) → `Ok`. Никакого `create`/спавна на покупке.

`PoolFull` из `buy` **недостижим** (`buy` не спавнит) — ветка кода/сообщения
оставлена для совместимости enum.

`const std::vector<OwnedVehicle> &owned(int)` — список владений (для диалога
парковки; bounds-safe — пустой статический вектор для невалидного id).
`int count(int)` / `bool atLimit(int)` — bounds-safe запросы числа владений и
лимита.

## Спавн (`spawn`) — на точке парковки

`SpawnResult spawn(playerId, ownedIndex, position, angle, colour1, colour2,
out = nullptr)` — зовёт `ParkingSystem` с СЕРВЕРНЫМИ координатами точки:

1. bounds `playerId` и `ownedIndex`; нет `VehicleService` → `Unavailable`,
   плохой индекс → `BadIndex`;
2. если экземпляр уже заспавнен (`vehicleId != -1`) — **ПЕРЕ-СПАВН**: старый
   `VehicleService::destroy`, затем новый. `destroy` СИНХРОННО триггерит
   `onWorldVehicleDestroyed` по старому id, который обнулит `vehicleId` записи (запись
   НЕ удаляется), а мы ниже пишем новый id;
3. `VehicleService::create(model, pos, angle, c1, c2, Owner::Player, playerId)`;
   `nullptr` (пул машин ядра исчерпан) → `PoolFull` (старую при пере-спавне уже
   уничтожили, `vehicleId` остался `-1`, владение цело);
4. иначе `vehicleId` записи = id новой машины, `*out` получает указатель → `Ok`.

`int currentVehicle(playerId, ownedIndex)` — id текущего экземпляра (или `-1`); для
исключения СВОЕЙ машины при поиске свободной точки (пере-спавн на её же точку).

`ownerId = playerId` — серверный СЕССИОННЫЙ ключ владельца (тег `Owner::Player`).
При переходе к персисту ключом станет `accountId`.

## Уничтожение машины — владение остаётся

`onWorldVehicleDestroyed(vehicleId)` (заменяет прежний `untrack`): машину уничтожил
кто-то ещё (взрыв/`destroy`/респаун-цикл — через `VehicleService::subscribeDestroyed`)
— находим запись владения с этим `vehicleId` (по всем игрокам) и **обнуляем её
`vehicleId`** (НЕ удаляем запись). Владение сохраняется; машину спавнят заново через
парковку. БЕЗ `destroy` (машина уже уничтожается). Линейно по игрокам (мало; редкое
событие).

## Смерть машины — личная ПРОПАДАЕТ (не висит вреком)

Личная машина **НЕ возвращается** после уничтожения. Важно: `respawnDelay = Seconds(-1)`
(в `VehicleService::create`) гасит только респавн ПО ПРОСТОЮ; death-респавн ядра идёт по
ГЛОБАЛЬНОМУ конфигу `game.vehicle_respawn_time`. Возврата нет НЕ из-за `respawnDelay`, а
потому, что при **реальном уничтожении** (смерть, HP → 0) машина немедленно УДАЛЯЕТСЯ —
в том же тике, до срабатывания глобального death-таймера.

`VehicleService::onVehicleDeath` после фиксации `health = 0` оповещает
**died-наблюдателей** (`subscribeDied`). `PersonalVehicleSystem::onVehicleDied`:
если машина ЛИЧНАЯ (`getOwner == Owner::Player`) → `VehicleService::destroy`. Это
синхронно (или отложенно под pool-lock) запускает `subscribeDestroyed →
onWorldVehicleDestroyed`, который **обнуляет `vehicleId`** записи (владение
сохраняется). Спавн заново — только вручную через парковку.

Чужие owner-теги (`Faction`/`Work`) `onVehicleDied` НЕ трогает — их политика смерти
своя.

**Урон личную машину не взрывает** — она глохнет как все (анти-грифинг в
`VehicleService`: HP клампится на `STALL_HEALTH = 300`, двигатель глушится; стол НЕ
ослаблен). Поэтому реальная смерть — редкий случай: мгновенный локальный подрыв
взрывчаткой вплотную, который сервер не успевает перехватить клампом.

### Ре-энтрантность `died → destroy → destroyed`

`destroy()` зовётся ИЗ died-наблюдателя, исполняемого ВНУТРИ события смерти
(`onVehicleDeath`). В этот момент запись держит ДВА лока: `MarkedPoolIterator` цикла
`onTick` (lock на текущую запись на всё тело итерации) и `ScopedPoolReleaseLock` диспатча
смерти — итого `refs = 2`. `IVehiclesComponent::release` → `storage.release(index, false)`:
при `refs > 0` лишь помечает `deleted_`, фактического `remove` нет. Когда
`ScopedPoolReleaseLock` снимается, `refs → 1` (lock итератора ещё держится) — машина
ОСТАЁТСЯ ЖИВОЙ, поэтому код ядра ПОСЛЕ диспатча смерти безопасно её разыменовывает
(нет UAF даже при `vehicle_respawn_time = 0`). Фактический `remove` (с
`onPoolEntryDestroyed → onVehicleDestroyed`) происходит на `++iter`
(`MarkedPoolIterator::operator++` = `++iter; unlock(); lock()`), когда `refs → 0` и ядро
к этой машине уже не обращается. UAF и двойного `destroy` нет.

## Жизненный цикл владения (через `PlayerSessionService`)

`PersonalVehicleSystem` подписывается на сессию (account-data — по конвенции, НЕ
через raw disconnect):

- **`subscribeStart`** → `loadOwnership(player, session)`:
  `DatabaseManager::selectQuery` — `SELECT model FROM personal_vehicle WHERE
  account_id = :acc` (запрос И вычитка в `std::vector<int>` на воркере). В колбэке
  **serial-guard** (`session.serial` совпадает с текущим) + живой игрок
  (`getPlayers().get`) → `PersonalVehicleService::load(playerId, models)`. Машину
  НЕ спавним — игрок берёт её на парковке.
- **`subscribeEnd`** → `reset(playerId)`: уничтожить заспавненные машины +
  очистить ПАМЯТЬ владения + снять `loaded`. **БД НЕ трогаем** — право владения
  остаётся в `personal_vehicle` и подтянется на следующем старте.

`load(playerId, models)` кладёт модели как `OwnedVehicle{model, -1}` (БЕЗ записи в
БД — это зеркало), отфильтровав по `validModel` и лимиту, и ставит `loaded = true`
(покупка разблокирована). Bounds-safe.

`reset(playerId)` уничтожает ВСЕ заспавненные машины игрока (`vehicleId != -1`)
через `VehicleService::destroy`, **очищает** `m_owned[playerId]` и снимает
`loaded`. **БД не трогает.** Bounds-safe.

### Ре-энтрантность `spawn`/`reset` ↔ `onWorldVehicleDestroyed`

`destroy(id)` СИНХРОННО триггерит наблюдателя `subscribeDestroyed` →
`onWorldVehicleDestroyed(id)`, который ищет id ПО ВСЕМ игрокам и изменяет `m_owned`.

- **`spawn` (пере-спавн):** запись владения НЕ удаляется при уничтожении — лишь
  обнуляется её `vehicleId`. Индекс/ссылка на запись стабильны; после `create`
  пишем новый id поверх. Дополнительно ставим `vehicleId = -1` сразу после `destroy`
  как страховку, если наблюдатель не сработал.
- **`reset`:** собирает id заспавненных экземпляров ЛОКАЛЬНО и **очищает владение
  игрока ДО вызовов `destroy`**. Тогда наблюдатель во время `destroy` видит уже
  пустой слот этого игрока (no-op), а мы итерируемся по своей копии id.

## Дебаг-команда `/pvbuy`

`DEVELOPER_LEVEL`, `HelpCategory::Hidden`. Один параметр — id модели (`Param::Int`).
Берёт `accountId` из `PlayerSessionService` (нет сессии/`NO_ACCOUNT` → сообщение
«Сначала войдите в аккаунт», return) и зовёт `buy(playerId, accountId, model)` —
регистрирует владение с write-through в БД, БЕЗ спавна. Спавн машины — только через
парковку.

Сообщения (через `u()`):

| Результат      | Цвет           | Текст                                                     |
|----------------|----------------|-----------------------------------------------------------|
| `Ok`           | `INFO_COLOUR`  | `Личная машина куплена (модель {model}). Возьмите её на парковке` |
| `LimitReached` | `ERROR_COLOUR` | `У вас уже есть личная машина (лимит {MAX})`              |
| `InvalidModel` | `ERROR_COLOUR` | `Недопустимая модель (400-611, кроме train carriage 569/570)` |
| `NotLoaded`    | `ERROR_COLOUR` | `Личный транспорт ещё загружается, попробуйте через момент` |
| `PoolFull`     | `ERROR_COLOUR` | `Пул машин переполнен` (недостижимо: `buy` не спавнит)    |
| `Unavailable`  | `ERROR_COLOUR` | `Покупка сейчас недоступна`                               |

Нет сессии (до логина) → отдельное сообщение «Сначала войдите в аккаунт» (до вызова
`buy`).

`INFO_COLOUR {120,220,255}`, `ERROR_COLOUR {255,90,90}` — игровые цвета (как в
`FamilySystem`/`HouseSystem`).

## Персист

**Право владения — в БД** (`personal_vehicle`, схема `Sql/personal_vehicle.sql`,
применяется ВРУЧНУЮ, как `factions.sql`/`house_owner.sql`). Персистится ТОЛЬКО
«какими моделями владеет аккаунт»:

- `account_id` — владелец (НЕ уникален: задел под лимит > 1 в будущем, только
  индекс `idx_account`);
- `model` — модель машины;
- `id` — суррогатный `AUTO_INCREMENT`: задел под будущее per-vehicle (продажа/тюнинг
  конкретной машины); в in-memory владении пока не используется.

Жизненный цикл:

- **load** — на старте сессии `SELECT model WHERE account_id` → в память
  `OwnedVehicle{model, -1}` (зеркало, без записи в БД);
- **write-through** — `buy` INSERT'ит строку сразу (память оптимистична);
- **reset** — на конце сессии чистит ТОЛЬКО память + машины; БД остаётся.

Машина-**СУЩНОСТЬ** в мире НЕ персистится: позиция/состояние/тот факт, что машина
сейчас заспавнена, сессионны — её подают заново через парковку. `ownerId = playerId`
(серверный сессионный ключ) у самой машины остаётся; ключ владения в БД —
`accountId`.

## Константы баланса

| Константа                | Значение | Смысл                                            |
|--------------------------|----------|--------------------------------------------------|
| `MAX_PERSONAL_VEHICLES`  | 1        | дефолтный лимит личных машин на игрока (расширяемо) |
| диапазон моделей         | 400..611 | валидные модели машин SA, кроме train carriage 569/570 (валидируется до SDK) |

`MAX_PERSONAL_VEHICLES` расширяемо позже (премиум/перки) — тогда лимит станет
пер-игроковым; `m_owned` уже `vector` ради этого.

## Будущее

- покупка через игровой UI (салон/диалог) вместо дебаг-команды `/pvbuy`;
- per-vehicle персист по `id` строки (продажа/тюнинг конкретной машины);
- пер-игроковый лимит (премиум/перки) с лимитом > 1 на `account_id`;
- цена/износ вызова машины (тогда пере-спавн целой машины через парковку обнулит
  любой ремонт-сток — учесть при вводе экономики).

## Три правила

- **Читер-абуз:** команда `/pvbuy` целиком за `DEVELOPER_LEVEL`. `accountId` берётся
  из `PlayerSessionService` (СЕРВЕРНЫЙ, не от клиента) — владение пишется в БД по
  нему. Политика серверная и на вырост: **лимит** `MAX_PERSONAL_VEHICLES` форсится В
  СЕРВИСЕ ПРОТИВ загруженного из БД числа; **гейт `m_loaded`** не даёт купить до
  прихода зеркала из БД (иначе купленная + загруженная модель обошли бы лимит
  гонкой); **модель** валидируется по диапазону `[400, 611]` (исключая train carriage
  `569`/`570`) ДО SDK (и при покупке, и при загрузке из БД); `ownerId = playerId` —
  серверный (не клиентский); машина создаётся ТОЛЬКО через `VehicleService::create`
  (тег `Owner::Player`). Спавн — только через парковку с СЕРВЕРНЫМИ координатами
  точек; индекс владения и сам владелец (`playerId`) серверные — игрок спавнит
  только свои машины и не задаёт произвольную позицию.
- **Краш/UB:** bounds `playerId`/`ownedIndex` во всех методах; **загрузка владения —
  async-`selectQuery` с serial-guard + null-гард игрока** (колбэк мог прийти, когда в
  слоте другая сессия / игрок вышел); БД-`errorCallback` логирует, не роняет; `create
  == nullptr` обработан (`PoolFull`, без разыменования); `subscribeDestroyed →
  onWorldVehicleDestroyed` — нет висячих id / двойного `destroy`; **запись владения
  НЕ удаляется при уничтожении** → индекс/ссылка стабильны при ре-энтрантном
  наблюдателе; **`reset` копирует id + чистит слот ДО `destroy`**; нет
  разыменования невалидного игрока/машины. **`died → destroy → destroyed`
  безопасна**: машина залочена в пуле во время события смерти, SDK откладывает
  `release` до unlock (`MarkedPoolStorage`/`MarkedPoolIterator`) — диспатч смерти не
  рвётся, нет UAF; `getOwner` по валидному id; наблюдатели итерируются без
  инвалидации (push в `subscribe*` только на старте).
- **Перф:** загрузка владения — ОДИН async-`selectQuery` на старте сессии (не
  per-tick); `buy` INSERT — ХОЛОДНЫЙ путь (по команде), push в `vector` O(1) +
  одна запись в БД; `spawn` — O(1) + один `create`/`destroy`; `reset` —
  O(owned) = O(1) при лимите 1; `onWorldVehicleDestroyed` — редкое событие,
  O(игроки×owned) (мало); `onVehicleDied` — РЕДКОЕ событие смерти,
  `getOwner` O(1) + один `destroy`. PER-TICK НЕТ.
