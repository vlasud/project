# Личный транспорт

Личные машины игрока — бизнес-фича (НЕ Core). Код:
`Src/Services/PersonalVehicleService`, `Src/Systems/PersonalVehicleSystem`.

Разделение **«владею vs вызываю»** (как дом: владение аккаунтом vs физический
вход): покупка регистрирует ВЛАДЕНИЕ (модель машины), машину НЕ спавнит. Спавн —
отдельный шаг через **парковку** (см. `Docs/Parking.md`): на пикапе парковки игрок
выбирает свою машину, и она появляется на свободной точке.

**Право владения ПЕРСИСТИТСЯ** в БД (`personal_vehicle`, по `account_id`,
write-through — как членство фракций `faction_member`): какими моделями владеет
аккаунт, переживает перезаход. Грузится на старте сессии (`load`). А вот
машина-**СУЩНОСТЬ** в мире — **СЕССИОННАЯ**: спавнится/уничтожается через парковку,
её позиция/состояние НЕ сохраняются (`vehicleId` обнуляется на `reset` в конце
сессии). Покупка пока — ДЕБАГ-команда `/pvbuy <id модели>`; реальная покупка-UI
(салон/диалог) — будущее.

## Источник правды

`PersonalVehicleService` — источник правды о ВЛАДЕНИИ личными машинами игрока
ОНЛАЙН (какие МОДЕЛИ принадлежат аккаунту). Машины ядра — у `VehicleService` (Core,
источник правды о машинах); этот сервис ведёт, какими моделями владеет игрок и
какой экземпляр (id) сейчас заспавнен.

- **Запись владения** — `struct OwnedVehicle { int model; int vehicleId = -1;
  long long dbId = -1; }`: модель машины + id её текущего заспавненного экземпляра в
  `VehicleService` (`-1` — не заспавнена сейчас; владение всё равно живёт) + `dbId` —
  стабильный ключ строки `personal_vehicle` (id), по которому **парковка у дома**
  ссылается на КОНКРЕТНУЮ машину (см. `Docs/ParkedVehicles.md`). `dbId = -1` — ещё не
  присвоен (окно между `buy` и приходом `LAST_INSERT_ID`); такую машину нельзя
  парковать/расшаривать, пока id не лёг.
- **Владение per-player** — `std::array<std::vector<OwnedVehicle>, MAX_PLAYERS>
  m_owned`. `vector` ради будущего расширения лимита; при
  `MAX_PERSONAL_VEHICLES == 2` держит 0..2 элемента.
- **Гейт загрузки** — `std::array<bool, MAX_PLAYERS> m_loaded`: пока зеркало
  владения из БД не легло в `m_owned`, `buy` отдаёт `NotLoaded`. Иначе «купил до
  загрузки» обошёл бы лимит (купленная модель + загруженная позже). Ставится
  `load`, снимается `reset` (как `m_ownershipLoaded` в `HouseSystem`).
- **Зависимость — `VehicleService`.** Реестр сервисов создаёт всё дефолтным
  конструктором, поэтому зависимость проставляется методом `bind(VehicleService&)`
  (как `VehicleService::bind`), который зовёт `PersonalVehicleSystem` в своём
  конструкторе. Машины создаются/уничтожаются ТОЛЬКО через `VehicleService::create`
  / `destroy` — сырой SDK сервис не трогает.

## Покупка (`buy`) — только ВЛАДЕНИЕ в памяти; write-through делает система

`BuyResult buy(playerId, accountId, model, outIndex = nullptr)` — регистрирует
владение в ПАМЯТИ, машину НЕ создаёт и **в БД НЕ пишет сам**:

1. bounds `playerId`, наличие связанного `VehicleService`, `accountId != NO_ACCOUNT`
   (иначе `Unavailable`). `accountId` — СЕРВЕРНЫЙ (из сессии), не от клиента;
2. **гейт загрузки** — `!m_loaded[playerId]` → `NotLoaded` (зеркало владения из БД
   ещё не пришло; покупка отложена, чтобы не обойти лимит гонкой);
3. **лимит** — `owned.size() >= MAX_PERSONAL_VEHICLES` → `LimitReached`
   (форсится ЗДЕСЬ, серверная политика, не на клиенте);
4. **модель** — вне диапазона машин SA `[400, 611]`, а также train carriage
   `569`/`570` → `InvalidModel` (валидируется ДО SDK). Train carriage ядро
   ОТКАЗЫВАЕТСЯ уничтожать (`release()` для `isTrainCarriage` делает early-return),
   поэтому такая машина не исчезла бы на `reset` — это утечка машин; её покупка
   запрещена;
5. иначе в `m_owned[playerId]` добавляется `OwnedVehicle{model, -1, -1}` (память
   оптимистична), `*outIndex` = индекс добавленной записи → `Ok`.

**Write-through с `dbId`** — раньше INSERT делал сам сервис (`throwQuery`, id не
возвращал). Теперь INSERT переехал в систему (`PersonalVehicleSystem::persistPurchase`),
т.к. нужен id строки для парковки у дома: `INSERT ...; SELECT LAST_INSERT_ID()` одной
сессией того же воркер-таска через `selectQuery<long long>` (`LAST_INSERT_ID`
connection-scoped, пул держит одну сессию на поток — id корректен), в success-колбэке
**serial-guard + живой игрок** → `setDbId(playerId, ownedIndex, dbId)`. Сбой INSERT →
`dbId` остаётся `-1` (парковка/шеринг недоступны до перезахода); ошибка БД логируется.

`PoolFull` из `buy` **недостижим** (`buy` не спавнит) — ветка кода/сообщения
оставлена для совместимости enum.

`const std::vector<OwnedVehicle> &owned(int)` — список владений (для диалога
парковки; bounds-safe — пустой статический вектор для невалидного id).
`int count(int)` / `bool atLimit(int)` — bounds-safe запросы числа владений и
лимита.

## Спавн (`spawn`) — на точке парковки

`SpawnResult spawn(playerId, ownedIndex, position, angle, colour1, colour2,
out = nullptr)` — зовёт `ParkingSystem` с СЕРВЕРНЫМИ координатами точки:

1. bounds `playerId` и `ownedIndex`; нет `VehicleService` → `Unavailable`,
   плохой индекс → `BadIndex`;
2. если экземпляр уже заспавнен (`vehicleId != -1`) — **ПЕРЕ-СПАВН**: старый
   `VehicleService::destroy`, затем новый. `destroy` СИНХРОННО триггерит
   `onWorldVehicleDestroyed` по старому id, который обнулит `vehicleId` записи (запись
   НЕ удаляется), а мы ниже пишем новый id;
3. `VehicleService::create(model, pos, angle, c1, c2, Owner::Player, playerId)`;
   `nullptr` (пул машин ядра исчерпан) → `PoolFull` (старую при пере-спавне уже
   уничтожили, `vehicleId` остался `-1`, владение цело);
4. иначе `vehicleId` записи = id новой машины, `*out` получает указатель → `Ok`.

`int currentVehicle(playerId, ownedIndex)` — id текущего экземпляра (или `-1`); для
исключения СВОЕЙ машины при поиске свободной точки (пере-спавн на её же точку).

`ownerId = playerId` — серверный СЕССИОННЫЙ ключ владельца (тег `Owner::Player`).
При переходе к персисту ключом станет `accountId`.

## Уничтожение машины — владение остаётся

`onWorldVehicleDestroyed(vehicleId)` (заменяет прежний `untrack`): машину уничтожил
кто-то ещё (взрыв/`destroy`/респаун-цикл — через `VehicleService::subscribeDestroyed`)
— находим запись владения с этим `vehicleId` (по всем игрокам) и **обнуляем её
`vehicleId`** (НЕ удаляем запись). Владение сохраняется; машину спавнят заново через
парковку. БЕЗ `destroy` (машина уже уничтожается). Линейно по игрокам (мало; редкое
событие).

**`/car` → «Мои машины» → «Респавн» для «вызванной»** (сессионная в мире, не
припаркована у дома — см. `Docs/CarMenu.md`) идёт ЧЕРЕЗ ЭТОТ ЖЕ путь: `CarMenuSystem`
зовёт `VehicleService::destroy(vehicleId)` напрямую (без нового API в этом сервисе) —
`onWorldVehicleDestroyed` сработает штатно и обнулит `vehicleId` владения, машина
уходит «на парковку» (статус списков), владение цело. Гейт «занята водителем» (`getDriver != -1`) стоит в
`CarMenuSystem` ДО вызова `destroy` — под сидящим игроком (владельцем) машину не
выдёргивают.

## Парковка НА МЕСТЕ — detach/attach (машина временно уходит из трекинга)

`bool detach(long long dbId)` / `bool attach(long long dbId, int vehicleId)` — публичные
методы для `CarMenuSystem` (ре-тег парковки НА МЕСТЕ, см. `Docs/ParkedVehicles.md`).
Поиск владения по `dbId` (уникален глобально → линейный проход по всем игрокам, как
`onWorldVehicleDestroyed`; холодный путь). Bounds-safe (`dbId < 0` → `false`).

- **`detach(dbId)`** — обнулить `vehicleId` владения (`→ -1`) БЕЗ `destroy`. При парковке
  НА МЕСТЕ живой экземпляр остаётся (его держит `ParkedVehicleService`), но выходит из
  сессионного трекинга Personal: **`reset` на дисконнекте владельца его больше НЕ
  уничтожит** (иначе припаркованная машина гибла бы — «доступна оффлайн» сломалась бы).
  Ре-тег `destroy` не зовёт → `onWorldVehicleDestroyed` не приходит → `vehicleId` сам не
  обнуляется, поэтому `detach` делается ЯВНО. Идемпотентно.
- **`attach(dbId, vehicleId)`** — вернуть живой экземпляр под сессионный трекинг (снятие
  с парковки): машина снова обычная личная сессионная (уничтожается на
  дисконнекте/смерти, как до парковки).

Пока машина припаркована, во владении `vehicleId == -1` — Personal сам по себе её
экземпляра не видит, а `/car`/парковка берут live id из
`ParkedVehicleService::byDbId(dbId)->vehicleId` (иначе показали бы «на парковке»,
хотя машина стоит у дома).

**Непересечение с деспавном припаркованных.** На конце сессии владельца `reset`
уничтожает ТОЛЬКО сессионные Personal-экземпляры (`vehicleId != -1`), а
`ParkedVehicleSystem::onOwnerOffline` — Parked-экземпляры личных припаркованных (их
`vehicleId` лежит в записи `Parked`, во владении он `-1` после `detach`). Наборы
`vehicleId` НЕ пересекаются; порядок между `PersonalVehicleSystem` и
`ParkedVehicleSystem` на конце сессии некритичен, двойного `destroy` одного id нет.

## Смерть машины — политика только на САНКЦИОНИРОВАННУЮ смерть

**died-наблюдатели (`subscribeDied`) получают ТОЛЬКО серверно-санкционированную
смерть** (`VehicleService::explode()`, флаг `serverKilled` — контракт смерти:
`Docs/Vehicles.md`). Несанкционированную смерть (клиентская детонация пустой,
фейковый репорт `Health<=0`) `VehicleService` гасит сам: died-политика НЕ
применяется, машина возвращается ЦЕЛОЙ на свою spawn-точку отложенным серверным
респавном; нарушение репортеру НЕ пишется — честную детонацию (расстрел
брошенной, утопление) по серверным фактам не отличить от фейка. **Грифер не
может «сжечь» личную машину**: владелец не теряет ни экземпляр в мире, ни
владение — прежний вектор «читер гоняет владельца на парковку бесконечно»
закрыт.

При САНКЦИОНИРОВАННОЙ смерти личная машина ПРОПАДАЕТ (не висит вреком и НЕ
возвращается). Важно: `respawnDelay = Seconds(-1)` (в `VehicleService::create`)
гасит только респавн ПО ПРОСТОЮ; death-респавн ядра идёт по ГЛОБАЛЬНОМУ конфигу
`game.vehicle_respawn_time`. Возврата нет НЕ из-за `respawnDelay`, а потому, что
машина немедленно УДАЛЯЕТСЯ — в том же тике, до срабатывания глобального
death-таймера.

`VehicleService::onVehicleDeath` после фиксации `health = 0` (и только при
`serverKilled`) оповещает **died-наблюдателей**. `PersonalVehicleSystem::onVehicleDied`:
если машина ЛИЧНАЯ (`getOwner == Owner::Player`) → `VehicleService::destroy`. Это
синхронно (или отложенно под pool-lock) запускает `subscribeDestroyed →
onWorldVehicleDestroyed`, который **обнуляет `vehicleId`** записи (владение
сохраняется). Спавн заново — только вручную через парковку.

Чужие owner-теги (`Faction`/`Work`) `onVehicleDied` НЕ трогает — их политика смерти
своя.

### Уведомление владельцу о несанкционированной смерти

`PersonalVehicleSystem::onUnsanctionedDeath` подписан на
`VehicleService::subscribeUnsanctionedDeath` (контракт крючка и антиспам-гейт —
`Docs/Vehicles.md`, «Уведомление владельца»). Только `Owner::Player`
(чужие теги — не наши); `ownerId` тега — `playerId` (сессионный ключ), напрямую
`m_core.getPlayers().get(ownerId)` (владение сессионное — машина существует
только пока владелец online, `reset` на конце сессии её уничтожает, так что
валидный тег уже означает «этот же игрок online»; null-проверка — страховка от
гонки колбэка/дисконнекта в тот же тик). Оффлайн-владелец (в этой ветке
недостижимо, но на всякий случай защищено) — молча, без сообщения.

Текст (`INFO_COLOUR`, `{имя}` — `VehicleModelNames::displayName`):

| `returnsInPlace` | Текст |
|----|----|
| `true` (первая смерть волны, вернулась НА МЕСТЕ) | `Вашу машину {имя} пытались уничтожить, но она цела` |
| `false` (повторная смерть окна, вернёт ядровой таймер на парковку) | `Вашу машину {имя} пытались уничтожить. Она эвакуирована на парковку` |

**Урон, который сервер видит, личную машину не взрывает** — она глохнет как все
(анти-грифинг в `VehicleService`: HP клампится на `STALL_HEALTH = 300`, двигатель
глушится; стол НЕ ослаблен; тот же кламп тушит кейс «пассажир без водителя» —
`secondTick`/`douseUnoccupiedFire`). По-настоящему ПУСТУЮ сервер не видит: её
клиент может детонировать локально (расстрел, утопление), но это
несанкционированная смерть — машина вернётся целой (см. выше), владелец ничего
не теряет.

### Ре-энтрантность `died → destroy → destroyed`

`destroy()` зовётся ИЗ died-наблюдателя, исполняемого ВНУТРИ события смерти
(`onVehicleDeath`). В этот момент запись держит ДВА лока: `MarkedPoolIterator` цикла
`onTick` (lock на текущую запись на всё тело итерации) и `ScopedPoolReleaseLock` диспатча
смерти — итого `refs = 2`. `IVehiclesComponent::release` → `storage.release(index, false)`:
при `refs > 0` лишь помечает `deleted_`, фактического `remove` нет. Когда
`ScopedPoolReleaseLock` снимается, `refs → 1` (lock итератора ещё держится) — машина
ОСТАЁТСЯ ЖИВОЙ, поэтому код ядра ПОСЛЕ диспатча смерти безопасно её разыменовывает
(нет UAF даже при `vehicle_respawn_time = 0`). Фактический `remove` (с
`onPoolEntryDestroyed → onVehicleDestroyed`) происходит на `++iter`
(`MarkedPoolIterator::operator++` = `++iter; unlock(); lock()`), когда `refs → 0` и ядро
к этой машине уже не обращается. UAF и двойного `destroy` нет.

## Жизненный цикл владения (через `PlayerSessionService`)

`PersonalVehicleSystem` подписывается на сессию (account-data — по конвенции, НЕ
через raw disconnect):

- **`subscribeStart`** → `loadOwnership(player, session)`:
  `DatabaseManager::selectQuery` — `SELECT id, model FROM personal_vehicle WHERE
  account_id = :acc` (запрос И вычитка в `std::vector<std::pair<long long,int>>` на
  воркере — `dbId` нужен парковке). В колбэке **serial-guard** (`session.serial`
  совпадает с текущим) + живой игрок (`getPlayers().get`) →
  `PersonalVehicleService::load(playerId, rows)`. Машину НЕ спавним — игрок берёт её
  на парковке.
- **`subscribeEnd`** → `reset(playerId)`: уничтожить заспавненные машины +
  очистить ПАМЯТЬ владения + снять `loaded`. **БД НЕ трогаем** — право владения
  остаётся в `personal_vehicle` и подтянется на следующем старте.

`load(playerId, rows)` кладёт пары `(dbId, model)` как `OwnedVehicle{model, -1, dbId}`
(БЕЗ записи в БД — это зеркало), отфильтровав по `validModel` и лимиту, и ставит
`loaded = true` (покупка разблокирована). Bounds-safe. `setDbId(playerId, ownedIndex,
dbId)` — проставить id из success-колбэка покупки (только если запись есть и её
`dbId == -1`, чтобы не перетереть уже присвоенный при reload).

`reset(playerId)` уничтожает ВСЕ заспавненные машины игрока (`vehicleId != -1`)
через `VehicleService::destroy`, **очищает** `m_owned[playerId]` и снимает
`loaded`. **БД не трогает.** Bounds-safe.

### Ре-энтрантность `spawn`/`reset` ↔ `onWorldVehicleDestroyed`

`destroy(id)` СИНХРОННО триггерит наблюдателя `subscribeDestroyed` →
`onWorldVehicleDestroyed(id)`, который ищет id ПО ВСЕМ игрокам и изменяет `m_owned`.

- **`spawn` (пере-спавн):** запись владения НЕ удаляется при уничтожении — лишь
  обнуляется её `vehicleId`. Индекс/ссылка на запись стабильны; после `create`
  пишем новый id поверх. Дополнительно ставим `vehicleId = -1` сразу после `destroy`
  как страховку, если наблюдатель не сработал.
- **`reset`:** собирает id заспавненных экземпляров ЛОКАЛЬНО и **очищает владение
  игрока ДО вызовов `destroy`**. Тогда наблюдатель во время `destroy` видит уже
  пустой слот этого игрока (no-op), а мы итерируемся по своей копии id.

## Дебаг-команда `/pvbuy`

`DEVELOPER_LEVEL`, `HelpCategory::Hidden`. Один параметр — id модели (`Param::Int`).
Берёт `accountId` из `PlayerSessionService` (нет сессии/`NO_ACCOUNT` → сообщение
«Сначала войдите в аккаунт», return) и зовёт `buy(playerId, accountId, model)` —
регистрирует владение с write-through в БД, БЕЗ спавна. Спавн машины — только через
парковку.

Сообщения (через `u()`):

| Результат      | Цвет           | Текст                                                     |
|----------------|----------------|-----------------------------------------------------------|
| `Ok`           | `INFO_COLOUR`  | `Личная машина куплена ({имя}). Возьмите её на парковке` — имя из `VehicleModelNames::displayName` (на `Ok` модель валидна; фолбэк `Модель {id}`) |
| `LimitReached` | `ERROR_COLOUR` | `У вас уже есть личная машина (лимит {MAX})`              |
| `InvalidModel` | `ERROR_COLOUR` | `Недопустимая модель (400-611, кроме train carriage 569/570)` |
| `NotLoaded`    | `ERROR_COLOUR` | `Личный транспорт ещё загружается, попробуйте через момент` |
| `PoolFull`     | `ERROR_COLOUR` | `Пул машин переполнен` (недостижимо: `buy` не спавнит)    |
| `Unavailable`  | `ERROR_COLOUR` | `Покупка сейчас недоступна`                               |

Нет сессии (до логина) → отдельное сообщение «Сначала войдите в аккаунт» (до вызова
`buy`).

`INFO_COLOUR {120,220,255}`, `ERROR_COLOUR {255,90,90}` — игровые цвета (как в
`FamilySystem`/`HouseSystem`).

## Персист

**Право владения — в БД** (`personal_vehicle`, схема — сводный
`Sql/schema_all.sql`, применяется ВРУЧНУЮ, как `factions.sql`/`house_owner.sql`).
Персистится «какими моделями владеет аккаунт» + остаток топлива:

- `account_id` — владелец (НЕ уникален: задел под лимит > 1 в будущем, только
  индекс `idx_account`);
- `model` — модель машины;
- `id` — суррогатный `AUTO_INCREMENT`: стабильный ключ строки, теперь используется как
  `dbId` в in-memory владении (ссылка парковки у дома на конкретную машину, см.
  `Docs/ParkedVehicles.md`);
- `fuel` — ПЕРСИСТЕНТНЫЙ остаток бака (`DOUBLE`, `0..VehicleService::FUEL_CAPACITY`,
  `DEFAULT 100` — полный бак), см. «Персист топлива» ниже.

Жизненный цикл:

- **load** — на старте сессии `SELECT id, model, fuel WHERE account_id` → в память
  `OwnedVehicle{model, -1, dbId, fuel}` (зеркало, без записи в БД; `fuel` клампится
  `0..CAP`, мусор — NaN/Inf → `-1` = «не сохранено», трактуется как полный бак);
- **write-through покупки** — INSERT'ит строку + `LAST_INSERT_ID` → `dbId` в память
  (делает `PersonalVehicleSystem::persistPurchase`, не сам сервис); `fuel` в строке —
  `DEFAULT 100` схемы (INSERT его не указывает — только что купленная машина ещё не
  существует физически, доливать нечего);
- **write-through fuel** — снимается перед КАЖДЫМ исчезновением заспавненного
  экземпляра (см. «Персист топлива» ниже) — `UPDATE personal_vehicle SET fuel = ?
  WHERE id = ?` (`PersonalVehicleSystem::persistFuel`);
- **reset** — на конце сессии чистит ТОЛЬКО память + машины; БД остаётся (fuel уже
  снят ДО reset, см. ниже).

Машина-**СУЩНОСТЬ** в мире НЕ персистится (кроме fuel): позиция/состояние/тот факт,
что машина сейчас заспавнена, сессионны — её подают заново через парковку.
`ownerId = playerId` (серверный сессионный ключ) у самой машины остаётся; ключ
владения в БД — `accountId`.

### Персист топлива — закрывает «бесплатный эвакуатор с заправкой»

Задача (`Docs/GameDesign/Economy.md`, «Задел на будущий сток: топливо и заправки»):
без персиста цикл «докатал бак почти до пустого → убрал машину на парковку (или её
детонировали) → вызвал заново» давал бы бесплатный полный бак — обход будущего
стока топлива дешевле и быстрее любой заправки. `OwnedVehicle::fuel` — ПЕРСИСТЕНТНЫЙ
снимок остатка (источник правды, пока `vehicleId == -1`; пока заспавнена — источник
правды `VehicleService::getFuel`, поле лишь снимок на момент последнего сохранения).

**Снимается (в память `setFuel` + БД `persistFuel`) перед каждым исчезновением
заспавненного экземпляра:**

- **пере-спавн на парковке** (`PersonalVehicleService::spawn`) — старый экземпляр
  снимается (`getFuel`) в `entry.fuel` ДО `destroy`, новый создаётся с полным баком
  от `create`, затем `entry.fuel >= 0` — `setFuel` перезаписывает его сохранённым
  остатком (память сервиса; персист в БД делает вызывающая система при следующем
  снятии — покупка/загрузка сама fuel не пишет за пределами `DEFAULT`);
- **конец сессии владельца** (`PersonalVehicleSystem::captureFuelBeforeReset`,
  зовётся ДО `PersonalVehicleService::reset`) — для КАЖДОЙ записи с `vehicleId != -1`
  снимает `getFuel` в память + `UPDATE fuel` по `dbId`; `reset` сам БД не трогает и
  безусловно уничтожает экземпляры — без снимка ДО него остаток был бы потерян;
- **санкционированная смерть** (`PersonalVehicleSystem::onVehicleDied`) — тот же
  снимок перед `destroy` (машина «сгорела», но владение остаётся — следующий спавн
  получит наездованный остаток, а не полный бак взорванной машины).

**Восстанавливается ПОСЛЕ несанкционированной смерти** (контракт смерти —
`Docs/Vehicles.md`): `onUnsanctionedDeath` снимает `getFuel` в
`m_pendingFuelRestore[vehicleId]` — машина ещё валидна, а физический возврат
случится позже (`respawnIfDead` ~100 мс либо ядровой death-таймер ~10 с), и
именно ОН (`onVehicleRespawn`) ставит машине дефолтный полный бак. Подписка
`VehicleService::subscribeRespawned` зовётся ПОСЛЕ этого дефолта — если для
`vehicleId` есть снимок, `onVehicleRespawned` перезаписывает его `setFuel` и
снимает запись из мапы. Снимок также снимается (без применения) в
`subscribeDestroyed` — `vehicleId` пула переиспользуем, и без очистки СЛЕДУЮЩАЯ,
совсем другая машина на этом id ложно унаследовала бы чужой fuel на своём первом
респавне.

Мусор из БД (`fuel` NaN/отрицательный/сверх `FUEL_CAPACITY`) клампится при
загрузке (`clampFuel` в сервисе): не-конечное → `-1` (трактуется как «нет
сохранённого», `spawn` оставит полный бак от `create`), отрицательное → `0`,
избыток → `FUEL_CAPACITY`.

## Константы баланса

| Константа                | Значение | Смысл                                            |
|--------------------------|----------|--------------------------------------------------|
| `MAX_PERSONAL_VEHICLES`  | 2        | дефолтный лимит личных машин на игрока (расширяемо) |
| диапазон моделей         | 400..611 | валидные модели машин SA, кроме train carriage 569/570 (валидируется до SDK) |

`MAX_PERSONAL_VEHICLES` расширяемо позже (премиум/перки) — тогда лимит станет
пер-игроковым; `m_owned` уже `vector` ради этого.

## Будущее

- покупка через игровой UI (салон/диалог) вместо дебаг-команды `/pvbuy`;
- per-vehicle персист по `id` строки (продажа/тюнинг конкретной машины) — fuel уже
  такой персист, HP/позиция/тюнинг пока нет;
- пер-игроковый лимит (премиум/перки) с лимитом > 1 на `account_id`;
- платные заправки (см. `Docs/GameDesign/Economy.md`) — персист fuel уже закрывает
  «бесплатный полный бак на респавне/перевызове», цену колонки можно вводить без
  доп. работы по стоку.

## Три правила

- **Читер-абуз:** команда `/pvbuy` целиком за `DEVELOPER_LEVEL`. `accountId` берётся
  из `PlayerSessionService` (СЕРВЕРНЫЙ, не от клиента) — владение пишется в БД по
  нему. Политика серверная и на вырост: **лимит** `MAX_PERSONAL_VEHICLES` форсится В
  СЕРВИСЕ ПРОТИВ загруженного из БД числа; **гейт `m_loaded`** не даёт купить до
  прихода зеркала из БД (иначе купленная + загруженная модель обошли бы лимит
  гонкой); **модель** валидируется по диапазону `[400, 611]` (исключая train carriage
  `569`/`570`) ДО SDK (и при покупке, и при загрузке из БД); `ownerId = playerId` —
  серверный (не клиентский); машина создаётся ТОЛЬКО через `VehicleService::create`
  (тег `Owner::Player`). Спавн — только через парковку с СЕРВЕРНЫМИ координатами
  точек; индекс владения и сам владелец (`playerId`) серверные — игрок спавнит
  только свои машины и не задаёт произвольную позицию.
- **Краш/UB:** bounds `playerId`/`ownedIndex` во всех методах; **загрузка владения —
  async-`selectQuery` с serial-guard + null-гард игрока** (колбэк мог прийти, когда в
  слоте другая сессия / игрок вышел); БД-`errorCallback` логирует, не роняет; `create
  == nullptr` обработан (`PoolFull`, без разыменования); `subscribeDestroyed →
  onWorldVehicleDestroyed` — нет висячих id / двойного `destroy`; **запись владения
  НЕ удаляется при уничтожении** → индекс/ссылка стабильны при ре-энтрантном
  наблюдателе; **`reset` копирует id + чистит слот ДО `destroy`**; нет
  разыменования невалидного игрока/машины. **`died → destroy → destroyed`
  безопасна**: машина залочена в пуле во время события смерти, SDK откладывает
  `release` до unlock (`MarkedPoolStorage`/`MarkedPoolIterator`) — диспатч смерти не
  рвётся, нет UAF; `getOwner` по валидному id; наблюдатели итерируются без
  инвалидации (push в `subscribe*` только на старте). `onUnsanctionedDeath` НЕ
  трогает пул машин (контракт подписки `subscribeUnsanctionedDeath` — только чтение
  стейта + сообщение); `m_core.getPlayers().get(ownerId)` может вернуть `nullptr`
  (оффлайн/гонка дисконнекта в тот же тик) — ранний return без разыменования.
  **Персист fuel:** `setFuel`/`clampFuel` режут NaN/Inf/отрицательное/сверх `CAP` (не
  оседает в снимке); `m_pendingFuelRestore` чистится И на успешном восстановлении
  (`onVehicleRespawned`), И на `subscribeDestroyed` — иначе `vehicleId` (переиспользуемый
  pool-слот) ложно передал бы чужой fuel следующей, СОВСЕМ ДРУГОЙ машине на этом id;
  `onVehicleRespawned` перепроверяет `getOwner == Owner::Player` (машину могли
  ре-тегнуть между смертью и возвратом) прежде чем писать `setFuel`.
- **Перф:** загрузка владения — ОДИН async-`selectQuery` на старте сессии (не
  per-tick); `buy` INSERT — ХОЛОДНЫЙ путь (по команде), push в `vector` O(1) +
  одна запись в БД; `spawn` — O(1) + один `create`/`destroy`; `reset` —
  O(owned) = O(1) при лимите 1; `onWorldVehicleDestroyed` — редкое событие,
  O(игроки×owned) (мало); `onVehicleDied` — РЕДКОЕ событие смерти,
  `getOwner` O(1) + один `destroy`; `onUnsanctionedDeath` — РЕДКОЕ событие (антиспам
  на стороне `VehicleService`), `getOwner`/`getOwnerId` O(1) + один
  `sendClientMessage`. `captureFuelBeforeReset` — O(owned) на конце сессии (не
  per-tick), один `UPDATE` в БД на заспавненную запись. `subscribeRespawned` —
  редкая точка (респавн), O(1) поиск в `m_pendingFuelRestore` (hash map).
  PER-TICK НЕТ.
