# Телефон (`/c`, `/acceptjob`)

Бизнес-фича (НЕ Core). Код:
- `Src/Services/PhoneService` — номера телефонов игроков онлайн, реестр служб и
  активные вызовы.
- `Src/Systems/PhoneSystem` — привод: команды, диалоги, рассылка вызова, звук,
  указатель на место вызова, выдача/загрузка номера.

## Меню `/c`

```
/c              ──► Скорая / Полиция / Такси / Ввести номер телефона
/c <номер>      ──► сразу набор номера (тот же пункт 4, без меню)
```

Заголовок диалога показывает собственный номер игрока — иначе узнать его негде.

Параметр у `/c` **необязательный**. Ради этого в `PlayerCommandService` появилась
поддержка необязательных параметров (`Param::optional`): раньше объявленный параметр
делал команду обязательной к аргументу, и голое `/c` отвечало бы подсказкой usage.
Необязательные параметры идут только хвостом и показываются в usage круглыми
скобками: `/c (номер телефона)`.

## Вызов службы

```
игрок выбирает службу ──► заказ с уникальным номером
   └─► всем, кто у службы СЕЙЧАС на смене:
       «Вызов скорой помощи номер 1042. Ivan_Ivanov[7]. Расстояние от вас 380 метров»
       + звук 17001
   работник: /acceptjob 1042
       └─► ему красный чекпоинт на место вызова
       └─► звонящему: «Ваш вызов 1042 принят: Ник[id] уже едет к вам»
```

Дистанция у каждого работника **своя** — от него до места вызова.

Позиция вызова — ПРИНЯТАЯ сервером (`PlayerLocationService`), а не заявление клиента:
по ней поедет работник.

Вызов забирает **первый** принявший: заказ удаляется, остальным `/acceptjob` ответит
«его уже приняли». Никого на смене нет — заказ не создаётся вовсе, звонящий узнаёт об
этом сразу и может позвонить снова.

### Кто получает вызов

Службы **регистрируются сами** (как в `JobDismissService`/`JobWalletService`): работа
приносит перечислитель «кто у меня на смене», а телефон про работы не знает. Новая
служба — одна строка регистрации.

| Служба | Кто получает | Кто регистрирует |
|---|---|---|
| Скорая | врачи в фазе `Working` (машина уже выехала) | `MedicJobSystem` |
| Такси | таксисты в фазе `Working` | `TaxiJobSystem` |
| Полиция | залогиненные члены фракций 2/3/4 (LS/SF/LV) | `PhoneSystem` (временно) |

Полицию регистрирует сам телефон: полицейских систем несколько, общей «работы» у них
пока нет. Когда полицию доработают, регистрация переедет к ней — телефон при этом не
меняется.

`/acceptjob` определяет службу принимающего по его же занятости: перебирает
зарегистрированные и ищет ту, где он числится на смене. Поэтому таксист не может
принять вызов скорой, даже зная номер.

### Жизнь заказа

- **Один живой заказ на игрока.** Иначе один звонящий завалил бы уведомлениями всех
  работников сразу.
- **`ORDER_TTL = 5 минут`.** Никто не принял — заказ протухает, и звонящий может
  позвать снова. Проверка ленивая (на создании и на приёме), отдельного таймера нет.
- Звонящий вышел из игры или погиб — его заказы снимаются: служба не должна ехать к
  трупу или к пустому месту.
- На приёме сверяется **серия сессии** звонящего: за время ожидания он мог выйти, а
  слот `playerId` — достаться другому игроку.

## Номера телефонов

Шестизначные (`100000..999999`), выдаются аккаунту один раз и живут в `player.phone`.

Загрузка и выдача идут **одним async-запросом на воркере**: номер обязан быть
уникальным, а гонять проверку уникальности по кругу с главного потока значило бы
несколько async-запросов подряд. Коллизия ловится по UNIQUE-индексу, номер
подбирается заново (до `PHONE_ISSUE_ATTEMPTS`). Запись условная
(`WHERE id = ? AND (phone IS NULL OR phone = 0)`) — параллельная выдача тому же
аккаунту не перетрёт уже выданный номер. В колбэке — serial-guard сессии.

Свой номер игрок узнаёт сообщением на входе и в заголовке `/c`.

## Звонки игрокам — заглушка

Пункт «Ввести номер телефона» и `/c <номер>` пока отвечают, что связь между игроками
появится позже. Номера при этом уже выданы и резолвятся
(`PhoneService::playerByPhone`) — когда разговор понадобится, инфраструктура готова.

## Миграция БД (выполняет ПОЛЬЗОВАТЕЛЬ)

Добавлено в `Sql/schema_all.sql` (идемпотентно). Применить на боевой БД:

```sql
ALTER TABLE `player` ADD COLUMN `phone` BIGINT NULL DEFAULT NULL;
ALTER TABLE `player` ADD UNIQUE INDEX `uk_player_phone` (`phone`);
```

Две тонкости, обе обязательные:

- **Колонка NULL-able, а не `NOT NULL DEFAULT 0`.** Под UNIQUE-индексом все старые
  строки получили бы одинаковый `0`, и индекс просто не создался бы. NULL под UNIQUE
  разрешён в любом количестве — это и есть «номер ещё не выдан». Код это понимает:
  `isNull()` читается как «номера нет», а выдача пишет
  `WHERE id = ? AND (phone IS NULL OR phone = 0)`.
- **Индекс UNIQUE обязателен** — на нём держится уникальность номера при выдаче.

MySQL **не поддерживает** `IF NOT EXISTS` в `ADD COLUMN`/`ADD INDEX` (это синтаксис
MariaDB). Повторный запуск ответит «Duplicate column/key name» — это значит «уже
сделано», а не поломку.

## Три правила

- **Читер-абуз:** место вызова — принятая сервером позиция звонящего, подделать
  «я рядом» нельзя. Один живой заказ на игрока плюс TTL закрывают спам уведомлениями.
  Принять вызов может только работник службы на смене, и служба определяется по
  серверной занятости, а не по тому, что игрок ввёл. Приём сверяет серию сессии
  звонящего (переиспользованный слот не считается тем же человеком). Номера выдаются
  случайно и защищены UNIQUE — перебором соседних не угадываются. Антифлуд команд —
  корневой, в `PlayerCommandService` (см. `Docs/CommandFlood.md`).
- **Краш-безопасность:** все входы сервиса bounds-safe по `playerId`; `IPlayer*` в
  колбэках диалогов и в рассылке берётся заново из пула и проверяется; заказ отдаётся
  копией и удаляется одним действием (двойной `/acceptjob` безвреден); конец сессии
  чистит и номер, и заказы слота; async-выдача номера — serial-guard, ошибки БД идут в
  лог и не роняют вход.
- **Перф:** событийно, только по командам игрока. Рассылка — проход по онлайну с
  ранним выходом (перечислитель службы сам отсекает не-работников), дистанция считается
  на месте без аллокаций. Реестр заказов — `unordered_map` на живые вызовы (единицы);
  чистка протухших ленивая, отдельного таймера нет. Номер телефона читается из
  ОЗУ-кэша, обращение к БД только на старте сессии.
