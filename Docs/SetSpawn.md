# Точка спавна `/setspawn`

Выбор «домашней точки» игрока: где он появляется при ВХОДЕ в игру (после
авторизации) и после СМЕРТИ. Бизнес-фича (НЕ Core). Код:
`Src/Services/SpawnChoiceService`, `Src/Systems/SpawnChoiceSystem`.

**Выбор главнее фракции.** Игрок ВСЕГДА может выбрать точку спавна — НЕЗАВИСИМО
от членства в организации. `SpawnChoiceSystem` — ЕДИНСТВЕННЫЙ писатель точки
спавна; `FactionSystem` её больше НЕ форсит (цвет/скин члена — по-прежнему зона
фракции, точка спавна — нет). Точка возврата прошлой сессии (`Docs/ReturnPoint.md`)
тоже НЕ писатель: она переносит игрока ТЕЛЕПОРТОМ после логин-спавна, `setSpawn`
не зовёт. Дефолт для ВСЕХ, кто не выбирал, — Порт. База
фракции достижима только через явный выбор пункта «Место работы». Источников на
выбор три:

1. **Порт** — фиксированная точка (порт Лос-Сантоса). Дефолт (нет записи в БД) И
   фолбэк (выбранный источник пропал/недоступен). Внутреннее имя не менялось:
   это по-прежнему `Choice::Station`/`choice=0` в БД (см. ниже) — игроку под этим
   же id теперь показывается «Порт», а не «ЖД вокзал».
2. **Дом** — точка ВЫХОДА дома, которым ВЛАДЕЕТ аккаунт игрока (фича домов уже
   есть): игрок появляется там же, куда его выбрасывает при выходе из дома, лицом
   ОТ двери. На пикап ВХОДА не спавним — его касание мгновенно затянуло бы игрока
   в интерьер (подробности ниже).
3. **Место работы** — точка спавна фракции игрока (база организации). Доступна
   только члену орга, у фракции которого задана точка спавна (`spawn.defined`).

Выбор хранит лишь НАМЕРЕНИЕ («хочу к дому» / «хочу на работу»), а конкретная
точка резолвится от СЕРВЕРНЫХ фактов в момент применения. Поэтому продажа дома
или выход из орга не оставляют битой точки — резолв на следующем применении даёт
валидную (фолбэк на порт). `/setspawn` НЕ телепортирует игрока сейчас —
настраивает только БУДУЩИЕ спавны.

## Устройство

- **`SpawnChoiceService`** (источник правды о выборе + write-through в БД). Бизнес,
  НЕ Core. Зеркалит паттерн `FactionService`:
  - `enum class Choice { Station=0, Home=1, Work=2 }`. Индексы совпадают с колонкой
    `choice` в БД — порядок менять нельзя. Неизвестное значение при загрузке
    нормализуется в `Station`.
    **Имя `Station`/`STATION_*` — исторический внутренний id, БД/enum не
    переименовывались.** Игроку в диалоге и сообщениях этот же выбор
    (`choice=0`) теперь называется «Порт» — координаты константы `STATION_*`
    правлены на портовые (см. таблицу ниже). Будущему разработчику: если в коде
    видно `Choice::Station` — это дефолтный/фолбэк-выбор, а показывается игроку
    он как «Порт», не «Вокзал».
  - `std::array<Choice, MAX_PLAYERS> m_choice` (онлайн), value-init → `Station(0)`
    для всех; bounds-гард `playerId` во всех методах.
  - `getChoice(playerId)` — текущий выбор (Station при невалидном id).
  - `setChoice(player, accountId, choice)` — память + **write-through** в БД
    (`REPLACE player_spawn` = `DELETE`+`INSERT` в ОДНОЙ ТРАНЗАКЦИИ). `accountId`
    приходит из сессии (НЕ от клиента); `NO_ACCOUNT`/невалидный id — no-op.
  - `load(playerId, choice)` — положить выбор в память на старте сессии (БЕЗ записи
    в БД — это загрузка).
  - `reset(playerId)` — сброс слота на конце сессии (`Station`).
- **`SpawnChoiceSystem`** (привод: команда/диалог, загрузка по сессии, резолв
  точки, перерезолв на смене членства). Зависимости: `PlayerSpawnService`,
  `FactionService`, `HouseService`, `PlayerSessionService`, `SpawnChoiceService`,
  `PlayerCommandService`, `PlayerDialogService`.

Спавн задаётся ТОЛЬКО через `PlayerSpawnService::setSpawn` — единственный источник
правды о спавне; команда не использует сырой телепорт.

## Команда `/setspawn` и диалог

Команда `setspawn` (открыта ВСЕМ, `HelpCategory::Misc`, описание для `/help`:
`выбрать точку появления: порт, дом или работа`). Гейта фракции НЕТ — диалог
открывается всегда.

Диалог `LIST`:

- **Заголовок:** `Точка спавна`.
- **Тело:** первая ЖЁЛТАЯ строка `{FFB400}` — невыбираемая подсказка о смысле
  (это настройка будущих спавнов, не телепорт сейчас), под ней три пункта:
  ```
  {FFB400}Где вы будете появляться при входе в игру и после смерти
  Порт
  Дом
  Место работы
  ```
- **Кнопки:** слева `Выбрать`, справа `Закрыть`.

**Смещение индексов.** Жёлтая подсказка — это первая строка тела, поэтому реальные
пункты сдвинуты на единицу: `listItem` 0 — подсказка, 1 — порт, 2 — дом, 3 —
работа. В колбэке диспетчеризация идёт по `listItem - HINT_ROWS` (`HINT_ROWS = 1`),
с bounds-проверкой (вне диапазона / сама подсказка — игнор).

### Диспетчеризация выбора (колбэк, всё перепроверяется серверно)

Колбэк заново берёт живого игрока (`getPlayers().get` + null) и сессию
(`PlayerSessionService::get` + `NO_ACCOUNT`-гард — без сессии выбору некуда
сохраняться). Затем по индексу:

- **Порт** (`item 0`, внутренне `Choice::Station`): `setChoice(Station)` →
  `applySpawn` → `INFO_COLOUR` `Теперь вы появляетесь в порту`.
- **Дом** (`item 1`): серверная проверка владения — `houseOf(std::to_string(accountId))`.
  Нет дома → `ERROR_COLOUR` `У вас нет своего дома. Займите свободный дом на карте`,
  **выбор НЕ меняется**. Иначе `setChoice(Home)` → `applySpawn` → `INFO_COLOUR`
  `Теперь вы появляетесь у своего дома`.
- **Место работы** (`item 2`): серверная проверка — `getMemberFaction(playerId) ==
  NO_FACTION` ИЛИ у фракции точка спавна не задана (`!getFaction(factionId)` /
  `!spawn.defined`) → `ERROR_COLOUR` `Вы не состоите в организации`, **выбор НЕ
  меняется**. Иначе `setChoice(Work)` → `applySpawn` → `INFO_COLOUR`
  `Теперь вы появляетесь на месте работы`.

Все строки через `u()` (cp1251). При отказе выбор остаётся прежним, диалог
закрывается, ошибка в чат. Цвета — ИГРОВЫЕ: успех `INFO_COLOUR {120,220,255}`,
отказ `ERROR_COLOUR {255,90,90}`.

## Применение и резолв

`applySpawn(player)` — единственный писатель точки спавна, зовётся для ВСЕХ (без
гейта фракции): `m_spawnService.setSpawn(player, resolveSpawn(player))`. Теперь это
буквально так: `PlayerAuthSystem` на логине больше не задаёт свою точку (там стоял
хардкод, который перебивал выбор и ставил игрока в стену) — ему нужна была лишь
пересборка spawn-инфо после смены скина, и для этого есть
`PlayerSpawnService::refreshSpawnInfo`, который точку не трогает. `setSpawn`
задаёт точку для ВСЕХ последующих спавнов (вход/смерть/respawn), сразу прокидывая
её в class-данные клиента — авторизационный спавн приходит уже в выбранную точку,
без промежуточного «порт, потом переехал». НЕ телепортирует сейчас.

`resolveSpawn(player)` ВСЕГДА возвращает валидную точку:

- **Station** → фикс. точка порта (внутренний id остался `Station`, координаты —
  портовые, см. таблицу ниже).
- **Home** → `houseOf(std::to_string(accountId))` (accountId из сессии). Дом есть →
  `{exit, snapToQuarterTurn(exitAngle + 180), interior 0, vw 0}` — точка ВЫХОДА из
  дома и разворот лицом ОТ двери, ровно как в `HouseSystem::onExitPickup`. Дома нет
  / нет сессии → **фолбэк на порт**.

  **Почему не `entrance`.** Пикап входа — тип 1 (подбор по касанию), и
  заспавненного прямо на нём клиент «собирает» немедленно: игрока уносит в интерьер
  дома (vw `2000000+id`) сразу после логин-спавна. Точка выхода лежит в 2 м
  (`HouseService` `EXIT_DISTANCE`) за спиной создателя, в основном мире —
  снаружи и не на пикапе.

  **Разворот и камера дублируются НЕ здесь.** `PlayerSpawnService::handleSpawn` на
  каждом спавне сам ставит интерьер/мир, позицию, `setRotation` из `point.angle`
  и `setCameraBehind()` — ветке «Дом» достаточно отдать правильный угол.

  **Грейс входа на спавне — СТРАХОВКА.** Точка выхода вне радиуса срабатывания
  входного пикапа (клиент собирает пикап примерно с метра, точка выхода — в двух;
  проверено в игре: стояние на ней вход не срабатывает и после истечения грейса),
  но ближе к пикапу точки нет. Выход из дома взводит на ней грейс входа, спавн
  выходом не является — от лага позиции в этой точке спавн не прикрыт ничем.
  Поэтому `HouseSystem` подписан на спавн игрока (`onPlayerSpawn`) и взводит ТОТ ЖЕ
  грейс входа (`EXIT_GRACE`, 1.5 с), если записанная сервером точка спавна — это
  точка выхода СВОЕГО дома (`house->exit` с допуском `SPAWN_AT_EXIT_TOLERANCE`
  0.5 м) в основном мире (интерьер 0, vw 0). Сверка идёт с самой точкой выхода, а
  НЕ с радиусом от двери: `EXIT_DISTANCE` — приватная константа `HouseService`, и
  её правка иначе молча отключила бы гейт. Второго механизма не заводится; см.
  `Docs/Houses.md`.
- **Work** → `getFaction(getMemberFaction(playerId))`. Фракция есть и у неё
  `spawn.defined` → `{spawn.position, spawn.angle, (unsigned)spawn.interior,
  spawn.virtualWorld}`. Не член / нет точки → **фолбэк на порт**.

**Когда выполняется резолв.** `resolveSpawn` вызывается на логине (по старту
сессии), на `/setspawn`, на смене членства (`subscribeMemberChange`) и по
завершении стартовой загрузки владения домами (`subscribeOwnershipLoaded` — только
для игроков с выбором `Home`, см. ниже), НЕ на каждой смерти: результат
замораживается в class-данных клиента до следующего `applySpawn`.
Следствие: если у игрока с выбором `Home` дом пропал в СЕРЕДИНЕ сессии (дев удалил
дом), он продолжит появляться у БЫВШЕГО дома (публичная точка, мир 0) до
следующего `applySpawn` — фолбэк на порт сработает лишь на следующем
`resolveSpawn`. При пропаже источника уведомление НЕ шлём (лишний шум на спавне
вреден).

### Координаты порта (дефолт и фолбэк)

| Поле | Значение | Смысл |
|----|----|----|
| `position` | `{2690.5237f, -2479.6560f, 13.6509f}` | вход в порт Лос-Сантоса; совпадает с проектным дефолтом `PlayerSpawnService::SpawnPoint` — новой константы не плодим. Константы `STATION_POSITION`/`STATION_ANGLE` в `SpawnChoiceSystem.cpp` переименования не получили — id внутри кода остался «станция» |
| `angle` | `89.2331f` | лицом к причалу, не в стену/воду |
| `interior` | `0` | открытый мир |
| `virtualWorld` | `0` | основной мир |

## Перерезолв на смене членства (снимает гонку)

`SpawnChoiceSystem` подписывается на `FactionService::subscribeMemberChange` и на
любую смену членства зовёт `applySpawn(player)` (игрок берётся из аргумента события
— гарантированно валиден). Это нужно по двум причинам:

1. **Снимает гонку двух async-загрузок на логине.** Членство (из `FactionSystem::
   loadMembership`) и выбор `/setspawn` (из `SpawnChoiceSystem::loadChoice`) грузятся
   ДВУМЯ независимыми async-колбэками — порядок их прихода недетерминирован.
   `member-change` триггерит `applySpawn` (из `FactionService::handleSessionStart`),
   и какой бы из двух колбэков ни завершился ВТОРЫМ — у него уже есть И членство,
   И выбор → последний `applySpawn` корректен. Если выбор `Work` пришёл раньше
   членства, `resolveSpawn` сначала даст фолбэк на порт, а пришедший следом
   `member-change` перерезолвит на базу.
2. **Экс-член с выбором `Work`, ВЫШЕДШИЙ из орга в середине сессии**, иначе остался
   бы со спавном в базе (возможно приватный `virtualWorld`/интерьер фракции).
   Перерезолв на выходе даёт фолбэк на порт (`resolveSpawn` для `Work` без
   членства → порт, внутренне всё тот же `Station`).

`SpawnChoiceSystem` уже зависел от `FactionService` — новой зависимости подписка
не добавляет.

## Перерезолв спавна «Дом» по завершении загрузки владения (старт-гонка)

Симметрично гонке членства, у выбора `Home` есть СВОЯ старт-гонка: владение
домами (`house_owner`) грузится async ПОСЛЕ старта сессий, а на логине выбор
`Home` уже применяется (`applySpawn` → `resolveSpawn` → `houseOf`) ДО прихода
зеркала владения. `houseOf` тогда ещё не находит дом → фолбэк на порт → игрок в
стартовом окне спавнится не у дома.

`HouseService` даёт one-shot наблюдатель завершения стартовой загрузки владения
(`subscribeOwnershipLoaded`; `HouseSystem` зовёт `markOwnershipLoaded()` по
завершении `loadOwnershipAsync` на ВСЕХ ветках — успех/ошибка БД). `SpawnChoiceSystem`
подписывается и по событию перерезолвит спавн (`applySpawn`) каждому ОНЛАЙН-игроку
с выбором `Home` — теперь `houseOf` видит загруженное владение и спавн встаёт у
дома. Зеркало `FamilySystem::loadAll` (там после async-загрузки членство
дорезолвится уже-онлайн игрокам). Событие одноразовое: новые логины после загрузки
владения уже видят его, повторно дёргать не нужно (поздняя подписка после загрузки
вызвала бы колбэк сразу). Spawn-authority не нарушается — перерезолв идёт через
`applySpawn` (единственный писатель точки спавна, выбор главнее).

## Персист (БД)

Таблица `player_spawn` (`Sql/player_spawn.sql`, **применяется вручную** — как
`Sql/factions.sql`/`Sql/house_owner.sql`):

| Колонка      | Тип          | Смысл                                            |
|--------------|--------------|--------------------------------------------------|
| `account_id` | BIGINT (PK)  | аккаунт игрока — один выбор на аккаунт            |
| `choice`     | INT (DEF 0)  | 0 — порт/дефолт (внутренний id `Station`), 1 — дом, 2 — место работы |

Схема плоская `INT` без `CHECK` — менять структуру не нужно. Неизвестное значение
при загрузке нормализуется в `Station` (`loadChoice` ниже).

Write-through, как членство фракций (`faction_member`):

- **Запись выбора** — `DELETE WHERE account_id=…` + `INSERT` в ОДНОЙ ТРАНЗАКЦИИ
  внутри `throwQuery` (`startTransaction`/`commit`, при исключении — `rollback` +
  проброс): либо новая строка применилась, либо ничего. Память выставляется ДО
  запроса (оптимистично); при сбое записи `errorCallback` логирует (память
  остаётся — это лишь намерение, резолв всё равно даст валидную точку).
- **Загрузка на старте сессии** — один `selectQuery<int>` по `account_id` с
  **serial-guard** (`SpawnChoiceSystem::loadChoice`): воркер вычитывает значение
  `choice` (нет строки → `Station(0)`), колбэк на ГЛАВНОМ потоке перепроверяет
  `session.serial` (в слоте мог оказаться другой игрок/сессия) и живого игрока
  (`getPlayers().get` + null), нормализует значение (0→Station, 1→Home, 2→Work,
  прочее→Station), кладёт в память (`load`) и `applySpawn`. На конце сессии —
  `reset`.

Нет отдельной save-подписки: выбор пишется в БД сразу при изменении (write-through),
автосейву нечего снимать.

## Порядок регистрации

- `ServiceRegister.cpp`: `registerService<SpawnChoiceService>()` (без зависимостей).
- `SystemRegister.cpp`: `SpawnChoiceSystem` ПОСЛЕ `PlayerSessionSystem` (подписки на
  старт/конец сессии), `PlayerSpawnSystem` (спавн-сервис), `FactionSystem` (членство
  читается в резолве `Work` и в подписке на member-change), `HouseSystem` (владение
  домами грузится на старте — резолв «Дом» видит дома; подписка на
  `subscribeOwnershipLoaded` ставится в конструкторе SpawnChoiceSystem, до того как
  async-загрузка владения завершится). Core-сервисы команд/диалога зарегистрированы
  раньше.

## Три правила

- **Читер-абуз:** выбор привязан к серверной сессии — `accountId` берётся из
  `PlayerSessionService`, НЕ от клиента; в БД пишется ЧИСЛО (индекс выбора), без
  клиентских координат. `/setspawn` валидирует серверно: «Дом» требует ВЛАДЕНИЯ
  домом (`houseOf` по серверному `accountId`), «Место работы» — членства
  (`getMemberFaction`) + наличия точки спавна у фракции (`spawn.defined`). В чужой
  дом / чужую базу попасть нельзя; экс-член перерезолвится на порт. Резолв точки
  серверный (`houseOf`/`getFaction`). Диспетчеризация по индексу строки, не по
  присланному тексту. Значение из БД нормализуется (неизвестное → порт, внутренне
  `Station`). Грейс входа на спавне (`HouseSystem::onPlayerSpawn`) сверяется с
  точкой, ЗАПИСАННОЙ сервером, и с домом, которым аккаунт ВЛАДЕЕТ: клиент ни
  позицией, ни RPC подбора этот гейт не сдвигает, а сам грейс лишь ЗАПРЕЩАЕТ вход
  на 1.5 с — доступа никуда не открывает.
- **Краш/UB:** загрузка по старту сессии — async `selectQuery` с **serial-guard**
  (перепроверка `session.serial` в колбэке — async-колбэк мог прилететь, когда в
  слоте уже другая сессия) + null-гард игрока. Null-гарды везде: `houseOf`
  (nullptr → фолбэк), `getFaction` (nullptr → фолбэк), `session`/`NO_ACCOUNT`,
  `getPlayers().get` в колбэке диалога. Колбэк `member-change` берёт игрока из
  АРГУМЕНТА события (валиден в момент вызова). Колбэк `ownership-loaded` итерирует
  только ЖИВЫХ игроков из `getPlayers().entries()` (валидные указатели), для каждого
  с выбором `Home` — `applySpawn`; событие one-shot (`markOwnershipLoaded` очищает
  подписчиков), повторно не дёргается. Bounds-гард `playerId` во всех
  методах сервиса. Спавн — ТОЛЬКО через `PlayerSpawnService` (он сам санитизирует
  точку: клампы координат/интерьера, finite-гард угла). Запись в БД с
  `errorCallback` + транзакцией (нет частичной записи). Нет ре-энтрантности (никаких
  таймеров, не отменяем себя из колбэка).
- **Перф:** `/setspawn` — ХОЛОДНЫЙ путь (команда → диалог по запросу игрока).
  Загрузка по старту сессии — ОДИН `selectQuery` (не per-tick). `applySpawn`/резолв
  — по входу, по смене выбора и по смене членства, НЕ per-tick. Резолв O(1) по
  выбору; `houseOf` линеен по числу домов (их мало, холодный путь), без аллокаций
  в горячем пути. Спавн-инфо в class-данные пишется один раз на `setSpawn`, не
  каждый кадр.
