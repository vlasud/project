# Стример (Core)

Инфраструктура Core: неограниченное число объектов, пикапов, иконок карты и
3D-текстов поверх клиентских лимитов. Код: `Src/Services/Core/StreamerService`
(механика), `Src/Systems/Core/StreamerSystem` (привод: проход на апдейтах игрока,
развёртка пикапов на тике). Кандидатов ищет `GridService` (spatial hash).
Бизнес-код НЕ зовёт стример напрямую — через фасады `PickupService`,
`MapIconService`, `TextLabelService` (и `addObject` для декора).

## Механика

Стример хранит **определения** (defs), а реальные клиентские сущности
создаёт/удаляет по близости игроков:

- **Объекты** — per-player (`IPlayerObjectData`): каждому игроку ближайшие
  `OBJECT_BUDGET` объектов в радиусе стрима.
- **Иконки карты** — per-player слоты `setMapIcon`: стример занимает слоты
  `0..ICON_BUDGET-1`, слоты `90..99` — ручные (`MapIconService`, персональные
  маркеры). Связка `FIRST_MANUAL_SLOT == ICON_BUDGET` закреплена `static_assert`.
- **3D-тексты** — per-player (`IPlayerTextLabelData`), до `LABEL_BUDGET`.
- **Пикапы** — пул open.mp глобальный, поэтому стриминг глобальный: пикап
  существует в пуле, пока хотя бы один игрок рядом. Проходы игроков помечают
  «нужен» (`lastWanted`), развёртка раз в секунду создаёт/удаляет
  (жизнь после ухода игрока — `PICKUP_KEEP` 2 с, чтобы не мигал на границе).

Проход игрока троттлится (`STREAM_INTERVAL` 500 мс, дедлайны размазаны по
игрокам): один обход сетки, фильтр по радиусу стрима каждого def'а на месте,
отбор ближайших в бюджет (`nth_element` только при переполнении), линейный
merge-diff показанного и желаемого. Все буферы переиспользуются — на
установившемся режиме проход не аллоцирует.

## Бюджеты и радиусы

| Константа | Значение | Комментарий |
|---|---|---|
| `MAX_STREAM_DISTANCE` | 300 м | максимум радиуса стрима и радиус обхода сетки |
| `OBJECT_BUDGET` | 400 | клиентский лимит объектов ~1000, запас под глобальные/ручные |
| `ICON_BUDGET` | 90 | клиентский лимит 100; слоты 90..99 — ручные |
| `LABEL_BUDGET` | 200 | per-player пул лейблов 1024; запас под ручные/прикреплённые |
| `PickupService::DEFAULT_STREAM_DISTANCE` | 100 м | клиент рисует пикапы на ~50-80 м |
| `EXIT_HYSTERESIS_SQ` | 1.44 | гистерезис выхода: 1.2 по дистанции, в квадрате |

**Гистерезис выхода** (объекты/иконки/лейблы): уже показанный def остаётся
желанным до `1.2 × streamDistance`, вход нового — строго по радиусу. Движение
вдоль границы не дёргает release/create. При переполненном бюджете отбор чисто
по дистанции — дальний показанный не вытеснит ближнего нового.

**Радиус пикапов**: open.mp сканирует ВЕСЬ активный пул на стрим-тик каждого
игрока (`pickups_main.cpp`), поэтому активный пул держим минимальным — дефолт
100 м у `PickupService::add(..., streamDistance)`, больший радиус передавать
только с обоснованием по месту.

## Virtual world

- **Пикапы** имеют `virtualWorld`: «нужен» ставится только игроком в мире
  пикапа (vw серверный, из `PlayerLocationService` — клиент влиять не может).
  Иначе один игрок в интерьере оживлял бы одноточечные exit-пикапы всех домов.
- **Объекты/иконки/лейблы** vw НЕ имеют: глобальный визуал стримера виден из
  всех миров на тех же координатах. Класть контент в интерьеры через стример
  нельзя без расширения defs.

## Инварианты

- **Обратный индекс пикапов** `m_pickupPoolToDef` (poolId -> defId) зеркалит
  ровно живые пул-экземпляры (`def.poolId != -1`): вставка при create в
  развёртке, стирание при release (развёртка и `removePickup`). Резолв
  `pickupDefByPoolId` — O(1); он стоит на каждом pickup-RPC, а клиент шлёт их
  повторно каждый кадр, пока игрок стоит на пикапе. Пул open.mp динамический,
  poolId не ограничен константой — только map, не массив.
- `pp.objects/icons/labels` отсортированы по defId (merge-diff и бинарные
  поиски). diffIcons двухфазный: сначала все release (возврат слотов), затем
  create — телепорт при полном бюджете иконок не «моргает».
- Валидация подбора пикапа (дистанция/vw/edge-триггер) — в `PickupService`,
  от принятых сервером фактов (`PlayerLocationService`).
